# 开发提示词 #142–#146:抢单规划、出餐时长、劳动者保护、配送费、天气自动化

承接 docs/DEV-PROMPTS-15.md。上一辑把派单算法修对并公开了,这一辑解决五件事,
其中 **#144 劳动者保护是这一辑的地基** —— 其余四条都要服从它。

## 贯穿全篇的前提:算法不能困住人

外卖行业最被诟病的一件事:系统不断压缩配送时间,骑手为了不超时逆行、闯灯、
边骑边看手机。**那不是骑手不守规矩,是算法把人逼到那一步。**

机制是这样形成的:平台用"实际送达时间"反过来训练"预计送达时间",
骑手跑得越快,系统认为越应该更快 —— 一个自我收紧的循环。跑得快的人
不是被奖励,是被加码。

所以本辑定一条**不可协商的原则**:

> **任何由骑手实际表现算出来的统计量,都不得用于收紧对骑手的要求。**

出餐时长统计用来治理**商家**、用来给骑手**更准的预期**、用来给平台**定更合理的
配送费** —— 但**不用来缩短骑手的时限**。这条要写进代码注释、写进公开算法页、
写进测试。

### 142. 抢单推荐:把整单成本讲清楚

```
现在骑手看到的是"到店 X 米、送程 Y 米"两个数,以及一个综合分排序。
但他真正要判断的是**这一单值不值得接**,而这取决于:

  跑多远(到店 + 送程) / 花多久(含出餐等待) / 挣多少(配送费 + 小费)

## 要补的信息

1. **预计总耗时**:到店骑行 + 在店等餐 + 送达骑行。
   在店等餐用该商家的**实测出餐时长分位数**(见 #143),不是拍脑袋的 20 分钟;
2. **每分钟收入估算**:(配送费 + 小费) ÷ 预计总耗时。
   这是骑手真正用来比较的量 —— 一个 3 公里 8 块的单和一个 1 公里 4 块的单,
   哪个划算不看总价看时薪;
3. **不确定度要如实标**:样本不足的商家,出餐时长给区间不给点值,
   并标明"这家店样本还少"。**给一个假装精确的数,比给区间更坏**。

## 排序仍然只是建议

不做强制派单这条不变。多给信息 ≠ 多做决定。
```

### 143. 出餐时长:长期统计,且只用于该用的地方

```
## 数据已经在记,只是从来没人读

`OrderEvent` 完整记录了 accepted → ready 的时间戳。实测本地库里
accepted 2423 条、ready 1578 条 —— **出餐时长一直可以算出来,只是没人算**。

所以这一项主要是聚合 + 反馈闭环,不需要新埋点。

## 要建的东西

1. **按商家 × 时段的出餐时长分位数**(P50 / P80 / P95),滚动窗口(建议 30 天);
2. **样本不足时明确回退**到商家自报的 `promise_ready_minutes`,
   并在所有出口标明"样本不足"。生产目前**没有任何真实出餐记录**
   (收不了钱就没有真实订单),所以这条不是理论情况,是当前状态;
3. **ETA 改用实测值**。现在 `eta.py` 用写死的 20 分钟兜底,
   而商家自报的 `promise_ready_minutes` 根本没被 ETA 读过 —— 两个数各说各话;
4. **商家端看得到自己的分位数**,以及与同品类的对比。
   商家出餐慢,平台掏钱赔付(超时安抚券由平台承担),而商家零反馈 ——
   这个闭环不通,治理就无从谈起。

## 红线(#144)

出餐时长统计**只用于**:给骑手更准的等待预期、给用户更准的 ETA、
治理慢出餐商家、给平台定更合理的配送费。

**绝不用于**:缩短骑手的配送时限、给骑手排名、作为考核指标。
```

### 144. 劳动者保护:算法不困住人(本辑地基)

```
## 一、ETA 只能放宽,不能收紧

**ETA 不得因骑手跑得快而变短。** 具体做法:

- ETA 的骑行时间部分用**保守速度**(建议 15 km/h,含等红灯、找楼栋、爬楼),
  这个数**写死在配置里,不由实际数据训练**;
- 允许因实测**变慢**(路况差、天气恶劣)而放宽,不允许因实测变快而收紧。
  代码里要有明确的单向钳制,并有测试钉住;
- 出餐慢导致的延迟**不计入骑手**。骑手到店时餐没好,那段等待是商家的问题。

## 二、超时的归因要分清楚

现在超时赔付一律由平台承担(不扣骑手不扣商家),立场是对的。
但**归因要记录**:是出餐慢、路上慢、还是 ETA 本身给得太紧?
不记录的话,永远不知道该改哪一头 —— 而且骑手会一直背着"超时"这个名声。

## 三、疲劳保护:连续在线要提醒并降权

`RiderSession` 已经在记在线时长(注释写着"只统计不考核")。加上:

- 连续在线超过 N 小时(建议 4 小时)→ 提醒休息;
- 超过 M 小时(建议 8 小时)→ 抢单池**主动降低推送频率**并置顶休息提示。
  **不硬性禁止**:骑手要吃饭,一刀切断人家收入是另一种不尊重。
  但平台不能装作没看见。

## 四、恶劣天气:加价 + 降速,不是只加价

现在恶劣天气只做一件事:加价 2 元。这不够 ——
**下雨天骑手更危险,而加价会诱使他跑更快。**

所以恶劣天气时:
- 加价照给(全归骑手);
- **同时放宽 ETA**(给用户的预计送达时间自动延长);
- 配送半径可收窄(可选,由城市运营决定)。

只加价不放宽时限,等于用钱买骑手冒险。

## 五、这些承诺要进公开算法页

/transparency/dispatch 的 never_do 里补上:
- 不用骑手的实际速度反过来缩短配送时限;
- 不因骑手一次超时就降低他能看到的单;
- 恶劣天气加价的同时一定放宽时限。

**承诺要能被验证**:每条都要有对应测试。
```

### 145. 配送费:讲得清道理的阶梯

```
现在:2km 内 ¥3,每超 1km +¥1,封顶 ¥10,4km 半径;夜间 +¥2、恶劣天气 +¥2。

## 现有问题

1. **按直线距离算**(#139 已接入骑行路径,配送费口径还没切)。
   实测直线比骑行短 19% —— 骑手一直在亏这部分;
2. **封顶 ¥10 与 4km 半径的组合有个洞**:3.9km 的单和 2.1km 的单差 2 块钱,
   但实际骑行时间可能差一倍;
3. **不含"在店等餐"的补偿**。骑手在店里等 20 分钟,这段时间没有任何收入 ——
   而这不是他的问题;
4. 起步价 ¥3 是否覆盖成本,没有算过账。

## 要做的

- 切换到**骑行距离**计价(单独开关,灰度,切换前新旧口径在真实订单上对比);
- **等餐超时补偿**:骑手到店后等待超过 N 分钟(建议 15),
  超出部分按分钟补贴,**由平台承担,不转嫁给商家或用户**
  (平台无补贴预算,但这一项属于履约成本不是营销补贴,要单独讲清楚);
- 每一项都要能在公开页讲出道理,和派单算法一样。

**配送费 100% 归骑手的承诺不变** —— 加价、补偿都归骑手,
审计恒等式(services/audit.py)照旧强制校验。
```

### 146. 天气自动化:按区县取,自动加价

```
现在恶劣天气加价是**管理员手动开关**,而且是**全局的** ——
成都下暴雨,北京的骑手也拿加价;北京下雪没人开开关,骑手就白挨冻。

## 选定 Open-Meteo(已实测)

- **无需 key**、官方声明免费商用,不必再申请任何资质;
- **按坐标查**,天然到区县甚至街道级;
- 返回标准 **WMO 天气码**,可编程判定,不是一句中文描述。

实测差异(同一时刻):成都锦江区 降水 0.2mm / 风 8.8km/h / 码 53;
成都双流区 0.1mm / 4.6km/h / 码 51;北京朝阳 0.0mm / 码 3。
**区县级差异真实存在**,全局开关必然误伤。

⚠️ 实测过一次:连续快请求会被限流(SSL EOF)。**必须缓存 + 限速**。

## 要做的

1. `services/weather.py`:按坐标查,结果按 ~10km 网格 + 30 分钟缓存
   (天气不是按米变的,网格粗一点没关系,配额省很多);
2. **判定规则要公开**:什么天气码 + 多大降水 + 多大风速算"恶劣",
   阈值写在代码常量里,由 /transparency 读同一份(与派单算法同一口径);
3. **自动开关**:清扫任务定期刷新各运营城市的天气,自动开/关加价。
   管理员保留**手动强制开**的能力(自动判定漏了也能救),
   但**不保留手动强制关** —— 天气恶劣却关掉加价,没有正当理由;
4. 恶劣天气时**同时放宽 ETA**(见 #144),不是只加价;
5. 三端呈现:骑手端显示"当前恶劣天气,本单加价 ¥X"、
   用户端显示"雨天配送,预计送达已顺延",商家端提示可能出餐延迟。

## 降级

天气服务挂了 → 维持当前开关状态不变,**不要因为查不到就关掉加价**
(正在下雨时把加价关了是最坏的结果)。记日志,管理员可手动介入。
```

## 执行记录

五项全部落地。**#144 劳动者保护是地基**,其余四项都调用它。

### 核心:ETA 只许放宽不许收紧

`labor_guard.clamp_eta_minutes(proposed, baseline)` 是那条原则的执行点。
写成一个**显式的、有名字的、有测试的函数**,是为了让收紧
**无法不小心发生**:想收紧就必须显式绕过它,而绕过它会在评审里被看见。

骑行速度 `RIDE_SPEED_KMH = 15` 写死,不由实际数据训练 ——
一旦允许它跟着骑手的实际速度走,自我收紧的循环就建立了。

实测验证(同一单约 1.1km):

| 情形 | ETA |
|---|---|
| 兜底(无实测) | 30 分 |
| 商家实测出餐 5 分(**比兜底快**) | **仍 30 分** —— 不许变短 |
| 商家实测出餐 35 分(比兜底慢) | 40 分 —— 该放宽就放宽 |

### 抢单推荐(#142)

抢单卡从「总价 + 到店距离」改为「整单耗时 + 时薪」。实测两单对比:

| | 耗时 | 收入 | 时薪 |
|---|---|---|---|
| 近单 | 11 分 | ¥4.00 | **¥21.8/小时** |
| 远单(含小费) | 38 分 | ¥9.00 | ¥14.2/小时 |

**总价高的那单时薪反而低** —— 旧界面看不出这一点。

真机链路验证:到店 212m / 送 1417m(`route` 真实骑行)、预计 6.5 分、
等餐来源 `measured`、时薪 ¥64.4/小时、顺路等级 none。

### 出餐时长(#143)

数据一直在记(OrderEvent 的 accepted→ready),只是没人读。
滚动 30 天算 P50/P80/P95,批量取(逐个查会把一次抢单变成几十次往返)。

等待预期取 **P80 而非中位数**:按中位数到店有一半概率白等,
而等待成本落在骑手身上。样本 <10 时回退商家自报值并标 `source=declared`。

⚠️ 生产目前**没有任何真实出餐记录**(收不了钱就没有真实订单),
本地也全是 e2e 秒级数据 —— 真实分布要等真实订单。这不是缺陷,是当前状态,
且来源已如实标注。

### 配送费(#145)

新增等餐超时补偿:15 分钟免费、超出每分 ¥0.3、封顶 ¥6,**平台承担**。
不转嫁商家(会让商家宁可晚点按"出餐",数据失真),不转嫁用户。

切骑行距离的开关已就位,**默认关** —— 直接改钱,要灰度对比后再开。

### 天气自动化(#146)

Open-Meteo,无需 key、按坐标查、WMO 标准码。实测同一时刻:

| 区县 | 降水 | 判定 | 加价 |
|---|---|---|---|
| 成都锦江区 | 1.1mm | **恶劣** | ¥2.00 |
| 北京朝阳区 | 0.0mm | 正常 | ¥0 |
| 上海浦东 | 0.0mm | 正常 | ¥0 |

旧的全局手动开关做不到这一点 —— 成都下暴雨北京也加价,
北京下雪没人开开关骑手就白挨冻。

管理员保留**强制开**(自动判定漏了能救),**不保留强制关** ——
天气恶劣却关掉加价,没有正当理由。

### 顺带修的测试问题

**过期的费率假设(5 处)。** 跑久了的库上演示店累计单量进入阶梯降档区间
(实测 1255 单 → 4%),而 e2e_tier_commission / e2e_orders / e2e_finance /
e2e_append_order / e2e_shop_coupon 都把佣金**写死成 5%**。挂的是对的行为。

改为按该店**实际费率**断言,并**顺带加强**:新增「任何档位不得高于 5%
承诺上限」与「净额 = 流水 − 佣金」两条恒等式 —— 比写死一个数守得更严。

**e2e_referral 的自伤。** 风控规则是「同格 24h 内 ≥4 单且多账号」,
而用例里多个被邀请人共用同一个 `LAT/LNG` 常量 —— **用例自己在制造风控命中**,
表现为"邀请奖励偶发不发"。改为每单独立取格。

**e2e_tier_commission 不再拿演示店当基准**,改为自建低单量店 ——
共享状态做基准,在跑久了的库上必然失效。
