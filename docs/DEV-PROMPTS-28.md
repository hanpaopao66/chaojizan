# 开发提示词 #243–#262:商家端鸿蒙原生版(ArkTS)

用户端鸿蒙版已经落地(`apps/user_app_harmony`,27 页 34 路由 10364 行,
接口 85/85)。这一批做商家端。

**先说结论:商家端不能照抄安卓端的听单架构,鸿蒙不给你保活。**
这不是选型偏好,是系统设计的硬边界,下面 #243 讲清楚。整份提示词的排序
都是围着这个约束转的。

## 先摆事实:哪些能做、哪些不能

动手前把三块硬骨头查实了,免得写到一半推翻重来。

| 能力 | 安卓端怎么做 | 鸿蒙侧 | 结论 |
|---|---|---|---|
| 蓝牙小票机 | `print_bluetooth_thermal` SPP | `socket` from `@kit.ConnectivityKit`,`sppConnect` + `sppWrite`,UUID `00001101-0000-1000-8000-00805f9b34fb` | ✅ 能做,三方应用可用 |
| 扫码核销 | `mobile_scanner` | Scan Kit | ✅ 能做 |
| 前台听单 | WebSocket | Network Kit `webSocket` | ✅ 能做(仅前台) |
| 语音催单 | `audioplayers` 循环播 | AVPlayer / Core Speech Kit | ✅ 能做 |
| 云打印 | 服务端飞鹅直推 | 纯服务端,客户端零改动 | ✅ 白拿 |
| **后台常驻听单** | 前台服务 + 电池优化白名单 | **不给** | ❌ 见 #243 |

## #243 听单架构必须重画(整批的地基,先定这个)

安卓端的听单靠三件套(`listen_service.dart`):前台服务把进程钉在前台
优先级、WebSocket 常连、有待接单就每 10 秒语音播报,再引导商家把 App
加进电池优化白名单。**这套在鸿蒙上一件都落不了地。**

鸿蒙的长时任务(`backgroundTaskManager.startBackgroundRunning`)只认这
几种模式:`dataTransfer`(下载上传)、`audioPlayback`、`audioRecording`、
`location`、`bluetoothInteraction`、`multiDeviceConnection`、`voip`;
`taskKeeping` 只给 2in1 设备,`wifiInteraction` 只给系统应用。
**"听订单"不属于其中任何一种。**

有人会想到用 `audioPlayback` 播一段静音音频骗保活。别做:

- 系统会校验声明的模式和实际行为是否一致,对不上照样收走;
- 上架审核这一条是明写的,拒了就是拒了;
- 更要命的是**它不可靠**。我们卖给商家的承诺是"锁屏不丢单",拿一个
  随时可能被收走的机制去兑现这个承诺,等于在午高峰押注。

**正解:推送兜底,而不是保活。**

好消息是服务端**早就是这么设计的** —— `server/app/services/push.py`
里 `notify_new_order` 的注释原话就是「新订单推给商家老板(离线也能听到,
替代只在前台有效的 WebSocket)」。安卓端的前台服务本来就是锦上添花。

所以鸿蒙商家端的听单口径是:

```
应用在前台 → WebSocket 实时推 + 语音催单 + 屏幕常亮
应用在后台/锁屏 → 系统通知(推送),商家点通知回到应用
回到前台 → 立刻全量拉一次订单,补上后台期间漏掉的
```

**要做**:

- `common/Listen.ets`:统一管前台 WS 连接、重连退避、心跳、以及**前后台
  切换**(`UIAbility` 的 `onForeground`/`onBackground`)。回前台必须**主动
  全量拉一次**,不能只依赖 WS 补发;
- 语音催单沿用安卓口径:只要有 `paid` 状态的单,每 10 秒播一次,直到
  商家处理。播报失败退回系统提示音,保证至少响一声;
- **屏幕常亮**:接单页用 `window.setWindowKeepScreenOn(true)`,离开页面
  关掉。商家手机插电放柜台,这一条比什么都实用,而且不需要任何权限;
- 顶部指示灯照搬 #237 的口径:**WS 连着 ≠ 列表拉到了**,两者都新鲜才
  显示正常。鸿蒙这边还要多一档:「应用在后台,靠推送」——这是正常状态,
  不是故障,别让商家以为出问题了。

## #244 推送接入(⚠️ 卡在账号上,先设计后接线)

服务端走的是极光(JPush),`platform: "all"`,但 notification 体里目前
只有 `android` 和 `ios` 两段。极光有鸿蒙 SDK,要补鸿蒙那一段。

**这一条卡在你的开发者账号上**,和用户端第四批那四个 SDK 是同一个卡点:
极光的鸿蒙通道最终是骑在华为 Push Kit 上的,要在 AppGallery Connect 里
注册应用、拿 Push 的 Client ID,还要申请通知消息的**自分类权益**
(不申请就落进默认分类,响不响、会不会被免打扰拦掉都不由我们说了算)。

**账号没下来之前能做的**:

- 客户端把**注册 token → 上报服务端 → 绑定 `u{user_id}` 别名**这条链路
  按接口契约写好,SDK 那一层留成一个 `PushChannel` 接口,先给一个空实现;
- 点通知进应用的**冷启动/热启动跳转**要现在就打通:通知里带 `order_no`,
  应用起来后直接落到那一单。这段逻辑和 SDK 无关,可以先写完先测;
- 服务端 `push.py` 补鸿蒙那一段。**字段名和平台值照极光当时的文档写,
  别照抄这份文档里的猜测** —— 我没能核到确切的键名,写错了是静默不发。

**账号下来之后要验的**(写进验收清单,别口头过):

1. 应用杀干净 → 下一单 → 手机响不响、通知点进去落不落到那一单;
2. 免打扰模式下响不响(这一条决定要不要去申请自分类权益);
3. 通知延迟的中位数和 P95 —— 超过 30 秒的话「锁屏不丢单」就是句空话,
   要回头找极光/华为要说法。

## #245 蓝牙小票机(ESC/POS,鸿蒙侧重写)

`printer_service.dart` 285 行,ESC/POS 排版那部分(`_Esc` 类、
58mm=32 列、GBK 编码、左右对齐补空格、走纸半切)是**纯字节拼装,
没有任何平台依赖,逐行照搬即可**。要重写的只有传输层:

```typescript
import { socket } from '@kit.ConnectivityKit';

const SPP_UUID = '00001101-0000-1000-8000-00805f9b34fb';
// sppConnect(deviceId, {uuid: SPP_UUID, secure: true, type: 0}, cb)
// → socketId,然后 sppWrite(socketId, buffer)
```

三个坑写在前面:

1. **GBK 编码**。热敏机的字库不认 UTF-8,这是行业约定不是我们的选择。
   ArkTS 侧没有现成的 `fast_gbk`,要么找鸿蒙的 `util.TextEncoder`
   看支不支持 GBK,要么**自带一张 GB2312 码表**。这是这一条里唯一可能
   卡住的地方,先做技术验证再往下写;
2. **配对在系统设置里做**。鸿蒙侧应用内直接配对经典蓝牙的路子不通畅,
   界面上要直说「先去系统设置里和打印机配对,再回来选」,别让商家
   在应用里点半天没反应;
3. **重连重试**照搬安卓端:断连自动重连重试一次,两轮都失败才报错。
   中间那轮的异常故意吞掉——还有第二次机会时报错等于骗人。

版式要能被测试断言。安卓端把 `ticketBytes()` 标了 `@visibleForTesting`,
理由是「58mm 只有 32 列,一行排不下就折行,而折行的地址在店里读起来
是灾难」。鸿蒙侧同样要留这个口子,并把安卓端那两条用例翻过来
(`顾客选送到楼下要印出来`、`自取单印取餐码,不印配送费`)。

## #246 地基复用:直接搬用户端鸿蒙版的 common/

`apps/user_app_harmony/entry/src/main/ets/common/` 里这几个是**角色无关**
的,原样拷过来:

| 文件 | 行数 | 说明 |
|---|---|---|
| `Api.ets` | 184 | 唯一网络出口,鸿蒙错误码翻人话,401 回登录页 |
| `Session.ets` | 152 | preferences 存 token,长辈版开关 |
| `Upload.ets` | 161 | photoAccessHelper 选图,不申请相册/相机权限 |
| `Money.ets` | 35 | 分转元,别在客户端做浮点 |

`Cart.ets`(选券比价)和 `Pay.ets` 商家端用不上,不拷。
`UserApi.ets` 换成 `MerchantApi.ets`,接口另列(#247)。

**规矩照旧,一条都不许破**:

- 任何页面不许自己 `http.createHttp()`。用户端做到了零处裸调,好处是
  超时、鉴权、401、错误文案只有一份口径。开一个口子就会出现"这页报错

  映射。否则迟早出现"骑手端说爬楼费、顾客端说远距离费";
- 金额一律是「分」的整数。

## #262 三端一致性回归

鸿蒙商家端上线前,拿同一家店在安卓端和鸿蒙端各跑一遍,逐项比对:

- 同一单在两端显示的**金额、状态文案、配送费构成**必须逐字一致;
- 同一单在两端打出来的**小票版式**必须一致(拍照比对);
- 佣金、满减、券后实收的计算结果必须一致。

这一条不是形式主义。三端说法不一致,商家会觉得平台在糊弄他,
而账目透明是这个平台唯一抄不走的差异点。

# 落地记录

`apps/merchant_app_harmony/`,7482 行 ArkTS、14 个页面。P0 / P1 / P2 全部闭环。
下面是**实际怎么做的**,以及提示词里没写到、动手才发现的东西。

## #245 的 GBK:是唯一能推翻方案的未知数,解掉了

提示词说「要么找鸿蒙的 `util.TextEncoder` 看支不支持 GBK,要么自带码表」。
实际是第三条路:**`TextEncoder` 不支持 GBK,但 `TextDecoder` 支持。**
所以把 GBK 所有合法双字节码位摆成一个 buffer 解一次,反查就得到编码表。
21791 条,几毫秒,比往仓库里塞几十 KB 静态码表干净。

**第一版写错了,而且是那种不会报错的错。** 非法码位在 `fatal:false` 下会解成
「替换字符 + 尾字节」**两个**字符,从那里开始整条位置对应关系全体错位 ——
23940 个码位解出 24728 个字符,后面每个字的编码都是错的。
不抛异常、不报错,只有商家拿到那张乱码小票时才知道。

修法:每个码位后跟一个 `\n`(0x0A 不在 GBK 次字节范围 0x40–0xFE 内,
不可能被当成双字节的一部分吞掉)。按它切开,段长不为 1 的就是非法码位。
修完拿 Python 的 cp936 全量对拍:**21887 个可编码字符,逐字节零差异**。

校验脚本进了 `tools/verify_gbk.py`。

## #245 的小票:版式与安卓端逐行比对一致

排版层从 `printer_service.dart` 逐行搬,**刻意不做改进** —— 两端一旦分叉,
同一单印出来长得不一样,商家会以为是打印机坏了。

`tools/verify_ticket.py` 拿安卓端 `flutter test` 的输出当基准逐行比对。
写这个脚本时它自己报了个假失败:时间那行两端都用**本地时间**,基准的时刻
取决于跑测试那台机器的时区。改成只核格式不核数值了 ——
**一个会报假失败的校验脚本比没有更糟**,迟早被人忽略。

## #243/#244 的落地:架构约束写进了代码

`module.json5` 里**没有 `backgroundModes`,是有意的**,理由和「为什么不用
audioPlayback 播静音音频保活」都写在那个文件的注释里 ——
免得以后有人看到别的应用有就"顺手补上"。

`PushChannel` 的空实现 `setup()` 返回 **false 而不是假装成功**。
假装更坏:界面会显示「推送已开启」,而商家锁屏后一单收不到,
等他发现已经丢了一天的单。店铺页那行状态照实说:
推送没接通就写「应用退到后台可能收不到新单」。

## 顺带修了鸿蒙**用户端**一个真 bug

对着服务端 schema 建商家端模型时发现的:`fee_parts` 服务端返回的是
**字典**(`{"base": 300}`,见 `schemas.py` 的 `fee_parts: dict`),
而 `user_app_harmony` 把它建模成了 `FeePart[]` 并直接 `ForEach` ——
配送费构成那一块**一项都渲染不出来**。就算能渲染,显示的也是 `base`
而不是「基础配送」,和它自己上面那行注释(「中文名由服务端下发」)相矛盾。

两端都加了 `feePartList()` 摊平函数,用服务端下发的中文名。

## 页签的一个决定:订单页常驻

四个页签 订单/菜品/对账/店铺,和安卓端同一套顺序。

**订单页用 `Visibility.None` 隐藏而不是销毁** —— 它持有 WebSocket、轮询和
催单定时器,切到菜单页就销毁的话,商家在看菜单时就听不到单了,
而看菜单恰恰是午高峰前最常做的事。

## #258–#261 P2:做完了,其中两条和提示词预期不同

**团购券核销比预期简单**:Scan Kit 的默认界面扫码由系统托管相机,
**应用侧零权限声明** —— 比安卓端还省一步(安卓端要先弹一次权限说明
再申请 CAMERA)。另外扫码取消也会走 catch,那里**不能报错** ——
主动取消不是故障,弹个红字只会让人以为出了问题。

手输入口**一直摆在那儿**,不藏在「扫码失败」之后。顾客屏碎了、码糊了、
店里光线暗都会发生,取餐窗口前不能让商家先失败一次才找到备选路径。

**资质页把两张证合成一页,但后果分开写**。提示词只提了许可证那个坑,
写的时候发现更要紧的是:健康证到期**只提醒不停业**(证是按人的,
一个员工过期停整家店不成比例),许可证过期**会停业**(7 天宽限期后暂停接单)。
这两句话必须分别写在各自那一块上 —— 混了商家会以为许可证过期也只是提醒一下。

老客召回那一页把「平台不会给你顾客名单」写在界面上,不是写在隐私政策里。
商家问「为什么不给我名单」的时候,答案要就在他眼前。

## 加了一个静态检查:空列表和加载失败长得一样

这是这个仓库反复出现的一类 bug,安卓端为此改过一整批(#240)。
`tools/check_error_states.py` 让它能被机器查出来:

**判据**:一个页面只要**进页面就自动拉数据**,就必须同时有错误态字段和
重试入口;所有页的空 `catch` 都要有注释说明为什么静默。

第一版判据写宽了,把「用户点按钮才发请求」的页(登录、订单详情)也算进去,
报了三个假警。那些页的重试就是再点一次按钮。**报假警的检查器比没有更糟**,
迟早被人忽略 —— 收窄到只看 `aboutToAppear` 里有没有拉数据。

三个脚本都验过能真抓到缺陷,不是只验它不报警:
往 `FinancePage` 注入「去掉错误态字段 + 塞一个空 catch」,脚本报两处。

## 还没做的

商家入驻、许可证换证的**提交**(要拍证照原件)、老客召回的**发券**动作 ——
三样都是低频的一次性操作,界面上直说「请在安卓端或网页端完成」,不含糊。

店铺页只做了每天真会用到的那几项。满减/满赠/店铺券/员工这些低频设置先不做 ——
安卓端的 `shop_tab.dart` 就是这么长到 2100 行的(刚拆完),别在鸿蒙端再来一遍。

**多报了 7 项。** 改成只扫 `pages/` 目录之后才是真实的 15/31。
教训和写 `verify_ticket.py` 时一样:**校验脚本自己也要被怀疑一次。**

## 缺的 16 项分三类,性质不同

## 地图:没 SDK 也能做,而且不算降级

华为 Map Kit 和腾讯的鸿蒙地图都要开发者账号(和推送同一个卡点)。
但商家在这两个场景真正需要的是**多远**和**怎么去**,后者系统地图做得比内嵌好。

所以给距离(和服务端 `haversine_m` 同一个公式)+ `geo:` scheme 拉起系统地图。
商家本来也要切到高德/百度才能真正导航,内嵌地图只是多看一眼。

## 微信进件:顾虑提过了,按决定做,但规矩写死在代码里

我提过「再实现一遍等于把攻击面翻倍」。既然要完全对齐,就做 ——
三条规矩写在 `ApplymentPage.ets` 的类注释里,不是散在各处:

1. 客户端永远拿不到明文(服务端只回尾 4 位),输入框回填不了完整值;
2. **空输入框 ≠ 清空**,只提交本次真填了的字段 ——
   把空串发上去会把已存的银行账户抹掉,而商家完全不知道;
3. 不存 preferences、不放 AppStorage、不打日志,提交完立刻从内存清掉。
