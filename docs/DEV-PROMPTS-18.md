# 开发提示词 #150–#153:商家端深化

参照:骑手端截图的拆解方法 + 常见商家后台(美团/饿了么商家版)的功能面。

## 先说结论:商家端的问题和骑手端不一样

骑手端的空白是「能力有、入口散」。**商家端不是** ——
30 个 `/merchants/me` 端点几乎全都接上了界面(订单/菜品/对账/店铺四个 tab
覆盖了促销、唤回、员工、备货、售后、发票、打印、券、评价回复……)。

商家端真正的问题是三类:

1. **闭环没通**:平台替商家的慢出餐掏钱赔付,而商家看不到自己慢在哪;
2. **只有当下,没有趋势**:能看到今天卖了多少,看不出「在变好还是变坏」;
3. **只有结果,没有诊断**:单量掉了知道掉了,不知道为什么掉。

### 150. 出餐时长闭环(#143 的欠账,优先做)

```
**这是上一辑没做完的事。** DEV-PROMPTS-16 的 #143 第 4 条明写
「商家端看得到自己的分位数,以及与同品类的对比」,而实际只把 prep_time
接进了骑手抢单池 —— 商家自己看不到。

## 为什么这条最优先

现在的链路是断的:

- 商家在店铺设置里**自己填**「承诺出餐时长」,没人核;
- 骑手抢单时看到的等待预期已经用上了**实测 P80**;
- 超时赔付**由平台承担**(安抚券,eta.py 明写不扣骑手不扣商家);
- 而商家**零反馈** —— 他不知道自己实际出餐比承诺慢多少,
  更不知道这让平台掏了多少钱。

**平台掏钱、商家无感、问题不改** —— 这个闭环不通,治理就无从谈起。

## 要做的

服务端加 `/merchants/me/prep-time`:
- 自己的 P50 / P80 / P95(近 30 天,复用 services/prep_time.py);
- **与自己承诺值的差距** —— 这是商家最该看到的一个数;
- 与**同品类**中位数的对比(不是排名,是参照系);
- 样本不足时明说「样本还少」,不给假装精确的数。

商家端在「店铺」tab 的「承诺出餐时长」旁边直接显示实测值。
让商家改承诺值时**看得见自己实际做得到多少** —— 现在他是闭着眼填的。

## 红线(承接 #144)

这个数**只用于**:给商家反馈、给骑手更准的等待预期、给用户更准的 ETA。

**不用于**:给商家排名、当作扣分依据、影响商家在用户端的曝光。
理由和骑手那条一样 —— 一旦分数影响生意,商家就会开始为分数经营
(比如提前点「出餐」而实际没好),数据反而失真。
```

### 151. 经营趋势:看得出在变好还是变坏

```
现在 /merchants/me/analytics 给的是**当期快照**(时段分布、菜品排行、
客单价、复购)。商家看完只知道「今天是这样」,不知道「比上周好还是差」。

## 要做的

- 关键指标的**环比**:单量、营业额、客单价、复购率、出餐时长;
- 用**周**而不是天:外卖有很强的周内节律(周末 ≠ 周三),
  按天比会把节律当成趋势,得出「周一生意变差了」这种废话;
- **变化要给量级而不只是方向**:「单量比上周 -12%」比「单量下降」有用得多;
- 趋势图只画最近 8 周 —— 再长商家也不会看,徒增加载时间。

## 不做的

不做「同行对比」「区域排名」。理由同 #150:一旦排名影响生意,
商家的动作就会从「把菜做好」变成「把数字做好看」。
```

### 152. 经营诊断:单量掉了,为什么

```
`/merchants/me/quality` 已经有一些质量信号(拒单率/超时率等),
但它是**孤立的数字**,不回答商家真正的问题:「我单量掉了,是什么原因」。

## 要做的:把已有信号串成解释

拿掉的单量,按可归因的原因拆开。数据全部已有,只是没串起来:

- **拒单**:拒了多少单(orders 里有);
- **停业/休息**:歇业时长(merchants.rest 有记录);
- **缺货下架**:多少单因菜品售罄没成交(dish sell-out 有记录);
- **出餐慢**:超时单量(#150 的数据);
- **起送价/配送范围**:多少人看了没下单(需要埋点,可以后置)。

每条给出「影响了大约多少单」的估算,并**明确标注这是估算** ——
给一个精确到个位的假数字,比给区间更坏。

## 呈现

不做一堆图表。做成**一句话诊断 + 可点开的明细**:
「本周比上周少 23 单,其中约 14 单来自 3 次缺货下架」。

商家要的是「我该改什么」,不是「这是你的数据」。
```

### 153. 商家端也该有一份「平台承诺」

```
骑手端的「我的」中心底部放了平台承诺(配送费 100% 归骑手、算法公开、
不按评分差别对待……),每条链到可验证处。

**商家端没有对应的东西** —— 而商家最关心的承诺同样具体:

- 佣金 5% 封顶,且**阶梯只降不升**(commission_tiers 的规则已实现:
  重算取 min(档位费率, 现费率),管理员手工调低的店绝不上调);
- 配送费不抽成;
- 券未核销不收费;
- 评价不删除、不能花钱删差评(reviews 的 moderation 是标记不是删除);
- 出餐时长统计不用于排名、不影响曝光(#150 的红线)。

放在「店铺」tab,每条链到 /transparency 的对应位置。

这不是营销文案 —— **它是可验证的**,和骑手端那份一样:
点进去能看到真实费率、真实分账、真实规则。
```

## 明确不做的

- **同行排名 / 区域榜单**:一旦排名影响生意,商家就会为数字经营;
- **付费推广 / 竞价排名**:与「不加价、不竞价」的立场直接冲突,
  而且它本质是让商家把省下的佣金再交回来;
~~满屏图表看板~~ —— **改为要做**(见 #154)。

我原先的理由是「商家在收银台前扫一眼,要的是我该改什么」。
这个顾虑对**订单页**成立,但**经营看板本来就不是扫一眼的场景** ——
它是打烊后坐下来看的。两种场景要的东西不一样,不该用一个理由否掉另一个。

所以 #154 做看板,但守住一条:**每张图都要能回答一个具体问题**,
不是"把数据画出来"。答不上"看了这张图商家会做什么决定"的图,不放。

### 154. 经营看板(打烊后坐下来看的那一屏)

```
和订单页不同,看板是**打烊后复盘**的场景 —— 可以信息密、可以多图。

## 每张图必须能回答一个具体问题

判据:**看了这张图,商家会做什么决定?** 答不上来的图不放。

| 图 | 回答的问题 | 商家的动作 |
|---|---|---|
| 近 8 周单量/营业额趋势 | 生意在变好还是变坏 | 决定要不要调整 |
| 分时段单量热力 | 哪个时段是主力、哪个时段空着 | 调整备货与人手 |
| 出餐时长分布 | 我到底多久出一单 | 改承诺值、改后厨流程 |
| 菜品贡献(销量×毛利位次) | 哪些菜该主推、哪些该下架 | 调菜单 |
| 流失去向(#152 的诊断) | 单量掉在哪一环 | 针对性修 |

## 呈现纪律

- **先结论后图表**:每张图上方一句话说明它说明了什么,
  不要让商家自己从折线里读结论;
- **环比用周不用天**:外卖周内节律强,按天比会把节律当趋势;
- 商家端是 operate 密度(#134),图表的点击区与字号跟着放大;
- 没有数据时给「还没有足够数据」,**不画一条平线假装有** ——
  平线会被读成"生意很平稳"。

## 不做的

不做同行对比、不做区域排名 —— 一旦排名影响生意,
商家的动作会从「把菜做好」变成「把数字做好看」。
```

## 执行记录

### 已做

**#150 出餐时长闭环**。新增 `/merchants/me/prep-time`,商家端在「承诺出餐时长」
旁边直接显示实测值,**编辑弹窗里也带上** —— 他填的那一刻最需要看到,
不然还是闭着眼填。

口径用 **P80**,和骑手抢单时看到的等待预期是**同一个数**。
不一致的话商家会觉得「我明明 15 分钟就出餐了,骑手凭什么说要等 22 分钟」。

用**造出来的真实间隔**验过:P50/P80/P95 = 20/26.8/32.6 分钟,承诺 15 分 ——
差距 11.8 分钟。在这之前这个差距没有任何人看得到,而超时安抚券是平台在掏钱。

(演示库那家老店加了出餐下限后样本归零,界面如实显示「样本还不够」,
原因见下面「实机跑起来才发现的」第 ① 条。)

**#151/#152 经营趋势与流失诊断**。新增 `/merchants/me/trend`,按自然周
(北京时间)聚合,环比给量级不只给方向,流失按可归因原因拆开。

**#153 商家版平台承诺**。五条,每条都链到可验证处。

**#154 经营看板**。五张图,每张上方一句话结论。不引图表库,
用 Container 柱状 —— 与既有 `analytics_page` 的做法一脉相承。

### 写承诺时发现自己差点写了假话

原计划里「评价不删除」这条,核代码时发现 `appeals.py:255` 有
`review.hidden = True` —— **评价是能被隐藏的**(申诉被人工复核判成立时)。

所以那条没写成「评价不删除、不隐藏」,改写成真实边界:
商家自己删不了(reviews 路由只有回复与追评)、没有任何付费删评口子、
唯一路径是人工复核判申诉成立,**且隐藏后评分会从店铺总分里扣回**,
不存在"删了差评还留着好评分"。

一份有一条假话的承诺比没有承诺更糟 —— 商家撞见那一条,其余四条也不会再信。

### 修的三个真问题

1. **样本不足仍返回分位数**。`/prep-time` 原样端出了 `stat.p50/p80/p95`,
   而 `prep_time.py` 自己的契约是「样本不足就不给点值」。3 单算出来的 P80
   是噪声,商家却会拿它去改后厨流程 —— 给假装精确的数比不给更坏。

2. **空周不补,折线会连成一条直线**。`GROUP BY` 只返回有单的周,
   6/22 和 7/13 之间的两个空周直接消失,图上连成直线,
   商家读成"生意平稳",**实际是一单没有**。补齐后如实显示 0 单,
   且客单价给 `None` 而非 `0`(0 会被读成"客单价跌到零")。

3. **流失归因用 `is_on_sale=false` 是错的**。它包含商家主动永久下架的菜
   (换季、停售)—— 那是正常菜单管理不是流失原因,这家店因此被算出
   「966 道菜下架」。改用 `sold_out_today`:今天卖光的才是"你还想卖但顾客搜不到"。

另外归因**不猜 `cancel_reason` 的文本**。它是自由文本(「牛肉卖完了,抱歉」
这种商家随手写的),按关键词分类今天能对、明天商家换个说法就错。
改用 `order_events.actor_role` 这个结构化信号。

### 实机跑起来才发现的三个(其中一个是危险的)

**① 「实测 0 分钟,承诺值可以往下调」。** 页面渲染出来第一眼就看见
P50/P80/P95 全是 0。查库:近 30 天 3724 单的出餐时长落在 0-1 分钟桶,
最小 0.000 分。

`prep_time.py` 剔了上限异常值(>120 分钟),**却没有下限**。
做一份饭不可能不花时间 —— 这些样本几乎都来自商家习惯性连点
「接单」→「出餐」(很多店接单后先点出餐,等真做好了再叫骑手)。

不修的后果是一条**有害建议**:商家看到「比承诺快 15 分钟,可以往下调」,
真去把承诺调低,然后每单超时 —— 超时安抚券由平台掏、骑手到店干等、
顾客看到的送达时间也不准。**三方一起受损,起因只是一个不该采信的 0。**

加了 `OUTLIER_MIN_MINUTES = 1.0`。加完这家演示店的样本从 3724 掉到 **0**,
界面如实显示「样本还不够」—— 这比「实测 0 分钟」正确得多。

**② 菜品贡献图的排序错位。** 底条按金额缩放、顺序却按份数(analytics 的
原始排序),看上去是"份数递减而条长忽长忽短";更糟的是结论句
「前三道菜撑起了 X%」里的"前三"取的是份数前三,算出来的百分比
对不上任何一句人话。这张图要回答「哪些菜该主推」,就得按金额排。

**③ 柱状图 overflow 5.0。** 本周那根柱加了「进行中」标签后装不下,
高度 118 → 132。

### 还有一个是写代码时看出来的:环比拿本周比上周

`series[-1]` 是本周、**还没过完**。周二拿两天的数据去比上周整七天,
每个周一、周二商家都会看到「单量比上周少了 70%」然后白慌一场。

这跟提示词里警告的「按天比会把周内节律当趋势」是同一类错误,
只是换了个尺度 —— 我差点自己踩进去。改成比**最近两个完整周**,
本周照常画在图上但标 `partial`,柱子描边不填实。

### 测试

新增 `e2e_merchant_insight`(回归 118 → 119 条),把红线钉在**数据结构层**:

- 环比的两周必须都是完整周,且不能是 `weeks[-1]` ——
  这条最容易被改回去,`series[-1] vs series[-2]` 看着更简单。
