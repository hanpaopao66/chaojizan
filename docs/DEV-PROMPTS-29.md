# 开发提示词 #263–#268:骑手端接单偏好补齐

来源是一次对照调研(见 [RIDER-PREFS-BENCHMARK.md](RIDER-PREFS-BENCHMARK.md)):
美团众包、蜂鸟众包(淘宝闪购)有而我们没有的功能,逐条过了一遍。

**借的是功能,不是立场。** 那份调研里最重要的发现是 2025 年 12 月美团上线
「分配抢单」—— 订单由系统分配、骑手无权自主修改、拒单可能扣分降权。
我们的 `dispatch.py:15` 写着「不做强制派单」,这条不动。下面五条都是
**扩大骑手的选择权**,没有一条是往回收的。

---

## 先说一条查错了的:红灯补时不用做

调研里看到劳动报报道美团试点「红灯补时」,我一开始判断我们的 ETA
没给红灯留余量 —— **这个判断是错的**,基于误读。

我读的是 `eta.py` 的 `ETA_MINUTES_PER_KM = 5`,但那只是 `baseline` 兜底值。
真正走的是 `labor_guard.ride_minutes()`,速度常量:

```python
RIDE_SPEED_KMH = 15.0
# 15 km/h 是**保守**取值:电动车空载能跑 25,但真实配送包含等红灯、
# 找楼栋、爬楼、等电梯、找不到门牌打电话。按巡航速度算 ETA,
# 等于默认骑手一路绿灯且送到楼下就完事。
```

**红灯余量早就在里面了**,做成了统计余量而不是逐单补时。而且比美团
更进一步:`clamp_eta_minutes` 只许放宽不许收紧,速度常量明令不由骑手
实际表现训练 —— 那行注释说破了为什么:

> 一旦允许它跟着骑手的实际速度走,自我收紧的循环就建立起来了 ——
> 骑手跑得快 → 速度上调 → 时限变紧 → 只能跑更快。

美团需要逐单补时,是因为它的 ETA 压得紧、要打补丁;我们是一开始就放松的。
**做逐单红灯检测是在解一个我们没有的问题。**

真实差距只剩一条,而且不大:**统计余量不区分路线**。市区一路八个红灯和
郊区一个红灯拿的是同一份余量。要补的话见 #268,那是个可选项不是必做项。

## #263 同时接单上限,交给骑手自己定(先做这条)

`config.py:132` 有 `rider_max_active_orders: int = 3`,`riders.py:1406`
拿它拦接单。问题是**它是全平台一个常数,骑手改不了**。

新手 3 单会超时,老手 3 单嫌少。而这个数**只影响他自己** ——
平台没有任何理由替他决定 3 是对的。

美团和蜂鸟都让骑手自调,两边的新手攻略都写「先设成 1 单」。

**要做**:

- `User` 加 `rider_max_active` 字段(null = 用平台默认);
- 接单校验取 `min(骑手自设, 平台上限)` —— **平台常数留作硬上限**,
  骑手可以往下调不能往上调。理由不是不信任他:同时 8 单必然有人超时,
  而超时的赔付是平台出、差评是他背;
- 偏好面板加一项,和现有 `grab_*` 那几个放一起;
- 文案照现有口径:每一项都写清楚「这只影响你看到/接到什么」。

## #264 收工单:往家的方向

蜂鸟/淘宝闪购有「回家单」。我们的 `same_way` 是按**手上已有单**的绕路
增量算的(`riders.py:986` 附近),而 `riders.py:993` 那段注释自己点明了:

> 手上没单时不生效 —— 那时无所谓顺不顺路

**而收工那一刻恰恰是手上快空了的时候。** 顺路筛选正好在最需要它的时刻
失灵,结果是最后一单接到反方向,白骑十公里回家。

**要做**:

- 骑手设一个「收工方向」(一个坐标,不是地址 —— 别让他把家庭住址填进来。
  用「我要回哪个大概位置」的口径,取个路口/地标就够);
- 开关打开后,`same_way` 的参照点从「手上单的送达点」换成这个坐标,
  绕路增量的算法**原样复用**,不新写一套;
- **默认关,而且不常驻** —— 它是收工前几十分钟才用的东西,
  常驻开着会让他白天也只看一个方向;
- 存的是坐标不是地址文本,而且**不进任何日志**。骑手的住处附近是
  比订单地址更敏感的东西。

⚠️ 隐私上这条要想清楚再做:哪怕存的是路口坐标,连着看几天也能推出
他住哪。可以考虑只存到街道级(截断到小数点后 2 位,约 1km 精度)——
对「往这个方向」这个用途够了。

## #265 排序交给骑手选

蜂鸟让骑手选运单排序,我们是服务端一套综合分排完就定死。

**这条和我们自己的立场是一致的。** `dispatch.py:15` 写着
「算法只负责把信息排得更有用」,那**排得对不对该由骑手说了算** ——
我们已经把算法公开给他看了(抢单页旁边的「抢单怎么排的」),
却不让他换个排法,这中间是断的。

**要做**:

- 抢单列表加排序切换:综合(默认)/ 配送费 / 距离 / 等待时长;
- **不做服务端持久化的必要性存疑** —— 这是个当下的选择,不是长期偏好。
  先做客户端内存态,骑手反馈要记住再说;
- 综合分仍是默认,并且在切换器旁边保留「抢单怎么排的」入口 ——
  换了排法之后更要能查"综合分是怎么算的"。

## #266 新手默认收窄接单半径

`grab_radius_km` 默认 `null`(不限)。新骑手第一次上线看到的是全城的单,
最容易接一个十公里的然后超时 —— 而超时的差评他自己背。

美团给新手推荐 3 公里内。

**要做**:

- 新骑手(完成单数 < N)首次上线时,把 `grab_radius_km` 默认设成 3;
- **必须明说**:「先给你设了 3 公里,熟悉之后随时改」。
  静默给人设一个筛选,就是我们刚修的那个 bug 的另一面 ——
  他不知道自己被筛过,只会觉得单少;
- 设过一次之后不再自动改。**只在第一次生效**,别变成平台反复插手。

## #267 明确不做:自动接单

美团和蜂鸟都有「自动接单 / 自动接派单」。**我们不做。**

理由不是技术:蜂鸟骑手自己写的攻略里,建议是**关掉它**。这个功能服务的
是平台的派单效率,不是骑手 —— 它会变成一个默认打开、骑手忘了关、
然后自动接下一堆烂单的开关。

我们做的是广播抢单,加自动接单等于把「接不接始终是骑手自己的决定」
这句话架空。

**写在这里是为了留个记录**:以后有人提「友商都有自动接单」时,
这一段就是答案。

## #268(可选)ETA 的路线级余量

前面说了红灯补时不用做,但有个小口子可以顺手补上。

现在 `ride_minutes()` 是 `距离 ÷ 15km/h`,而 `bicycling_m()` 已经在调
腾讯骑行路径接口了(`routing.py:87`),只取了 `distance` 没取时长。
腾讯那个返回里通常也有 `duration`。

**可以做**:ETA 取 `max(常量速度算出来的, 腾讯给的时长)`。

**只许放宽**这一条必须守住:

- 腾讯的时长比我们的常量估计短时,**用我们的** —— 那个接口是按
  普通骑行算的,不含取餐、找楼栋、爬楼;
- 腾讯的时长更长时(市区多灯多路口),用它 —— 这正好补上
  「统计余量不区分路线」那个缺口。

这不违反「速度常量不由骑手表现训练」那条红线:腾讯的时长是路况数据,
不是我们骑手跑出来的数。但**实现时要写清楚这个区别**,
否则下一个人会以为可以拿骑手实际耗时来"优化"。

优先级最低。缺了它只是市区骑手的余量偏紧一点,不是错。


## 验收时要一起看的

这批全是「骑手的选择权」,所以每一条都要过同一个问题:

**这个设置没生效的时候,骑手看得出来吗?**

我们刚修过一个反例:定位取不到时接单半径静默失效,而界面上还选着 3km
(见 `stale_location_prefs()` 和 `test_stale_prefs.py`)。
新加的每一项偏好都要想一遍它会不会有同样的失效路径 ——
**让骑手误以为某件事在生效,比没有这个功能更坏。**
