# 骑手接单偏好:和美团、淘宝闪购的对照

起因是一个具体问题:**我们的「接单半径」以什么为圆心?** 查完发现是骑手
实时 GPS,顺带发现一个静默失效的 bug(已修,见文末)。既然查到这儿,
把商业平台怎么做的一并记下来 —— 有一条是根本性的分歧,值得写清楚。

调研时间:2026-08。信息来自公开报道与骑手社区,**不是官方文档**,
细节可能随版本变。

---

## 一、最根本的分歧:选单权在谁手里

这不是功能差异,是立场差异。

| | 我们 | 美团众包 | 蜂鸟众包(淘宝闪购/饿了么) |
|---|---|---|---|
| 主模式 | **广播抢单,骑手自己选** | 系统派单 + 推荐单 + 抢单 | 智能派单 + 抢单 |
| 拒单后果 | 无 | 扣分、降派单优先级,严重可封号 | 有指派单,可关自动接 |

**2025 年 12 月,美团上线「分配抢单」模式**:订单由系统自主分配,
骑手暂时无权自主修改接单选择。报道里的说法是「拼手速时代宣告终结」,
理由是打击外挂抢单、让分配更公平。

代价是骑手社区里最集中的两条抱怨:**失去自主权**(拒单要扣分),
以及**头部骑手收入被分流**——订单平均分给更多人,而分到的可能是
偏远单、复杂单,单量涨了实收未必涨。

我们的口径写在 `server/app/services/dispatch.py:15`:

> **不做强制派单。** 广播抢单,骑手自己选。算法只负责把信息排得更有用。

这条不打算改。理由不是"我们更善良",是**我们没有资格**:强制派单的
前提是平台对骑手有惩戒权(扣分、降权、封号),而那套东西一旦建起来,
"算法只负责排序"这句话就不成立了。我们连派单都不派,自然也没有
"拒单扣分"这一说。

**这也是我们唯一能拿出来的差异点。** 抽成低是可以被抄的,
"接不接是你自己的决定"是抄不了的 —— 抄它就得放弃对骑手的控制权。

## 二、范围怎么选:圆心跟着人走,还是钉在地上

这是我最初的疑问,两家的答案不一样,而且**都有道理**。

| | 圆心/范围 | 怎么设 |
|---|---|---|
| 我们 | 骑手**实时 GPS** | chips:不限 / 1 / 2 / 3 / 5 km |
| 美团众包 | 推单范围(近单模式) | 新手建议 3 公里内 |
| 蜂鸟众包 | **常驻配送区域**(钉在地上) | 地图上拖选或搜地名,另有「远近皆可 / 5 公里以上 / 5 公里以下」档位 |

蜂鸟的「常驻区域」是**地理围栏**:骑手在地图上圈一块或搜一个地名,
选定之后就钉在那里,人走出去了池子还是那块地方的。

我们的是**跟着人走的圆**。两种语义的差别:

- 跟着人走:「离我 3 公里内的单」—— 适合满城跑的全职骑手;
- 钉在地上:「XX 片区内的单」—— 适合"我今天只在这个片区"的人。

**我们暂时不加地理围栏。** 不是做不了,是我们已经用另一个东西覆盖了
后一种需求 —— `grab_same_way_only`(只看顺路),而它的判据是**绕路增量**
不是两点距离(`riders.py:986` 附近)。注释里写了旧口径的实测反例:
送达点相邻但取餐点在反方向 3km 的单也被判顺路,骑手照着接会多跑近 6 公里。

对兼职骑手来说,「下班这条路上」比「某个片区内」更准 ——
片区是他为了表达"顺路"而不得不画的一个近似。

真要加围栏,判据是:**有骑手明确说"我只在这个商圈跑,不是顺路问题"**。
在那之前不加。

## 三、几处我们已经比它们细的地方

不是自夸,是记下来免得以后被"对齐友商"给改掉。

**1. 距离用真实骑行路径,不用直线。**
`riders.py` 走 `bicycling_m()`,拿不到才回退直线 ×1.2 **并标明来源**
(`distance_source` 会下发给客户端)。注释里有实测:成都两点直线 1467m、
骑行 1745m,差 19%。所以"3 公里内"是骑得到的 3 公里。

直线会系统性低估,而低估的后果落在骑手身上 —— 他按 3 公里接的单,
实际要骑 3.6 公里。

**2. 被自己偏好挡掉了几单,要摆出来。**
`filtered_by_prefs`。悄悄过滤的表现是"今天怎么一直没单",而骑手不会
想到去翻两个月前设的一个开关,他只会觉得平台不给他派单。

没查到美团或蜂鸟有对应的东西。

**3. 排序算法对骑手公开。**
抢单页旁边就是「抢单怎么排的」入口,权重从 `dispatch.py` 的常量读,
**不另抄一份**。美团 2021 年公开过订单分配算法规则,但那是对公众的
一次性说明,不是骑手端的常驻入口。

## 四、这次修的 bug

**定位取不到时,接单半径和只看顺路会静默失效。**

两个偏好都在 `if rider_pos:` 分支里算(`riders.py` ~919),位置没上报
或 Redis 过期(5 分钟)时整段跳过 —— 而骑手界面上 chip 还选着「3km」,
实际收到的是全城的单。

这比「挡掉了 N 单你不知道」更坏:那个是**少看到单**,这个是**接错单** ——
他以为自己只看 3 公里内,接了才发现要骑十公里。

修法:服务端多回 `has_location` 和 `stale_prefs`(哪些偏好因为没定位
而没生效),骑手端照实显示一条红字:

> 定位没拿到,「接单半径」现在没生效 —— 下面是全部的单,不是筛过的

纯函数抽成 `stale_location_prefs()` 并加了 7 条单测
(`server/tests/unit/test_stale_prefs.py`),包括「没设过的偏好不报」
和「`grab_radius_km=0` 当没设」两个边界 —— 报一个骑手从没设过的东西,
他会更懵。

老客户端不传 `with_meta` 时仍返回裸数组,老服务端不返回新字段时客户端
按"有定位、没失效"处理,两头都不会因为升级出问题。
