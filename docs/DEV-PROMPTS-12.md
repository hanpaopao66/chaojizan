```

- 没有任何错误追踪,线上报错只能翻 docker logs,而日志还没轮转上限。

   不强依赖。没有 DSN 时第 2 条已经能兜住。

验收:e2e 验证跨域来源被拒、白名单来源放行;人为造一个 500 能在日志里
看到 traceback 且**看不到任何手机号/地址**。
```

**踩到的一个自己的坑**:第一版分类脚本用了 `timeout` 命令 —— macOS 上没有,
67 个用例全部记成"失败"且错误信息为空。差点把这个结论当真报出去。

### 真正的根因:用例是按「小数据集」写的,库长大后集体失效

把 67 个用例逐个纳管的过程中,失败几乎全部收敛到**同一个成因**:

> **接口有条数上限,而用例假设"我要的东西一定在返回里"。**

涉及的上限:`/merchants` LIMIT 50、`/admin/merchants` 分页、
`/merchants/me/finance/orders` LIMIT 500、`/stays/hotels` LIMIT 200。
演示库从几十条长到 200 家商家 / 单日 545 条入账之后,这些假设集体不成立。

对应的四种修法(按可靠性排序):
1. **能直查就别扫列表** —— `demo_shop()` 直接取详情;
2. **确实要验列表** —— 用目标对象自身的坐标查询,让它必在首位;
3. **验的是筛选** —— 断言"筛出来的每一条都符合条件",而不是"某条一定在里面";
4. **翻页求和** —— 对账类必须翻完,只取第一页的合计天生对不上。

**这一轮里唯一一个真实的产品缺陷也是这么冒出来的**:
`/merchants/me/finance/orders` 写死 `LIMIT 500` 且不分页,
演示店单日入账 545 条时,**明细合计 ≠ 日汇总**(775590 vs 837340)。
对一个把「每一单的账都可查」写在首页的平台,这不是测试问题。
已按 `/orders` 的先例改成游标分页(`before`/`limit`),客户端同步支持翻页。

另有一条老写法漏网:`e2e_risk` 仍在用 `30.6650 + (ts % 20) * 1.3e-3` 算坐标
—— 只有 20 个点、每 20 秒循环,一天里反复跑必然和别的用例撞进同一个 65m
风控格子,表现为"前 3 单不该标记"随机失败。`unique_spot()` 当初就是为替掉
这个写法而做的,唯独这条漏了。

**给后来者的判断**:在被几百轮测试跑脏的共享开发库上追这类失败,
边际收益递减很快。真正的解是 CI 跑在干净库上(本轮已建),
本地库定期重置(见 [[superz-e2e-practices]] 的清库流程)。
