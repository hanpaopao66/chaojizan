### 127. 生产运维基线(P0 + P1 里同类的几条)

```
把"脚本写好了但没挂上去"这件事收掉。全是配置与运维层改动,不碰业务代码。

说明:提示里把 P1 的监控/演练/日志轮转也并进来了 —— 它们和 P0 是同一类
(挂 cron、改配置),同一次上机做完,分两次反而更容易漏。

现状(实地核查):
- deploy/backup.sh 写好了,注释里连 crontab 那行都给了,但没挂;
  部署机上 0 个 .dump 文件,OFFSITE_DEST 未配;
- deploy/healthcheck-alert.sh 同样存在、同样没挂;
- deploy/restore-drill.sh 存在,从没跑过(本来也没备份可演);
- .env.prod 里 MOCK_PAY_ENABLED 未配置,代码默认 True;
- 演示账号 13800000001/13800000002 用 123456 能登进生产。

要做的:
1. **数据库备份**:backup.sh 挂进 crontab(避开出餐高峰,与 MinIO 备份错开),
   配 OFFSITE_DEST。**没有异地目标的备份只算半个备份** —— 脚本自己的注释
   就是这么写的,照做。
2. **立刻跑一次备份 + 一次 restore-drill**,把"备份能恢复"这件事验过再说下一步。
   没演练过恢复的备份等于没有备份。
3. **MOCK_PAY_ENABLED=false**,并**用不存在的单号探测确认返回 403 而不是 404**
   (404 说明守卫没生效,只是订单没找到 —— 这正是我发现问题的方法)。
4. **演示账号**:生产上的 13800000001/13800000002 要么改成强口令,要么禁用。
   注意它们是 seed 里的固定账号,后续跑 seed 会重新写回 ——
   改口令治标,得同时让 seed 在生产环境不写弱口令账号。
5. **healthcheck-alert.sh 挂进 crontab**,并**人为制造一次失败验证它真的会响** ——
   一个从没告警过的告警系统,和没有告警没区别。
6. **Docker 日志轮转**:compose 里给各服务加 log-opts(max-size/max-file)。
   磁盘现在剩 133G 够用,但日志只增不减。

验收:
- 部署机上有 .dump 文件且 restore-drill 通过;
- /orders/X/pay/mock 对不存在的单号返回 **403**;
- 演示账号用 123456 登录被拒;
- 告警链路做过一次真实触发;
- docker inspect 能看到日志上限。
```

### 128. 回归纳管 + CI

```
让"跑没跑测试"不再取决于人的记性。

现状:tests/ 下 117 个 e2e,make test 只跑 50 个,剩 67 个平时不跑 ——
不跑的测试会烂,烂了之后没人敢再跑,最后等于删掉。

要做的:
1. **逐个跑那 67 个未纳入的用例**,分三类处置:
   - 能过的 → 纳入 make test;
   - 需要特殊环境的(如 e2e_privacy_phone_strict 要对着 STRICT=true 的实例跑)
     → 单独列一个 make 目标,并在 Makefile 里写清前置条件;
   - 已经烂掉的 → **修好或删掉,不许留着**。留一个永远红的用例,
     等于给后面所有人一个"红了也没关系"的许可。
2. **GitHub Actions**:起 postgres+postgis / redis / minio 三个 service,
   跑 alembic upgrade → seed → make test。
   注意本地跑全量的三个前置条件(见 docs 的 e2e 跑法记录):
   AUTO_FLOW_ENABLED=false、SMS 日配额、库存 —— CI 里是干净库,
   但 auto_flow 那条必须照样关掉。
3. CI 里同时跑 flutter analyze(三端 + shared)与 security_scan.sh。

验收:make test 覆盖数从 50 提到尽可能高,且**每一个没纳入的都有一行说明为什么**;
CI 在 PR 上能跑绿。
```

### 129. 服务端单元测试(从最该有的地方开始)

```
现状:服务端 0 个单元测试,全靠 e2e。e2e 慢、依赖真实服务、失败时定位成本高,
不适合覆盖边界条件。

不追求覆盖率数字,只挑**算错了会直接变成钱的地方**,且优先纯函数:
- services/pricing.py:配送费分段计价、夜间/天气加价、距离边界(4km 那条线);
- 阶梯佣金:档位边界、"不得高于 5% 承诺上限"的钳制、"手工调低的店绝不上调";
- services/risk.py:addr_freq 的 ~65m 包围盒判定(这条曾让 e2e 时好时坏);
- 时间窗工具:in_hhmm_range 跨零点、宵禁窗口;
- 账本哈希链:canonical 序列化的稳定性(同样输入必须同样输出)。

技术要点:用 pytest,纯函数直接调,不起服务、不连库。
放 server/tests/unit/ 与 e2e 分开,make 目标也分开 ——
单测要能在 1 秒内跑完,慢了就没人跑。

验收:make unit 全绿且 < 5 秒;上面五类边界各有用例;纳入 CI。
```

### 130. CORS 收紧 + 线上错误可见

```
现状:
- main.py 里 allow_origins=["*"],注释自己写着"上线前收紧到实际域名";
- 没有任何错误追踪,线上报错只能翻 docker logs,而日志还没轮转上限。

要做的:
1. **CORS 白名单**:允许的来源做成配置(默认生产域名 + 本地开发),
   不再 *。注意别把 App 端打挂 —— 原生 App 不发 Origin 头,不受 CORS 约束,
   受影响的只有官网和管理后台这类浏览器页面。
2. **未捕获异常统一留痕**:加一个中间件,把 5xx 的请求方法/路径/traceback
   写进结构化日志(不带请求体 —— 里面有手机号和地址)。
   **绝不把用户数据写进日志**:那等于给自己造了第二个数据泄露面。
3. Sentry 一类可选接入:照本项目既有的降级风格(未配 DSN 就整体静默),
   不强依赖。没有 DSN 时第 2 条已经能兜住。

验收:e2e 验证跨域来源被拒、白名单来源放行;人为造一个 500 能在日志里
看到 traceback 且**看不到任何手机号/地址**。
```

### 131. 外部依赖体检(P3 能做的部分)

```
P3 那六项(JPush / 高德 / 阿里隐私号 / 身份证核验 / 骑手保险 / 灵活用工)
**全部卡在外部账号申请**,不是写代码能解决的。代码早就写好且能优雅降级 ——
问题是"降级了但没人知道"。

最典型的:昨天刚做的骑手新单推送,在生产上一条都发不出去,
因为 JPUSH_APP_KEY 没配。功能验收全绿、线上完全无效。

要做的:**把降级状态变成可见的**,而不是继续假装功能存在。
1. 新增 `GET /admin/readiness`(仅管理员):逐项列出外部依赖的配置状态、
   未配置时的**实际降级行为**、以及**影响谁**。例如:
   - jpush:未配置 → 所有推送静默跳过 → 骑手收不到新单提醒、用户收不到订单状态
   - privacy_phone:未配置且非严格模式 → **商家和骑手看到用户真实手机号**
   - idcheck:未配置 → 实名只校验格式与校验位,不核验真伪
   - insurance:未配置 → 骑手意外险只登记不投保
   ...
2. 配一个运维脚本 deploy/readiness.sh 直接打印这张表,发版后跑一眼。
3. **不要**因为"没接就先关掉功能"而悄悄改行为 —— 现在的降级设计是对的,
   缺的只是可见性。

**一个需要你拍板、我不替你决定的**:
PRIVACY_PHONE_STRICT 现在是 false,即未接隐私号时**向商家/骑手下发用户真号**。
开成 true 会打码并隐藏拨打按钮 —— 隐私更好,但骑手找不到门时**没法联系用户**,
可能直接变成配送失败。在 AXB 号池接通前,这是"隐私"与"送得到"的取舍,
属于业务决策不是技术选型。readiness 里要把这个取舍明确写出来。

验收:/admin/readiness 逐项如实反映 .env 配置状态;
非管理员访问被拒;readiness.sh 在部署机上能跑。
```

## 明确做不了的

- **iOS 发版**:需要 Apple 开发者账号与签名证书,且发版脚本只出 Android arm64。
- **微信支付**:卡在商户号开通 APP 支付,流程问题非技术问题。
- **P3 的六项外部服务**:需要你去申请账号/Key。
- **多机高可用**:当前是单机 + frpc 内网穿透,机器/宽带/隧道任一挂掉全站不可用。
  这个阶段可接受,但要知道在赌什么。
