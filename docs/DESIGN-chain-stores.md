# 连锁店群支持 · 设计文档

> 状态:**方案二已全部落地**。拍板结论:做连锁;证照按门店独立不复用;
> 不做品牌级钱包。
>
> 落地清单:
> - 后端:`services/staff.py`(权限解析唯一入口)、`routers/brands.py`
>   (品牌/门店/成员/菜单下发)、`X-Shop-Id` 中间件(`main.py`)
> - 前端:merchant-web 顶栏切店 + 「连锁店群」页;
>   商家 App 顶栏切店 + 「连锁店群」页(看数 + 开新店)
> - 回归:`server/tests/e2e_chain_stores.py`(已挂进 `make test`)
>
> ## 实施中发现、并已修掉的三个坑
>
> 都是同一个根因的不同长相:**`db.scalar(select(...owner_id == 我))`
> 不带 ORDER BY**。单店时永远只有一个候选,看不出问题;名下有两家店起,
> 返回哪一家由数据库决定 —— 而且三处的表现都是"操作成功、屏幕正常、
> 结果是错的",商家自己发现不了。
>
> 1. **改到别家的菜单**:37 处端点直查 owner_id,切了门店照样改上一家的
>    价格和库存。已全部收敛到 `resolve_shop`,并让它在"名下不止一家却
>    没指定是哪家"时直接拒绝,而不是猜。
> 2. **听单通道随机连不上**(`ws.py`):三家店里只有随机命中的那家能连,
>    另外两家听不到新单 —— 商家只会以为今天没生意。
> 3. **区域经理能把整店的钱提到自己卡上**:钱包余额按 `merchant_id`
>    算(整店营收),已提现却按 `user_id` 减。两个 id 不是同一个人时
>    同时出两个洞:经理提走全额,且店主已提走的部分不计入经理的额度,
>    两人各提一次全额。已引入 `money_shop()` —— 资金路径只认
>    店铺登记的 owner 本人,品牌层一律不放行。

## 1. 为什么现在要谈这件事

商家端做到今天,单店老板要的功能基本齐了(接单/菜单/营销/对账/评价/看板)。
下一个天花板是**连锁**:两家以上门店的老板,今天在超级赞上只能:

- 用两个手机号注册两个商家账号,App 里来回切登录;
- 每家店的菜单、活动、营业时间分别手工维护一遍;
- 想看"这个月两家店一共赚了多少",只能自己拿计算器加。

美团/淘宝闪购都有"总部视角":一个账号看所有门店报表、统一改菜单、
统一投活动。连锁商家谈入驻时,这是必问项 —— 没有它,
稍成规模的商家从谈判第一轮就走不下去。

## 2. 现状约束盘点(为什么不能"加个字段就完事")

一号一店的假设**遍布全库**,不是某一处判断:

| 位置 | 现状 | 数量 |
|---|---|---|
| `Merchant.owner_id ==` 直查 | 拿到"这个人的店",隐含只有一家 | 38 处 |
| `_my_shop_or_404(db, user)` | 同上,商家端点的标准开头 | 29 处 |
| `operable_shop(db, user)` | 店主/店员二选一,仍返回**单个**店 | 16 处 |
| `POST /merchants` | 显式 409「你已提交过申请,一个账号一家店」 | merchants.py:387 |
| 客户端 | `ShopGate` 拿 `myShop()` 单个对象决定进哪个工作台 | 三端 |

`services/staff.py` 的注释写得很清楚:敏感端点靠 `owner_id` 天然挡住店员。
一旦一个账号能有多家店,**这条天然防线就失效了** ——
所有 `owner_id ==` 的地方都要改成"这个人 + 指定这家店"的二元判定,
漏一处就是越权(A 店店长能改 B 店的价)。

## 3. 三个方案

### 方案一:账号切换(最小改动)

一个手机号下允许注册多个商家账号,登录后先选门店,选完之后
整个 App 的行为与今天完全一致。

- 改动:登录态加 `active_merchant_id`,`_my_shop_or_404` 读它;
- 优点:改动集中,风险低,一周内可交付;
- 缺点:**没有总部视角**。跨店报表、统一改菜单都做不了,
  只是把"退出重登"换成"下拉切换"。

### 方案二:引入 Brand(品牌)层 —— 推荐

新增 `brands` 表与 `brand_members`(角色:owner/manager/staff,
manager 可限定门店范围)。`Merchant.brand_id` 可空(单店商家不受影响)。

- 单店商家:`brand_id` 为空,所有现有逻辑走原路径,**零感知**;
- 连锁商家:一个品牌挂多家店,总部视角是新增端点
  (`/brands/me/overview`、`/brands/me/dishes/sync`),不改老端点语义;
- 权限:`operable_shop` 升级为 `resolve_shop(db, user, merchant_id)` ——
  显式传门店 id,服务端校验这个人对这家店有没有权限。
  这一步是**必须逐个改 83 处调用点**的硬工作量,没有捷径。

### 方案三:组织/多租户模型(过度设计)

完整的 org → team → member → resource 权限体系。
超出当前需要,先不做;方案二的 brand 层留了升级空间。

## 4. 方案二的实施路径(建议分四步,每步可独立上线)

1. **地基**:brands / brand_members 表 + `Merchant.brand_id`;
   `resolve_shop(user, merchant_id)` 落地,83 处调用点逐个迁移
   (老行为保持:不传 merchant_id 时退化为"我的唯一一家店");
2. **切换**:客户端门店选择器(ShopGate 前置一层),三端登录后选店;
3. **总部视角**:跨店汇总报表(单量/营业额/评分/超时率)、
   门店列表、按店钻取;
4. **统一运营**:菜单模板下发(选门店批量应用)、活动批量投放、
   新开门店一键复制配置。

## 5. 需要拍板的问题

1. **优先级**:连锁支持 vs 其他候选(拼团/预约到店/供应链)。
   连锁的收益是"能签下更大的商家",但当前平台还在开城早期,
   连锁商家未必是第一批客户 —— 这是个商业判断,不是技术判断。
2. **权限粒度**:manager 是"管指定几家店"还是"管全品牌"?
   前者要 `brand_member_shops` 关联表,后者一个 role 字段就够。
3. **对账口径**:品牌层报表是"各店简单相加",还是要引入
   品牌级钱包(总部统一提现)?后者牵动资金链路,复杂度陡增,
   且与"每一笔分账可查可申诉"的承诺要重新对齐。
4. **审核口径**:同一品牌新开门店,证照是否可复用总部的?
   (法规上食品经营许可证是**按门店**核发的,倾向于每店独立审核。)

## 6. 明确不做的

- 不做加盟商分润/供应链结算 —— 那是 ERP 的活;
- 不做品牌级竞价推广 —— 与"没有竞价排名"的承诺冲突;
- 不做总部强制改价 —— 门店经营自主权不该被平台的产品设计架空。
