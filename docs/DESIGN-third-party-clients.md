# 设计:第三方客户端怎么接入

> 状态:**方案,待拍板**(2026-09-15)。只定结构,不写代码 —— 照 `DESIGN-errand.md` 的先例。
>
> 起因:有人问「为什么 Turrit 这类 App 能给 Telegram 套个壳」,接着要一份「别人也能给超级赞做客户端」的方案。
>
> 和旧口径的关系:[API.md](API.md) 写着「现在**不开**第三方用户端」,
> [DEV-PROMPTS-38.md](DEV-PROMPTS-38.md) 第一条拍板给的理由是钓鱼客户端能拿走收货地址和手机号,
> 前提是「**等授权体系立住了再说**」。这份文档就是那套授权体系。拍板之前,旧口径照旧有效。

## 一、先看现状:服务端今天分不出谁是谁

| # | 事实 | 在哪 |
|---|---|---|
| 1 | 登录令牌只有 `sub` / `role` / `exp`,扫码登录的多一个 `ld`(设备行号)。**没有任何字段说明是哪个 App 签的**。30 天有效,`/auth/refresh` 能一直续 | `security.create_token`、`config.jwt_expire_minutes` |
| 2 | 手机 App 的登录**不落库**:列不出来,也没法单独踢。能移除的只有扫码登录的网页版和电脑版 | `models.LoginDevice`、`routers/qr_login.py` 的 `/login-devices` |
| 3 | 客户端只报 `X-App-Build`,服务端只记日志、不拦;`min_build` 没有地方强制 | `main.ObserveAppBuildMiddleware` |
| 4 | 老的两条实时通道自己解令牌,不认「设备已移除」「账号已注销」 | `ws.order_ws`、`ws.merchant_ws`(已单独立项) |
| 5 | 按 IP 的限流拿不到真实来源地址,全站看起来是同一个 IP | `ratelimit.client_ip` |
| 6 | 好几条规矩只有官方客户端在守 | 第四节 |

**结论:代码开源(AGPL),接口是普通 HTTP。今天就有人能照着编一个客户端,用手机号 + 验证码登录,服务端完全分不出来。**
所以 1、2、4 和第四节的前几条,开不开放第三方都得补 —— 它们本来就是缺口。

## 二、登录:验证码不经过第三方的手

Telegram 的第三方客户端自己收手机号和验证码。拿到验证码就是拿到账号,用户在对方的界面上登录,也分不出真假。
这正是钓鱼的口子:2023 年卡巴斯基报告过 Google Play 上一批中文版「纸飞机」改版,以「比别的客户端快」为卖点,
把聊天记录和联系人全部发回自己的服务器([Securelist](https://securelist.com/trojanized-telegram-mod-attacking-chinese-users/110482/))。

### ❌ 方案 A:照搬 Telegram,第三方自己收验证码,登录时带上 client_id

最省事,也最像 Turrit。但验证码和令牌全在对方手里 —— 就是 API.md 当初拒掉的那种钓鱼客户端,多了个登记号而已。

### ✅ 方案 B:登录由我们来批,第三方只拿到批下来的令牌

第三方客户端**永远拿不到验证码和密码**。批准只在我们的界面上发生:

1. **在官方 App 里确认**(第一步就做,复用扫码登录):
   - 不在同一台设备:第三方客户端显示二维码,官方 App 扫;
   - 在同一台手机:第三方客户端拉起官方 App,直接弹确认页,点完切回去。
2. **官网授权页**(第二步做,给没装官方 App 的人):第三方客户端用**系统浏览器**打开 `chaojizan.cc` 上的授权页,
   在我们的页面上短信登录、确认,再跳回客户端(原生 App 的标准做法:OAuth 2.0 授权码 + PKCE)。
   不许用 App 内置网页 —— 内置网页里的内容,宿主 App 全都读得到。这条技术上拦不死,靠审核和条款。

确认页上的名字、开发者、权限**全部从登记表读**,不用客户端自报的
(现在扫码登录的设备名是客户端自己报的,`qr_login.describe_device` 为此只从固定词表里拼):

```
「某某客户端」想登录你的超级赞账号
第三方客户端,不是超级赞官方做的 · 开发者:某某 · 源码:……
它能:收发聊天、看视频、下单(付款仍在官方 App)
它不能:付款、实名认证、注销、换绑手机、管理登录设备
            [ 拒绝 ]   [ 同意并登录 ]
```

这张页同时是个人信息保护法第 23 条要的「单独同意」:把个人信息提供给别的处理者,
要告诉用户接收方是谁、怎么联系、为什么拿、拿哪些,并单独征得同意。(口径待法务确认。)

## 三、结构

### 1. 登记表 `client_apps`

挂在开发者名下(`models.Developer`,小程序和机器人用的同一个)。

| 字段 | 说明 |
|---|---|
| `client_id` | 公开编号,写在客户端里。**不是密钥** —— 装在别人手机上的包里的任何东西都能被拆出来,Telegram 的 api_hash 也一样。它管的是「认得出、掐得断」,不是「证明身份」 |
| 名称、简介、图标、平台 | 名称套用小程序的禁用词:超级赞、官方、客服、支付、钱包、SuperZ(`dev_miniapps.py`) |
| 主页、隐私政策、联系方式 | 确认页和官网列表要摆出来 |
| 源码地址 | 见第七节第 3 条 |
| 申请的权限块 | 见本节第 3 条 |
| 盈利方式 | 有广告必须写 |
| 跳回地址 | 官网授权页用 |
| 状态 | 测试中 → 审核中 → 已上架 / 已驳回;已上架 ⇄ 已暂停;任何状态 → 已停用 |

测试中不用审核:只有开发者本人和最多 20 个测试号能登录(沿用小程序的测试号上限)。

### 2. 会话:第三方的每次登录都是 `login_devices` 的一行

- 表里加 `client_app_id`、`scopes`。令牌照旧带 `ld`,`get_current_user` 本来每次都回库查这一行(`login_device_alive`),
  顺手查客户端的状态和权限 —— **不新开入口**。助手令牌和扫码会话都收口在这个函数里,理由写在它的注释里:
  逐个路由加限制,漏一个就是一条没人看守的路;
- 用户在「已登录的设备」里看得到「某某客户端(第三方)· 安卓 · 3 分钟前」,点移除立刻退出 —— 网页版、电脑版现在就是这么做的;
- 客户端被停用:名下所有会话下一次请求 401,错误码单独一个(比如 `client_disabled`),好让它跟用户说清楚;
- 第三方会话**不能批准别的设备登录,也不能管理登录设备** —— 和网页版、电脑版一个待遇(`qr_login._phone_app`)。
  不然一个坏客户端能把官方 App 踢下线,再给自己批新设备;
- 调用量按客户端按天计数,不逐条记。助手令牌那样一条条进 `api_calls`,放到一个完整客户端上量太大。

### 3. 权限:白名单,按块勾

照助手令牌的做法 —— **全匹配的白名单,新接口默认不开放给第三方,要开是一个显式动作**
(`security.py` 里 `AGENT_*` 那段注释讲了为什么不用黑名单:第一版用前缀匹配,单测当场抓出商家的财务接口被放行)。

| 块 | 包括 |
|---|---|
| 聊天 | 私聊、群、频道、收发消息;通话(开关开着时) |
| 机器人 | 和机器人对话、菜单、回调 |
| 视频 | 看、点赞、评论;投稿单独一块 |
| 外卖和团购 | 找店、下单、看订单和进度 —— **不含付款** |
| 我的资料 | 昵称头像、地址簿 |
| 小程序 | **第一步不给**,见第四节 |

**永远不给第三方**,在第三方客户端里点到了就跳官方 App 或官网去做:

- 付款、退款;
- 实名认证 —— 身份证号和照片不能经过第三方的代码;
- 注销、换绑手机、管理登录设备、批准新设备;
- 签发 AI 助手令牌;
- 开发者后台、运营后台、商家端、骑手端的一切。

### 4. 推送

第一步不给。极光现在全站一个 app key,按 `u{用户号}` 这个别名推(`services/push.py`),第三方客户端收不到;
硬给就是推到官方 App 上。第一步第三方客户端在前台靠实时通道收消息;以后要做,就让开发者在后台填他自己的推送密钥,我们替他推。

### 5. 限流和成本

- 按客户端的总量限:每分钟发起多少次登录、同时多少个会话。按 IP 的那套在现在的入口下靠不住;
- 短信只在官网授权页上发,走现有的按手机号限额和滑块。第三方碰不到发短信的接口,也就刷不了我们的短信费。

### 6. 开发者后台、审核、官网列表

- 开发者后台加「客户端」一栏,登记、改资料、看调用量;
- 审核沿用小程序那一套:先进先出的队列、逐项清单、驳回要理由码、申诉换一个人审、每个决定留痕
  (`admin_miniapps.py`、`miniapp_publish.py`);
- 审核清单第一版:名字和图标不像官方;写明「非官方,基于超级赞开放接口」;隐私政策打得开;
  申请的权限说得出用处;授权页用系统浏览器打开;消息按纯文本显示(防脚本注入现在靠官方客户端这么做,
  见 [SECURITY-AUDIT-40.md](SECURITY-AUDIT-40.md));源码打得开,抽查它和上架包对不对得上;
- 官网公开一页「第三方客户端」:名字、开发者、权限、源码、状态。被停用的也留着,写明原因。

### 7. 使用条款(对着 Telegram 那几条改)

- 不许冒充官方:名字里不许有「超级赞」,不许用官方图标,介绍里写明非官方;
- 不许做「幽灵模式」(看了不回已读、不显示正在输入),不许留存别人已撤回的消息,不许背着用户替他操作;
- 消息按纯文本显示;
- 不许把付费位置当成平台排序给用户看 —— 平台承诺「不做竞价排名」,第三方客户端不能在自己的界面里把这句话变成假的;
  有广告就在应用介绍里写明;
- 用户数据不许传出设备(翻译这类非传不可的,隐私政策写明、单独征得同意),不许拿来训练模型;
- 违规限期 10 天改,改不了就停用;安全问题当场停。

### 8. 法律文本

- 用户协议现在写账号「仅限本人使用,不得转让、出借」,要补一条:可以用官网列出的第三方客户端,第三方客户端由它的开发者负责;
- 隐私政策补一节:第三方客户端是另一个个人信息处理者,授权时单独同意;
- [COMPLIANCE-40.md](COMPLIANCE-40.md) 新增一条问法务:开放第三方客户端以后,我们作为即时通信服务提供方的义务变不变;
  第三方客户端在国内上架要自己办 App 备案(我们自己的 App 备案也还没办,见 [ROADMAP.md](ROADMAP.md))。

## 四、只有官方客户端在守的规矩

一个改过的客户端能绕过去的,都在这一节。

### 已经堵上 / 已立项(今天用 curl 就能做,和第三方无关)

| 问题 | 处理 |
|---|---|
| 顾客调 `/orders/{no}/transition` 传 `paid`,不付钱单子就成了已支付;商家照常出餐,完成时还给商家、骑手记账 | 已修(`b61ff88`):状态机只留 system,单测 + e2e 钉住 |
| 加急小费在生产上「视为已收」,平台替顾客给骑手垫最多 100 元,取消时还按 total 退 | 已修(`b61ff88`):和模拟支付同一道闸门,生产回 503,新版 App 关着时不摆按钮 |
| 老实时通道不认吊销 | 已立项 |

生产上查过,这两处都没有被用过的痕迹。另有一处已知的:跑腿「按小票补收」只记账不收钱,代码里写明了上线前要接微信补收款,有额度上限。

### 开放前要搬到服务端的

| 规矩 | 现在 | 要改成 |
|---|---|---|
| 用户协议和隐私政策的同意 | 只记在手机本地(`privacy_gate.dart`),登录请求里没有同意字段,服务端不记也不拦 | 服务端记同意的版本号;没同意当前版本的会话只给看协议、点同意的接口。**这条不开放第三方也该做** —— 出了纠纷,现在拿不出用户什么时候同意了哪一版 |
| 小程序拿昵称头像的授权 | 弹窗只在官方 App 里,服务端只要带着用户令牌就记授权 | 第一步第三方会话调不了这个接口;要开就把确认挪到服务端 |
| 小程序的能力开关、可跳转的域名 | 只在官方 App 的桥里执行 | 第一步不给第三方开小程序 |
| 聊天总开关 | 只挡 `/chat/v1`,实时网关和 `/social/v1` 不看这个开关 | 服务端补齐 |

### 服务端管不了、只能写进条款的

- 已读:什么时候报已读由客户端决定;
- 「受保护」会话:转发和收藏服务端拦了,复制和保存媒体只在官方 App 里藏起来 —— 媒体要下载下来才能显示,就拦不住存;
- 视频的观看时长由客户端报(按人按天去重在服务端);
- 截图。

### 本来就在服务端的(不用动)

正在输入(成员校验 + 频率)、48 小时内改消息、双向删除、隐私设置、群和频道的权限 / 慢速 / 封禁、视频审核、
功能开关(视频、投稿、机器人、通话都回 503)、付款金额和微信回调验签、商家自动接单和忙碌模式、实名的几道闸、
小程序身份(签名的 initData 和按应用分开的 open_id)。

### 为什么骑手端不开

抢单先到先得。服务端在抢单那一下只查实名、在途单数、有没有被别人抢走,**不查频率、冷却、在不在线、离得远不远**;
位置只校验了坐标范围,「我到了」的地理围栏只在客户端传了坐标时才判,取餐尾号不传就不核。
放开第三方骑手端,等于给抢单外挂发执照。

反过来说,这些缺口今天就在 —— 官方骑手端的接口也是公开的,有人写脚本抢单,服务端现在分不出来。
这件事和第三方方案无关,应当单独立项。

## 五、分几步做

**第 0 步:不开放也该做**

- 手机 App 的登录也落一行会话,「已登录的设备」列出全部、都能踢;新设备登录时给其他会话发一条提醒;
- 官方客户端带上自己的 client_id(预置几个官方编号),服务端先只统计 —— 和 X-App-Build 一样,先看见;
- 服务端记录协议同意;
- 老实时通道统一校验(已立项);聊天总开关补齐。

**第 1 步:只对开发者自己和测试号**

- 登记表、官方 App 里确认登录(扫码 + 同机拉起)、权限白名单、后台暂停 / 停用、按客户端计数和限流;
- 条款草稿公开,听开发者意见。

**第 2 步:公开**

- 审核、官网列表、官网授权页;法律文本改完;
- 等大部分人都更新到带 client_id 的官方 App,**不带 client_id 的登录不再接受**。
  在这之前,不带编号的请求只能当「老版官方 App」放行 —— 这就是第六节第 1 条那个口子。

**第 3 步:以后再说**

- 开发者自带推送密钥;
- 第三方客户端开小程序。

## 六、坦白:这套挡不住什么

1. **挡不住存心冒充官方 App 的人。** 官方 App 的代码是公开的,谁都能编一个一模一样的,直接用手机号验证码登录;
   client_id 写在包里,也能被抄走。这件事今天就是这样,开不开放都一样。能做的只有第 0 步:每个会话看得见、踢得掉,新登录有提醒。
2. **挡不住客户端这边的约定。** 已读、撤回、截图,服务端管不住,只能写进条款、发现就停。Telegram 也一样。
3. **审核看不全。** 源码和上架包对不对得上只能抽查,做不到逐字节复现。
4. **用户会找错人。** 第三方客户端出的问题会算到我们头上。「已登录的设备」和确认页上要写清「第三方,问题找开发者」。
5. **要人手。** 审核、处理举报、盯异常调用。

## 七、要拍板的

1. **开哪几端**:只开用户端(推荐)。商家端已经有商家 API Key 给收银和 ERP 用;骑手端的理由见第四节。
2. **登录**:验证码不经过第三方,由我们批(推荐)/ 照 Telegram 让第三方自己收验证码。
3. **开发者门槛**:
   - 公开上架前要不要实名(个人或企业)。注意:个人实名核验服务在生产上没配,
     现在个人开发者过不了实名(`idcheck.verify_two_elements`),只有企业走人工审核能过;
   - 要不要求公开源码(推荐要:我们的代码是 AGPL,改我们代码做的客户端本来就得开源;
     要求所有上架的都开源,审核才看得了。代价是 Turrit 那种闭源的就不收)。
4. **广告**:允许但必须写明(推荐)/ 不许。
5. **名字**:依赖商标口径。[DEV-PROMPTS-30.md](DEV-PROMPTS-30.md) 里倾向「代码随便用,牌子和域名不给用」,还没落进 README。
