# 开发提示词 #147–#149:骑手端功能补齐(对照竞品拆解)

参照物:蜂鸟众包(饿了么)与美团骑手端的"我的"首页截图。

## 先说结论:空白不在能力,在入口

逐项比对后,**服务端能力其实很全** —— 24 个骑手端点,客户端 API 方法也齐
(`riderWorklog` / `myAppeals` / `submitAppeal` / `riderDiscipline` 全都有实现)。

真正的问题是**信息架构**:

| 能力 | 现在藏在哪 | 骑手怎么找到它 |
|---|---|---|
| 工时统计 | 钱包页深处 | 想不到去钱包里看工时 |
| 违规申诉 | 「异常上报」页 | 要先想到点"异常上报" |
| 转单纪律 | 入驻页 | 入驻完就再也不会去了 |
| 意外保障/装备/紧急联系人 | 钱包页「保障与规则」 | 同上 |

**两家竞品都有的那一层「我的」中心,我们没有。** 骑手打开 App 只有
抢单/配送/钱包三个 tab,没有一个地方能回答"我这个人在这个平台上是什么状态"。

## 竞品功能拆解:哪些抄、哪些**坚决不抄**

### ❌ 坚决不抄:评分与段位体系

截图里最显眼的东西:**服务分 70.0 / 安全分 70 / 派单分 200 / 一星青铜 /
潜力青铜 / 冲段位争荣誉**。

**这些恰恰是「算法困住人」的核心机制**,而我们在 #144 里已经把反对它写进了
公开承诺(/transparency/dispatch 的 never_do):

> 不按骑手评分或等级差别对待 —— 同一批单,所有在线骑手看到的口径一致

抄了就是**当众违背自己刚公开的承诺**。这条没有讨论余地。

段位/评分的作用机制是:把骑手的收入与一个平台单方面控制的分数绑定,
分数又由"接单率/超时率/差评率"构成 —— 于是骑手不敢拒单、不敢休息、
不敢跟顾客理论。**那不是激励,是绳索。**

### ❌ 不抄:烧钱玩法

千万奖金、抽电动车、717 骑士节、签到抽奖、商城积分。
平台无补贴预算(这是既定约束),而且这类玩法的钱最终来自抽成 ——
羊毛出在羊身上,与"低抽成"的立场冲突。

### ❌ 暂不抄:进阶跑单体系

乐跑/畅跑/优选/驻线/时段任务……这些本质是**用排他性换稳定性**:
承诺跑够多少单给多少保底,代价是不能挑单、不能随时下线。

它对骑手不全是坏事(收入更稳),但**前提是平台有足够单量**。
我们现在连支付都没通,谈这个为时过早。**留到有真实单量再设计**,
而且要设计成"骑手可随时退出且不受惩罚"的版本。

### ✅ 该抄:被我们埋起来的实用功能

这些竞品有、我们**也有能力但没入口**的:

1. **「我的」中心页** —— 把散落的入口收拢;
2. **今日数据**(完成单量 / 今日收入)—— 竞品放在最显眼处,我们要滑到钱包页;
3. **违规申诉**独立入口 —— 现在埋在"异常上报"里;
4. **工时统计**独立入口 —— 现在埋在钱包页;
5. **服务评价**(顾客对我的评价)—— 服务端有 reviews,骑手端**完全没有**;
6. **在线客服**入口 —— 有工单能力,但骑手端没有明显入口。

### ✅ 该抄但要改造:单量热力图

竞品的热力图告诉骑手"哪里单多",这对骑手是**真实有用**的信息 ——
它减少空跑,提高时薪。

但要注意:**不能变成变相调度**。我们的做法是只显示"过去 N 小时各区域的
单量密度",**不做"建议你去哪"的指引** —— 给信息,不给指令。
骑手自己判断,这与"不做强制派单"一脉相承。

### 147. 骑手「我的」中心

```
新建 apps/rider_app/lib/profile_page.dart,作为第四个 tab。

## 顶部:今日数据(竞品都放最显眼处,合理)

今日完成单量 / 今日收入 / 当前在线时长。
**不放任何分数、等级、段位** —— 见上面的红线。

收入要标明口径:哪些已结算、哪些在途(竞品写"不含未结算周期收入",
这个提法值得学 —— 不写清楚骑手会以为平台少算了)。

## 中部:把散落的入口收拢

按「跑单」「保障」「账目」「规则」四组:

- 跑单:我的订单、工时统计、服务评价(新)、单量热力图(#149)
- 保障:意外保障、紧急联系人、事故上报、装备申领
- 账目:我的钱包、收款账户、收入明细
- 规则:抢单怎么排的(已有)、违规申诉、转单纪律、上岗培训、协议规则

**每一项都是已有能力,只是把入口搬到骑手找得到的地方。**

## 底部:平台承诺(这是我们的差异点)

竞品这个位置放的是活动 banner。我们放**平台对骑手的承诺**:
配送费 100% 归骑手、算法公开可查、不按评分差别对待、疲劳只提醒不断单。
每条都链到可验证的地方(/transparency/dispatch),不是标语。
```

### 148. 服务评价:顾客怎么评价我的

```
服务端 reviews 有 7 个端点,但**骑手端完全看不到自己的评价** ——
而顾客的评价直接影响骑手的心情与改进方向。

要做的:
- 骑手能看到自己的评价(评分 + 文字 + 时间);
- **不做评分排名、不做与其他骑手的对比** —— 那是段位体系的入口;
- 差评可申诉(复用已有的 appeals 能力);
- 明确告知:**评价不影响派单**(这是我们的承诺,要在页面上写出来,
  否则骑手会默认它影响,然后开始为分数跑单)。

⚠️ 这一条最容易滑向评分体系。判断标准很简单:
**这个数字会不会影响他能看到的单?** 如果会,就是绳索;不会,才是反馈。
```

### 149. 单量热力图:给信息,不给指令

```
骑手最实际的问题之一是"去哪等单"。现在完全没有这个信息,
只能凭经验。竞品有热力图,这一条该学。

做法:
- 按网格聚合**过去 N 小时**的下单密度,在地图上着色;
- **只显示密度,不显示"建议前往"** —— 给信息,不给指令。
  一旦变成指令,就是变相调度,与"不做强制派单"冲突;
- 数据是**全平台聚合**,不含任何个人信息(与透明中心一个口径);
- 骑手位置不上传给这个功能(它只需要看的区域,不需要知道你在哪)。

技术:复用 admin 已有的 dispatch-overview heat 数据结构,
但**必须做隐私脱敏** —— 管理端能看的粒度和骑手端能看的不一定一样。
```

---

## 明确不做的

- **服务分 / 安全分 / 派单分 / 段位**:见上,违背已公开的承诺;
- **烧钱活动**:无补贴预算,且钱来自抽成;
- **进阶跑单体系**:等有真实单量再设计,且必须"可随时退出不受罚";
- **商城 / 签到 / 积分**:与主业无关,徒增维护面。

### 边界测试

新增三条,从**数据结构层面**堵死评分体系:

- 公开承诺里必须有「不按评分/等级差别对待」;
- 排序权重的 key 里不许出现 rating/score/level/rank/tier/star;
- `dispatch.Candidate` 的字段里不许出现这些词 ——
  **评分进不了打分函数的入参,就不可能影响排序**。

python 单测 92 → 95。

### 顺带修的第五个 LIMIT 截断

`e2e_withdrawal_failed` 断言「工单总数 +1」,而 /admin/tickets 是 LIMIT 50、
库里已有 **243 条** —— 加一条后总数仍是 50,`+1` 永远不成立。
改为验**内容**(退票是否生成了对应工单)而不是验**计数**。

按上一辑沉淀的判据全量扫过「计数型断言」,已无同类残留。
