# 开发提示词 #186–#199:先能收钱,再能上架,最后才是加功能

这一批不加新功能。九路代理把用户端从代码到合规扫了一遍,结论很直接:

**用户端不缺功能,缺的是「能收钱」和「能上架」。**

- 三条业务线的支付全是 mock。生产 `MOCK_PAY_ENABLED=false`
  (`server/app/routers/orders.py:703`)一封死,用户连模拟支付都走不了 ——
  也就是说线上现在一分钱收不到,而不是"收得少"。
- 跑腿下单后没有任何支付入口,单子挂着「待支付」15 分钟后被自动清扫。
- 市场监管总局 **123 号令 2026-06-01 已施行**,营业执照公示与堂食标识是法定强制,
  我们两样都没有 —— 不是"将来要补",是现在就不合规。

所以顺序是:**P0 收钱 → P1 上架 → P2 通电 → P3 工程**。
P2「通电」指的是 `/transparency/*` 那十个已经写完但用户端一个都没接的端点 ——
这个平台最核心的差异化,现在只存在于代码里。

## P0 · 能收钱(#186–#190)

### #186 列表半径与配送上限统一口径

**现状**:商家列表 `radius_m` 默认 5000(`server/app/routers/merchants.py:136`),
配送上限 `delivery_max_km=4.0`(`server/app/config.py:64`)。
4–5 公里的店能看到、能进店、能加购物车,提交时被 `orders.py:419` 以超出配送范围拒掉。

用户视角就是"这店明明在列表里,凭什么不给我送"。这是信任伤害,不是体验瑕疵。

**要做**:列表默认半径直接取 `delivery_max_km`,不再各写一个数。
如果产品上希望超范围的店仍可浏览(自取场景),那就必须在列表卡片上标明
「超出配送范围·仅支持到店自取」,并在进店时就提示,而不是等到付款那一刻。

**验收**:列表里出现的每一家店,要么能下配送单,要么卡片上写清楚为什么不能。

### #187 餐饮商家营业执照公示 + 堂食/无堂食标识

**现状**:`merchants.py:3044` 对餐饮商家只公示食品经营许可证,
`business_license_no` 字段在 `models.py:297` 存在但不下发;酒店反而公示了。
「无堂食」标识全仓零命中。

**法条**:市场监管总局令第 123 号(2026-06-01 施行)第十一条要求经营资质在主页面
显著位置持续展示,第十二条新增堂食/无堂食标识要求,且**列表页和商家主页都要展示**。
36 号令同日废止。

**要做**:
1. `Merchant` 加堂食标识字段(有堂食/无堂食/未填报三态),补 alembic 迁移;
2. 商家端入驻与资料页可填报,平台侧可复核;
3. `merchants.py` 的证照公示接口对餐饮商家同时下发营业执照;
4. 列表卡片与商家详情页展示标识,`licenses_page.dart` 展示营业执照。

**验收**:一家没填报堂食状态的店,列表上显示「未填报」而不是假装有堂食。
不要为了好看给默认值 —— 这是法定公示项,填错比不填更糟。

### #188 结算页选券必须按门槛过滤

**现状**:服务端 `/coupons` 的 `usable` 只判「未使用且未过期」
(`server/app/routers/orders.py:674`),不含门槛;
结算页 `_loadCoupons`(`apps/user_app/lib/checkout_page.dart:50`)
只按面额倒序取第一张,`min_spend_cents` 在整个文件里没出现过。

结果:拿一张「满 50 减 10」点 30 块的单,页面默认勾上并显示"已省 10 元",
提交时被 `orders.py:481` 以「未达券的使用门槛」409 打回。
用户看到的是"说好的优惠不算数"。

**要做**:
1. 按当前餐费+打包费过滤出真正可用的券,不可用的置灰并写明「满 X 可用」;
2. 自动选券要和满减比价,选真正最优的那个 —— 服务端 `orders.py:485` 就是这么判的,
   客户端算法必须和服务端同一口径,否则还是会 409;
3. 券 chip 上硬编码的「无门槛」文案(`checkout_page.dart:466`)改成真实门槛;
4. 金额变化(改数量、删菜、改配送方式)后要重算可用性。

**验收**:结算页显示"已省 X 元"的任何一单,提交都不会因为券被 409。

### #189 待支付订单要有支付入口(跑腿现在是死胡同)

**现状**:`errand_page.dart:372` 下单后 `pop(order)`,
但 `main.dart:859` 用 `MaterialPageRoute<void>` 且 push 不 await,返回值直接丢掉。
订单建出来是 `PENDING_PAYMENT`(`server/app/routers/errands.py:151`),
会以「待支付」出现在订单列表,但全仓 `payOrder(` 只有结算页和加菜页两个调用点,
**订单列表和详情页都没有「去支付」按钮**。用户填完地址、看完报价、点了下单,
页面一关就没了,15 分钟后单子被 `auto_flow` 清扫关闭。

**要做**:
1. `main.dart` 的跑腿路由改成 await 拿回订单,下单成功直接进支付;
2. 订单列表卡片与详情页,对 `pending_payment` 状态统一显示「去支付」按钮
   —— 这个入口不是给跑腿一条线用的,是所有业务线的支付重试通道;
3. 支付失败或用户中途退出,订单仍可从列表回到支付,不留悬空单。

**验收**:跑腿下单能付款成功;任何一个「待支付」的单,用户都点得到付款入口。

### #190 payOrder 不许静默降级

**现状**:`apps/user_app/lib/payment_service.dart:14` 的 fluwx 调用仍是 TODO,
拿到 prepay 参数后 `debugPrint` 一下就回退 `mockPay`。
生产 `MOCK_PAY_ENABLED=false` 时 `mockPay` 返回 403,用户拿到的是一个无法理解的报错。
住宿和团购更糟,各自直接调 `payStayMock` / `payVoucherMock`,连这层封装都没走。

**要做**:
1. 三条业务线的支付统一走 `payOrder`,不再各调各的 mock;
2. 商户号未配置(503)时的开发降级保留,但要在 UI 上明确标注是模拟支付;
3. 商户号已配置但客户端 SDK 未接时,不要假装付款成功 —— 明确告诉用户
   「支付暂不可用」并保留订单待支付,让 #189 的入口能接上;
4. `mockPay` 被 403 拒绝时,给的是人话,不是原始报错。

**注**:fluwx 真正接入需要微信正式商户号和 appId,属于外部依赖,不在本批次。
本批次只保证 **SDK 一到位就能接上,且在此之前不骗用户**。

## P1 · 能上架(#191–#193)

### #191 同意隐私政策前不得联网

**现状**:`SplashGate` 包在 `PrivacyGate` 外层(`apps/user_app/lib/main.dart:127`),
`splash_gate.dart:91,107` 在用户同意前就发了 HTTP;
`main.dart:84` 更早,在 `runApp` 之前就打 `/platform/config`。

这是工信部通报和应用商店驳回的头号事由(2025 年 8 批通报共 315 款,
集中在"未经同意收集"),也是我们自己隐私政策里承诺过不做的事。

**要做**:把 `SplashGate` 挪到 `PrivacyGate` 内层,
`runApp` 前的远端配置拉取移到同意之后。同意之前只允许读本地资源。

**验收**:全新安装、不点同意,抓包应当一个请求都没有。

### #192 商店渠道包必须摘掉 REQUEST_INSTALL_PACKAGES

**现状**:`packages/apk_installer/android/src/main/AndroidManifest.xml:11` 带入
`REQUEST_INSTALL_PACKAGES`,文件注释里写明"商店包要摘掉",
但**没有 store flavor,`scripts/release_apks.sh:26` 也没传 `SUPERZ_CHANNEL=store`**。
国内商店明令禁止绕过审核的应用内自升级,权限扫描必然命中。

**要做**:加 store 渠道,构建时用 `tools:node="remove"` 摘掉该权限并关闭应用内更新入口;
发版脚本区分官网直链包(带自更新)和商店包(不带)。

**验收**:store 包的合并清单里没有 `REQUEST_INSTALL_PACKAGES`,且更新检查入口不显示。

### #193 关闭明文流量 + 订正权限声明

**现状**:三端 `AndroidManifest.xml:17` 都是 `usesCleartextTraffic="true"`,
而 `packages/shared/lib/src/legal.dart:118` 向用户承诺"传输全程 HTTPS 加密"。
这两件事同时成立就是虚假公示。
另外 `legal.dart:149` 声明用户端使用相机,但代码只用 `ImageSource.gallery`
(`main.dart:3118,3304,4332,4737`)—— 申请与业务无关的权限也是商店检测项。

**要做**:release 构建关闭明文流量(本地开发用 debug 的 network security config 放行);
隐私政策里删掉用不到的相机声明,或者把功能补上,二选一,不能两不靠。

## P2 · 让透明中心通电(#194–#196)

### #194 接上 `/transparency/*` 十个端点

**现状**:资金去向、赔付记录、每日核账、可用率、公平性、派单算法、明厨亮灶规则、
治理留痕、月度财报、更新日志 —— 十个端点全部写完、无鉴权、带完整 docstring,
用户端**一个都没接**(`api_client.dart` 只有 `dispatchSpec`)。
`trust_page.dart` 和 `five_percent.dart` 页面都在,纯粹缺数据源。

这是整个仓库性价比最高的一块:后端零改动,前端只差渲染。
也是外部调研得出的空白位 —— 京东把"零佣金"翻译成用户能验证的信任信号
(堂食标签、餐箱温度、透明厨房),而"这单钱怎么分"三大平台都没做。

**要做**:做一个用户点得进去的「平台体检」页,把十个端点渲染出来。
重点是**可验证**,不是好看:每日核账差一分钱就要亮红灯,可用率缺档按不可用算,
赔付记录要包含平台赔出去的钱。数字难看也照实显示 —— 这页的价值就在于它敢难看。

## P3 · 工程(#197–#199)

### #197 首页商家列表虚拟化 + 分页

`main.dart:1280` 用 `SliverChildListDelegate`,`main.dart:1314` 一次性 for 出全部卡片;
服务端 `merchants.py:88` 硬编码 `LIMIT 50`。任何一个真实城市第 51 家店起永远看不到,
而且商家一多首帧就卡。订单页 `main.dart:2930` 已经做对了(builder + 游标分页),照它改。

### #198 订单详情:并发请求 + 生命周期暂停 + 错误可重试

`main.dart:2994` 每 15 秒 `_refresh()`,内部 `main.dart:3033` **串行**发最多 5 个请求,
然后 `setState` 刷一个 614 行的 build,退到后台照跑,订单到终态也不停。
`main.dart:3059` 是 `catch (_) {}`,首次失败则永远转圈,既无提示也无重试。

改:`Future.wait` 并发、`AppLifecycleState` 暂停、终态停表、失败暴露错误加重试按钮。

### #199 MenuPage 错误态 + 首页切 tab 不重拉

`main.dart:2473` 菜单加载失败是死路一条(纯 `Text(_error)`,无重试);
`main.dart:256` 用 `AnimatedSwitcher` + 不同 key,从订单切回首页会重新定位 + 重拉列表。
前者换成共享库已有的 `SzError`,后者改 `IndexedStack`。

## 不做什么

- **团购线冻结**:`voucher_pages.dart` 七个月没有业务逻辑改动,
  要补的是数据模型(适用时段、套餐内容、门店范围)不是 UI,
  而美团团购是最卷的赛道。当前状态(能买能核销能退)够做外卖商家的附加变现工具,停在这里。
- **酒店线不投开发**:闭环已经 90%,瓶颈是没有商家入驻
  (`hotel_pages.dart:115` 的演示城市降级就是证据)。该派 BD,不该派开发。
- **打车、家政、维修、货运、零工**保持关闭(`feature_flags.dart:9`)。
- **不做拉新玩法**:外部调研的结论是用户换平台只因补贴,留下来靠商家密度。
  我们没有补贴预算,力气花在一个小格子里的供给密度上。

## 执行记录

四条线并行落地(服务端合规 / 支付与券 / 渠道包 / 透明中心),
main.dart 是冲突热点,单独串行改。全部 #186–#199 已完成。

### 顺手补掉的三个洞(不在原计划里)

**住宿和团购的模拟支付没有生产闸门。** 外卖那条早就有
`MOCK_PAY_ENABLED` 判断,`stays.py` 和 `vouchers.py` 一直漏着 ——
真实收款上线后,这两个口子等于白送房间和白送券。已补上同一道闸门。

**券在零抵扣时也被烧掉。** `orders.py` 无条件把 `used_order_no` 写上,
而平台券的 `coupon_off` 被前面的立减/满减吃光钳成 0 时,一分没减也照标已用。
改成只有真抵到钱才标记。

**「拍照举证」全是假话。** 用户端四处图片选择全走 `ImageSource.gallery`,
从不开相机,而隐私政策里声明了相机权限、界面上写着「拍照」。
申请与业务无关的权限是商店检测项,文案和声明一并订正成相册口径。

### 一个必须记下来的口径分歧

`payOrder` 支付失败**不再抛异常**,而是原样返回状态仍为 `pending_payment`
的订单(它自己已经把原因提示给用户了)。所有调用方都要判状态,
不能"拿到东西就当成功" —— 这正是 #189 那个入口存在的前提。

### 回归

- 单元测试 199 例通过(含新增 17 例);四个 Flutter 包 `analyze` 全 0 issue;
  `packages/shared` 59 个测试全过。
- e2e 挑了 16 个相关套件逐个查退出码:15 个 exit=0。
- `e2e_errand_send` exit=1,**不是这批改动引起的**:报红的 4 张帮买单
  建于 08-07,今天新建的跑腿单一单没报。开发库里的历史脏数据,
  连跑两次报的是同样这 4 单。要么清库,要么把这条自检的取数范围
  收到用例自己建的单上 —— 一个每次都红的自检等于没有自检。

- **fluwx 没接**:需要微信正式商户号和 appId,外部依赖。代码路径已就绪,
  SDK 一到位就能接上,在此之前不骗用户(见 #190)。
- **见证节点没原生化**:`nodesSummary()` 方法已加,`trust_page.dart` 的外链先留着。
- **App 备案与软著没办**:这两件不是写代码能解决的。
