## P0-1 · 没有任何可用的支付通道(阻塞一切)

**证据**(生产容器 `app.config.settings`):

```
mock_pay_enabled  = False   ← 生产该关,关得对
wxpay_configured  = False   ← 真通道没开
```

两条路都是断的。下单能走完,到支付这一步没有出口 ——
这也正好解释了订单为什么停在 8 月 12 日。

**方案(三条,建议 C 先行)**

- **A 主路:微信支付进件。** 卡点不是代码,是一个必须先问微信的问题:
  我们属于「普通服务商」还是「电商平台服务商」,两套进件与分账 API 完全
  不通用(见 `docs/DEV-PROMPTS-24.md`)。`docs/WXPAY-SETUP.md` 已按电商
  收付通写好,但**周期不可控,不该等它**;
- **B 折中:先开一个普通商户号收款,人工结算给商家。** 代价是二清风险 ——
  货款在平台账户过一手。几家店的规模下可以用「当天结算、平台不留存」压住,
  但这是**明确的合规折中**,要自己认;
- **C 建议先做:到店付 / 货到付款。** 订单流程照常走完,钱线下收。
  零外部依赖、零合规风险,**今天就能上**,而且正好适配冷启动的几家店 ——
  它验证的是供需和履约,那才是现在真正没被验证的东西。
  代码侧要加的只是一种支付方式枚举 + 结算时按"已线下收款"记账。

⚠️ 不要在生产上重开 `MOCK_PAY_ENABLED` 来救急:那是"任何登录用户都能把
订单标成已支付",`platform.py` 的自检把它列为生产红线是对的。

## P0-2 · 拉新链路是断的:微信里打不开点餐页

**证据**:`web/src/` 只有官网、运营大屏、透明中心三个页面;
用户要下单**必须装 Android arm64 的 APK**,没有 iOS、没有 H5。

在中国,新平台的第一批用户几乎全靠微信群/朋友圈传播。
现在把链接发进群里,点开是一个介绍页 —— 传播链在这里断掉。

**方案**:用户端 H5(商家列表 → 菜单 → 下单 → 支付),
**复用现有 API,不需要新后端**。README 的路线图里本来就欠这一条。

这是当前投入产出比最高的一件事:它不增加任何新能力,只是把已有的能力
放到用户能碰到的地方。

## P0-3 · 供给侧空转:1 个骑手

19 家商家里 18 家是演示数据,骑手 1 个。**即使有订单也无法履约。**

技术侧其实备齐了:招募页(`/join/merchant`、`/join/rider`)、自助入驻、
实名认证、接单偏好、新手保护期、周报——**一个都没被真实用过**。

这是运营问题不是技术问题,列在这里是因为它决定了前两条的意义:
支付通了、H5 有了,没有骑手照样跑不起来。

## P0-4 · 账本链在 7-28 被重置过,而见证节点报警了一个月没人管

**这条是第一次评审后新出现的,比商业化差距更要紧** —— 它动摇的是这个平台
唯一抄不走的差异点。

| | 最早锚点 | 最晚 | 天数 |
|---|---|---|---|
| 平台现在 | 2026-06-29 | 2026-08-22 | 55(连续) |
| 官方节点本地留存 | **2026-06-13** | 2026-08-22 | **71** |

平台现存最早那条锚点的 `created_at` 是 **2026-07-28 13:48** —— 现在这条链是
那天**重新起的**(很可能跑过 `scrub_demo.py`,它会清空 `ledger_anchors`
让链从头起)。6-13 ~ 6-28 那 16 天的锚点就此消失。

于是节点每 5 分钟报一次「锚点消失: 2026-06-13; …」,**从 7-28 报到今天**,
`/nodes/summary` 上是 `verified_ok: 0, divergent: 1`。

**对外部观察者来说,这看起来就是「平台删了 16 天的账」。**
`LEDGER-SPEC.md` §4 里我们自己写过这种情况「由人来判断是公告过的重置还是
真的在毁账」—— 而这一个月里**没有人判断,也没有任何公告**。

**方案(按顺序)**:

1. **公告这次重置**:节点页 + 透明中心写明 2026-07-28 因清理演示数据重置了链,
   6-13~6-28 属于演示期。**不公告的话,这个警报挂得越久越像掩盖**;
2. **给链一个机器可读的纪元标记**:`/ledger/anchors` 加 `chain_epoch`
   (重置时间 + 原因),节点看到 epoch 变了就知道是公告过的重置,不必和
   「毁账」混为一谈 —— 这是协议层的缺口,`LEDGER-SPEC` 只写了「由人来判断」,
   没给机器任何判断依据;
3. **根上的问题:演示数据和真实账混在同一条链上。** `scrub_demo` 清演示数据
   会连带清账本,说明链上本来就记着演示订单的账。真开始运营前必须分开,
   否则每清一次演示数据就重置一次链、就报一次警。

## P0-5 · 节点地图的位置基本是错的

「定位不准」是三个问题叠加:

1. **官方部署机画在非洲**:witness 容器没设 `TZ`,取到的偏移是 `UTC+00:00`,
   而 `nodes.html` 的 `nodePos()` 对 `UTC±HH:MM` 是**纬度硬编码 22、
   经度 = 时区 × 15** → `[22, 0]`,落在几内亚湾;
2. **同城堆一点**:IANA 名走 `TZMAP` 查表,`Asia/Shanghai` 全中国一个坐标,
   西安的节点显示在上海;
3. **手机节点不落点**:它们上报的 `tz` 是空串。

⚠️ 要说清楚:**位置粗略是刻意的**。`witness/README` 承诺「节点不收集、
不上传关于你的任何信息」,上报里只有时区没有坐标 —— 这是对的,不该改成
真实定位。所以第 2、3 条**不是 bug**,是设计。

而且页面**已经把话说在前面了**(写这份评审时先漏看了,这里更正):
地图下方原本就写着「落点来自节点自愿上报的时区(城市群级精度)——
我们不做 IP 定位……不想上报时区的节点会出现在列表里但不落点」,
图例里也有「另有 N 个节点未上报时区,未落点」,同城多节点还会绕圈散开。

**所以真正要修的只有两条,都已经改掉**:

1. ✅ compose 给 witness 加 `TZ=Asia/Shanghai` —— 容器默认 UTC,
   自己的节点因此被画到几内亚湾;
2. ✅ `UTC±HH:MM` 的落点不再硬编码纬度 22(那条纬线大半是海),
   改成沿该经度用页面里已有的 `isLand()` 找一个落在陆地上的纬度。
