# 开发提示词 #237–#242:商家端第三批改造——先把"听不到单"堵死

前两批把商家端的功能铺齐了(入驻、上传、评价、看板、自动接单、忙碌模式、
进件资料)。这一批不加功能,**修的是可靠性和可用性**。

## #237 订单列表加载失败不许静默(最严重)

`apps/merchant_app/lib/main.dart:519` 的 `_refresh()`:

```dart
Future<void> _refresh() async {
  try {
    final orders = await widget.api.myOrders();
    if (mounted) setState(() => _orders = orders);
    _autoPrintNew(orders);
  } catch (_) {}          // ← 拉不到就当无事发生
}
```

**这是商家端最坏的失败模式。** `_orders` 同时驱动两样东西:

1. 订单列表本身;
2. **持续催单语音**(`main.dart:415`:`if (_orders.any(paid)) announce()`)。

拉取失败时:列表是空的、语音不响,而顶部的连接指示灯(`_wsConnected`,
`main.dart:1136`)**还是绿的** —— WebSocket 连着不等于列表拉到了。
商家看到的是"一切正常,今天没单",实际上单在往里进。

午高峰漏一单的代价,是这个平台赔不起的。

**要做**:
- 记录失败状态,顶部横条明说「订单列表 X 分钟没更新成功,点这里重试」;
- **失败时不要清空 `_orders`** —— 保留上一次的结果比变成空列表安全;
- 连接指示灯的口径改成「WS 连接 + 列表新鲜度」两者都好才显示正常;
- 首次加载失败要显眼,不能和"今天没单"长得一样。

## #240 错误态要能重试

商家看到的是一片空白或者一个转圈,**没有重试按钮**。

(`dish_manage_page.dart:37`、`shop_tab.dart:65/69/73/760` 等)。

**判断标准**:这次失败会不会让商家**误以为某件事没发生**?
会 → 必须显式提示;不会 → 可以静默,但注释写清楚为什么。

# 落地记录

六条都做完了。下面是**实际怎么改的**,以及改的过程中发现的、原提示词里
没写到的东西。

## #237 订单列表加载失败不许静默 ✅

`main.dart` 加了 `_lastOrdersOkAt` / `_ordersError` 两个状态和 `_ordersStale`
判据(距上次成功 > 60 秒,或首次就失败)。失败时**保留上一次的 `_orders`**,
顶部出一条红色可点重试的横幅,连接指示灯的口径改成 `_wsConnected &&
!_ordersStale`,空态文案在 stale 时换成「订单列表没能加载出来」。

那条横幅后来抽成了共享组件 `SzRetryBanner`(见下)。

## #238 并发拉数据 ✅ —— 顺带发现两个坑

原提示词说「`Future.wait` 并发,各自兜底」。真写下去踩到两件事:

1. **`Future.wait`(List 版)要求返回类型一致**。财务页那五个请求类型各不
   相同,硬用会拿到 `List<Object>`,再一个个强转回去,得不偿失;
2. 改成「先全部发出去、再逐个 `await`」之后,**第一个抛异常就跳进 `catch`,
   后面几个 Future 没人接** —— 变成未处理的异步错误,Flutter 会往控制台
   刷红,测试里直接算失败。记录 `.wait` 能保证都被 await,但它抛的是
   `ParallelWaitError`,`toString()` 是一串英文,商家看了一脸懵。

所以在 `packages/shared` 里加了 **`SzGather`**:每个 Future 都被 await,
失败记下**第一条原始异常**,类型不丢,`message` 只在 `ApiException` 时
用它的人话、其余兜底成通用说法(避免把接口地址和参数抖到界面上)。
次要数据用 `soft(future, fallback)`,不计入 `failed`。

覆盖到:`finance_page`(5)、`shop_tab`(6)、`appeal_page`(3)、
`invoice_page`(2)、`main.dart:_refreshToday`(2)、`dish_manage_page`(2)。
`reviews_page:298` 是三目运算的两个分支,只会走一个,不是并发点。
`shop_tab:797` 是「删完再拉」,必须串行。

`packages/shared/test/gather_test.dart` 7 条用例,其中一条专门用
`runZonedGuarded` 断言**没有漏网的异步错误**。

## #239 长列表虚拟化 ✅

改成 `ListView.builder` 的:

- **菜品**(`dish_manage_page`):原来是「分类嵌菜品」两层 `for`,没法直接
  按需构建 —— 拍平成一维 `_MenuRow`(要么分类标题、要么一道菜)再交给
  builder。菜单上百道时,原来首帧要把每行的缩略图、上下架开关、
  估清/补货按钮全建出来;
- **消息中心**、**进货台账**:这两个是翻页/只增不减的,越滚越长。

没改的:财务按日账单(封顶 30 天)、提现记录(取前 20)、连锁门店、
节假日计划 —— 都是有界的小列表,改了只是增加复杂度。

## #240 错误态可重试 ✅

补了 `_error` + `SzError(onRetry:)` 的页面:财务、菜品、经营分析、
团购券管理、评价、消息中心、判责申诉。

判断标准照原文:**这次失败会不会让商家误以为某件事没发生?**

- 评价/消息:失败时原来显示「这一栏没有评价/消息」—— 差评看不到就错过
  申诉窗口;
- 菜品:失败时原来显示「还没有菜品」—— 商家会跑去重录一遍菜单;
- 店员名单(`shop_tab`,原来是空 `catch`):拉不到照原样开面板,店主看到
  一份空名单会以为店员清光了,而那些账号还在听单;
- 换证申请(`license_page`,原来是空 `catch`):拉不到就显示成「没有待审
  申请」,而这句话对应着「再交一份」的按钮,商家会重复提交。

最后一条只缺一块数据、页面主体还能看,所以用横幅而不是整页错误态 ——
为此把 #237 那条横幅抽成了共享的 **`SzRetryBanner`**。它和 `SzError` 的
分工:整页没数据用 `SzError`,只是某一块拉不到用 `SzRetryBanner`。

逐页扫的时候又翻出三处**失败被显示成一句错误的事实陈述**,比空白更坏,
因为商家会照着它做决定:

- `printer_page`:云打印配置拉不到时,界面显示的是「平台还未开通云打印
  服务」—— 这是一句关于平台的断言,商家看了就不去绑打印机了。改成横幅
  说明「开没开通现在说不准」;
- `rider_track_page`:骑手位置拉不到和骑手真的没上报位置,原来都显示
  「骑手位置暂不可用」。顾客正在催单,商家该回的那句话完全不同 ——
  现在区分开,拉取失败时明说「这不代表骑手没在送」;
- `shop_tab` 自己:店铺信息没拉到就一直转圈,补了 `SzError` + 重试。

空 `catch (_) {}` 现在全仓为 0:该报的报了,该静默的在注释里写明了为什么
(打印机断连失败、重试中间轮的异常)。
