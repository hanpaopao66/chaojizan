# 开发提示词 #139–#141:派单算法讲道理,并且公开

承接 docs/DEV-PROMPTS-14.md。地图换成官方 SDK 之后,**地图能力还只用在"看"上**,
没有用在"算"上。这一辑把骑手侧的路径与顺路算法修对,并把它公开出去。

## 诊断(全部有实测反例,不是推测)

现算法在 `server/app/routers/riders.py::available_orders`:

```
综合分 = 骑手到取餐点直线距离(米) − 等待分钟 × 150 − 小费元 × 300
        (越小越靠前)
same_shop = 与手头单同商家
same_way  = 与手头单**送达点**相距 < 800m
```

### 缺陷 1:顺路标记根本不参与排序(最严重)

`same_shop` / `same_way` 算出来只用于两件事:UI 上打个标、豁免接单半径过滤。
**综合分里一个字都没有它们。**

顺路串单是外卖单位经济最大的杠杆 —— 同样的时间送两单。现在算出来了却不用,
等于白算。一个真顺路的单,排序上完全没有优势。

### 缺陷 2:顺路判定只看送达点,不看取餐点

实测反例(骑手手头单:A 取餐 → D1 送达,向北 1112m):

| 场景 | 现算法判定 | 实际多跑 |
|---|---|---|
| 取餐点也在 A 附近,送到 D1 旁边 | `same_way = True` | **73 米** |
| 送达点在 D1 旁边,取餐点在**反方向 3km** | `same_way = True` | **5982 米** |

两单都被标成"顺路",一个多跑 73 米,另一个多跑近 6 公里。
骑手照着这个标记接单会被坑 —— 而他信任这个标记,正是因为是平台给的。

### 缺陷 3:排序只看「到取餐点多远」,不看「取餐后要送多远」

同一家店的两个单:一个送 220m,一个送 4km,**综合分完全相同**。
骑手看不出哪单更划算,只能逐个点进去看。

### 缺陷 4:全程直线距离

`haversine_m` 是直线。实测成都两点:直线 1467m,**腾讯骑行路径 1745m,差 19%**。
隔河、跨高架、单行道的场景只会更大。`pricing.py` 自己写着
「之后接路径规划 API 可换成骑行距离」—— 一直没换。

配送费按直线算,**骑手实际在亏**;而配送费 100% 归骑手是平台的承诺,
用一个系统性低估的距离去算它,承诺就打了折。

### 缺陷 5:权重没有上限

- 等待权重 150 米/分钟:等 30 分钟 ≈ 抵消 4500m,**超过整个 4km 配送半径**;
- 小费权重 300 米/元:小费 20 元 ≈ 抵消 6000m,同样超出半径。

等待权重需要上限是因为:超过一定时间的单该走「无人接单兜底」流程
(no_rider_alert / no_rider_cancel),而不是靠把它顶到榜首硬推。
小费权重需要上限是因为:**这是"钱能买多靠前"的定价**,无上限意味着
出得起钱的人永远排在前面 —— 这条要和平台"不杀熟"的立场对齐,
而且既然要公开算法,这个数就必须是能讲出道理的。

### 139. 用真实骑行距离替换直线距离

```
接腾讯骑行路径规划(已验证可用:
https://apis.map.qq.com/ws/direction/v1/bicycling/,status 0)。

服务端代理,key 不下发 —— 与 /geo/tips、/geo/reverse 同一口径。

**必须有缓存**:抢单池一次要算几十个单的距离,每个都实时请求的话
配额瞬间打光(按次计费)。缓存键用「起点网格 × 终点网格」,
网格取 ~100m(0.001°),同一片区的请求共用一条结果。

**必须有降级**:路径规划挂了/超时/配额用尽时回退直线距离,
并在返回里标明用的是哪种(`distance_source: route|straight`)。
不标的话,骑手看到的距离时准时不准,却不知道为什么。

配送费改用骑行距离要**单独灰度**:它直接改钱。
先只用于"给骑手看的距离与排序",配送费口径的切换单开一个开关,
切之前把新旧两种算法在真实订单上跑一遍对比,差多少要有数。
```

### 140. 顺路撮合:让顺路真的影响排序

```
把顺路从"UI 标记"变成"排序主力",并且判定要讲几何。

## 顺路的正确判定:看绕路增量,不看两点距离

判据换成「接了这单要多跑多少米」:

    绕路增量 = (当前位置 → 新单取餐点 → 新单送达点 → 手头单送达点)
             − (当前位置 → 手头单送达点)

这个量才是骑手真正付出的成本。用它替换现在的「送达点相距 <800m」。
阈值给绕路增量,不给两点距离 —— 前者有物理意义,后者没有。

顺路等级建议分档(具体数值要用真实订单验证后再定,别拍脑袋):
  - 强顺路:绕路增量 < 500m,排序上给显著提前
  - 弱顺路:绕路增量 < 1500m,给适度提前
  - 不顺路:不给优势

## 同商家(same_shop)是更强的顺路

同一家店取两单,取餐环节的时间几乎为零 —— 比"路线接近"更值钱。
它应该有独立且更高的权重,不要和 same_way 混成一个布尔。

## 排序要把送程算进去

现在只看「到取餐点多远」。骑手真正关心的是**这一单整体划不划算**:
到店距离 + 送程距离,以及这单给多少钱。

## 不做强制派单

平台立场是广播抢单,骑手自己选。这一条不变 ——
算法只负责**把信息排得更有用**,不负责替骑手做决定。
排序变了,但"接不接"始终是骑手的。
```

### 141. 把算法公开(这是本辑的重点)

```
账目透明是这个产品唯一抄不走的差异点。而**派单算法对骑手的意义,
等同于账目对商家的意义** —— 它决定骑手今天挣多少。
资本平台的算法是黑箱,骑手只能猜"为什么好单不给我"。

在透明中心(/transparency,已有 7 组接口)加第 8 组:`/dispatch`。

要公开的内容:

1. **完整公式与全部权重的当前取值**,不是描述性文字。
   骑手要能拿自己的单代进去算,得到和 App 里一样的排序;
2. **每个权重为什么是这个数**。「等待 1 分钟 ≈ 150 米」不是常识,
   必须讲出它的道理(否则公开了也等于没公开);
3. **顺路的几何定义**,包括绕路增量怎么算;
4. **不做什么**:不做强制派单、不按骑手评分差别对待、
   不因为骑手拒过单就降权。**承诺不做的事和承诺做的事一样重要** ——
   这几条正是资本平台被骂最多的地方;
5. **权重变更历史**。改了算法就要记一笔,时间 + 改了什么 + 为什么。
   算法可以改,但**不能悄悄改** —— 悄悄改就等于没公开过。

技术要求:
- 公开无鉴权(与透明中心其余接口一致);
- 权重值从代码常量**同源读取**,不许在接口里另写一份字面量 ——
  抄一份的那份迟早和真实算法对不上,那时公开的就是假的;
- 骑手端加入口:能从抢单页直接看到"为什么这样排"。
  公开给外人看却不给骑手看,是本末倒置。

验收:
- 改一个权重常量,/dispatch 返回值跟着变(证明是同源,不是抄的);
- 骑手端能看到,且看得懂(不是把 JSON 甩出来);
- 有测试钉住「公开值 == 代码常量」。
```

## 执行记录

三条都已落地并实机验证。

### 修了什么(全部有实测反例)

| 缺陷 | 修法 | 验证 |
|---|---|---|
| 顺路标记不进排序 | 顺路/同店成为排序主力 | 强顺路综合分 −1337,普通单 0 |
| 顺路只看送达点 | 改用**绕路增量** | 假顺路从 `True` 变 `none`(绕路 7214m) |
| 只看到店距离 | 送程按 0.35 权重入分 | 同店 220m 单排在 4km 单前 |
| 全程直线距离 | 腾讯骑行路径规划 + 缓存 + 降级 | 实测直线 1467m / 骑行 1745m |
| 权重无上限 | 等待封顶 3000m、小费封顶 1500m | 巨额小费买不过强顺路+同店 |

### 算法公开

- `/transparency/dispatch` 无鉴权公开,**从 services/dispatch.py 的常量直接读**;
- 骑手端「抢单怎么排的」页,入口就在抢单池的半径栏旁边;
- 官网透明中心第 8 节,公式用账目深色台面呈现;
- 17 条单测,其中「改了常量公开值跟着变」这条是真·同源检验 ——
  抄一份字面量的实现过不了它。

### 顺带修的三个既有缺陷

排查回归时发现,都不是本次改动引入的:

1. **e2e_stays_settle 跨月挂**:用例用 `date.today()`(机器本地时区)算账期,
   服务端按北京时间。跨月那几小时会算出上个月账期,而订单已属新月 ——
   实测 2026-08-01 00:03 北京时间挂过一次;
2. **e2e_home_filters 的手机号断言太粗**:写的是 `"13" not in blob`,
   被 `dormant_30d: 13`(沉睡用户数)打中。守的东西是对的,判据错了 ——
   改成 `1[3-9]\d{9}` 形态匹配,并双向验证过(真手机号能抓、计数不误报);
3. **`/riders/location` 的 haversine_m 导入被误删**:我替换 available_orders
   的导入时波及了它。两处函数各自局部导入,改一处要看清楚是哪一处。
