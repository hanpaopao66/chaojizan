# 开发提示词 #200–#206:服务商资质到位,先做不依赖类目答案的那半

微信支付**服务商资质已下来**。但在写任何一行收款代码之前,有个问题必须先问微信:

**我们是「普通服务商」还是「电商平台服务商」?**

普通服务商的特约商户进件走 `/v3/applyment4sub/`,而官方文档在这个接口上明确写着
「银行、支付机构、**电商平台**不可用」;电商平台要走[平台收付通](https://pay.weixin.qq.com/doc/v3/partner/4012086891),
进件是 `/v3/ecommerce/applyments/`、分账是 `/v3/ecommerce/profitsharing/orders`,
**两套 API 完全不通用**。外卖平台大概率算电商平台,但这个不能猜。

所以这一批只做**两套 API 都要、答案出来之前不会白写**的部分。
进件 API 本身、下单改服务商参数、分账真实调用,一律等类目确认。

---

## 先说清楚这次迁移到底改变了什么

不是"接个 SDK",是**钱的流向整个换掉**。

现在:货款 100% 先进平台的商户号,再由平台人工线下打款给商家
(`Withdrawal.channel` 默认 `manual`,`models.py:842`)。
这在监管口径上就是**二清** —— 平台归集用户资金再向下游结算,
而这需要支付业务许可证(《非银行支付机构监督管理条例》2024-05-01 施行)。

服务商模式:官方文档写明「微信支付 → 子商户结算账户,**服务商账户不直接收款**」。
钱直接进商家账户,平台的 5% 通过**分账**拿。

这正是路线图里那句「货款直达商家不经平台沉淀」。它不是优化,
是把一个真实存在的法律风险拆掉。

## P0 · 真钱进来之前必须干净(#200–#202)

### #200 分账的桩不许"假成功"

`server/app/services/profit_sharing.py:34` 的 `_call_channel` 现在的行为是:
未配置返回 False;**已配置就只打一行日志、返回 True,把台账置成 `success`**。

也就是说,哪天在管理端把某个商家的 `ps_ready` 打开,系统会开始产生
「分账成功」的记录,而实际上一分钱都没动。**台账和真实资金对不上,还对得很自信。**

这个不管最后走哪套 API 都得先改掉。改成:渠道未实现就**失败要响** ——
记录停在 `pending`(而不是假 success),日志用 error 级别,
并且让每日账务自检能看见「有多少笔分账挂着没走通」。

顺带清掉 `wechat_pay.py:119-130` 的 `request_profit_sharing` ——
它没有任何调用方,是死代码,留着只会让人以为分账已经接了。

### #201 外卖订单要存 `transaction_id`

分账接口的必传入参是微信侧的 `transaction_id`,而**外卖订单表根本没有这个字段**
—— `wx_transaction_id` 只存在于 `StayOrder`(`models.py:1918`)。

支付回调里拿得到,现在直接丢掉了。加字段、回调落库。
这是分账的硬前提,两套 API 都一样,现在就该做。

注意:**存量已支付订单补不回来**。这意味着资质到位之前的订单永远分不了账,
这条要写进迁移说明,别到时候以为是 bug。

### #202 支付回调加固

`server/app/routers/payments.py:35` 现在只做了验签和幂等,**没有校验金额**。

回调里带着 `amount.total`,但代码从不拿它和 `order.total_cents` 比。
验签能挡住伪造回调,但挡不住"金额对不上"这类渠道侧异常或自己的下单 bug ——
而这类错误的后果是订单被标成已付、商家开始做菜,钱却没收够。

要做:
1. 比对 `amount.total` 与订单应付金额,不一致**拒绝入账**并告警(记 `audit_alerts`),
   而不是先入账再说;
2. 落 `transaction_id`(#201);
3. 服务商模式下回调会带 `sp_mchid`/`sub_mchid`,预留校验位置并写清楚;
4. 找不到订单现在是 `raise HTTPException(404)` —— 微信会**重试**这个回调,
   404 对它是"我等会儿再来",这个行为是对的,但要确认日志里能一眼看出来。

## P1 · 进件资料(两套 API 都要收的东西,#203–#206)

进件的 API 形状取决于类目,但**要商家交的材料两套是一样的**:
营业执照照片、法人身份证正反面、结算银行账户、超级管理员联系人、经营场景照。

而我们现在**一样都没有** —— `Merchant` 只存了食品经营许可证号和照片,
营业执照连照片都没有、只有一个号(`models.py:279`)。

所以这部分现在就能做,而且它是整条链路里最耗时的一环:
**没有商家配合,一家特约商户都开不出来。**

### #203 进件资料的数据模型与敏感信息处理

**字段(定死,几端按这个对齐)**,加在 `Merchant` 上:

| 字段 | 说明 |
|---|---|
| `subject_type` | 主体类型:`individual` 个体工商户 / `enterprise` 企业 |
| `business_license_image_url` | 营业执照照片(私密桶,purpose=`license`) |
| `legal_person_name` | 法人姓名 |
| `legal_person_id_encrypted` / `legal_person_id_tail` | 法人身份证号,密文落库 + 尾 4 位展示 |
| `legal_person_id_front_url` / `legal_person_id_back_url` | 身份证人像面/国徽面(私密桶,purpose=`id_card`) |
| `admin_contact_name` / `admin_contact_phone` / `admin_contact_email` | 超级管理员(微信要给他发通知、他要扫码签约) |
| `settle_account_type` | `corporate` 对公 / `personal` 对私 |
| `settle_account_name` / `settle_bank_name` / `settle_bank_branch` | 开户名 / 开户银行 / 开户支行 |
| `settle_account_no_encrypted` / `settle_account_tail` | 银行账号,密文落库 + 尾 4 位 |
| `applyment_status` | `not_submitted` / `submitted` / `need_sign` / `need_account_verify` / `rejected` / `finished` |
| `applyment_no` / `applyment_reject_reason` / `applyment_updated_at` | 微信侧申请单号与驳回原因 |

**敏感信息的规矩(这条比字段重要):**

- 身份证号和银行账号**一律走 `services/crypto.py` 加密落库**,和 `PayoutAccount`
  同一套。接口**只回尾 4 位**,任何角色都一样;
- 证件照走**私密桶**(`id_card`/`license` 这两个 purpose 已经是私密的,不用新造),
  出口只有 `uploads.py` 的 `private_file`,每次访问过鉴权;
- **管理员查看解密后的身份证号/银行账号必须留痕**(写审计),
  谁在什么时候看了哪家店的什么字段。这是一个把「账目三方透明」写在首页的平台,
  对用户隐私不能反过来松;
- 经营场景照用现有的 `shop` / `gallery`(公开)—— 门头照本来就是给用户看的,
  不要为了进件把它挪进私密桶,那样商家详情页就没图了。

**不要复用 `PayoutAccount`。** 它是「平台打款给谁」(按 user 一人一户),
而进件结算账户是「微信把钱结给谁」(按门店,连锁每店可以不同)。
两件事,而且分账上线后前者对商家就没用了。同一个银行账号存两张表迟早分叉。

### #204 商家端进件资料采集(Flutter)

`apps/merchant_app/lib/onboarding.dart` 现在是三步(业态 → 门店信息 → 资质证照),
入驻硬校验只有食品经营许可证。

**不要把进件资料塞进入驻流程。** 理由:入驻要快,多一步就多一批人放弃;
而且进件资料是"能收钱之前"要的,不是"能开店之前"要的。
做成独立的「收款资料」页,从「店铺」页进,顶部说清楚为什么要这些。

⚠️ **文案是这一页的一半工作量。** 要商家交法人身份证和银行账号,
不解释清楚就是在要命的东西。至少讲明白三件事:
① 这些资料交给微信支付、不是交给平台,平台只是代传;
② 交了之后**货款直接进你自己的账户**,不再经过平台的手 —— 这对商家是变好不是变坏;
③ 平台看得到什么(尾号)、看不到什么(完整号码),以及谁看了会留痕。

### #205 merchant-web 同步

`merchant-web/` 加同一套页面。手机上传身份证和填银行账号很难受,
而这些资料多半是老板在电脑前照着营业执照抄 —— 网页端才是主场景。

字段与校验和 #204 完全一致,共用同一组接口,不要各写一套校验规则。

### #206 进件状态与管理端复核

商家侧:能看到自己卡在哪一步。微信的进件是**异步**的,中间有「待账户验证」
和「待签约」两个环节要商家本人操作(扫码确认、验证打款金额),
状态页不说清楚,商家会以为提交完就没事了。

平台侧:管理端要能看到「谁填齐了、谁缺什么、谁被驳回了」。
资质到位后这就是提交微信的工作队列。

**接口契约**(几端按这个写,别自己发明):

- `GET /merchants/me/applyment` —— 资料 + 完整度 + 状态,敏感字段只回尾号
- `PUT /merchants/me/applyment` —— 提交/更新资料。**这一版只落库,不调微信**
- `GET /admin/applyments` —— 平台侧队列,按完整度和状态筛
- `GET /admin/merchants/{id}/applyment` —— 详情;**解密字段单独接口 + 审计留痕**

## 明确不做的(等类目答案)

- **进件 API 本身**:`applyment4sub` 还是 `ecommerce/applyments`,取决于类目;
- **下单改服务商参数**:`sp_appid`/`sp_mchid`/`sub_mchid` 三件套,以及
  `partnerid` 该填服务商号还是特约商户号(官方文档:appId 与 partnerId 必须成对,
  平台用自己的 App 收款就该填 `sp_mchid`);
- **分账真实调用**:`profitsharing/orders` 与解冻;
- ⚠️ **下单时的 `settle_info.profit_sharing=true`**:漏了这个标记,
  资金直接结算给商家,**那一单的佣金永远拿不回来**。等改下单参数时一起做,
  但现在就记在这里,因为它是这次迁移最不可逆的一个点。

## 几个到时候会踩的坑(先记下来)

- 分账有 **30 天窗口**,过期不能分;
- 分账要商家在他自己的微信后台**授权**并设置最大比例,平台单方面开通不够;
- 已分账的订单退款,要**先发起分账回退**再退款,否则商家账上余额不足会直接失败 ——
  而我们的退款调用点有 15 处,顺序约束现在一处都没有;
- 跨主体绑定**不支持移动应用类型 AppID**,所以平台自有 App 不能当某个商家的 `sub_appid`。

### 几个动手之后才看清的点

**分账的桩比想象中更危险。** 原以为只是"没实现",实际是 `_call_channel`
在配置齐全时**直接返回 True 并把台账置 success**。也就是说它不是没做,
是做了一个会说谎的版本。现在改成三态 `CHANNEL_OK / CHANNEL_UNIMPLEMENTED /
CHANNEL_ERROR`,恒返回 UNIMPLEMENTED;`attempts` 只在渠道真被调用过时递增,
否则未实现的渠道会把所有记录烧成 `failed`,等接通了反而没得重试。

**金额校验只能在"即将入账"那条路上做。** 支付之后 `total_cents` 会被加急小费、
帮买按小票补收、改地址退差价改动,拿一条老回调去比新金额必然误报 ——
而误报多了这条检查就废了。所以只在订单仍是 `pending_payment` 时比。

**「钱收了、单没了」以前是静默 ack。** 取消与支付并发、或超时清扫抢在回调前面,
用户付款成功而订单已取消,钱躺在商户号里没人知道,直到用户来投诉。
现在仍然 ack(已取消是终态,重试不会把它变回来)但留告警,并且照样落
`transaction_id` —— 人工退款时要用。

**审计不能变成第二个泄露点。** 管理员查看完整身份证号/银行账号走单独接口、
理由必填,而审计记录里**只存尾号**。已知短板:用的是 `AppEvent`,
而注销账号会删该用户的 AppEvent 行 —— 审计不该被被审计者删掉,
加了 warning 日志兜底,将来有专表再换。

**私密图的老坑顺手填了。** 私密桶的唯一出口每次都要过鉴权,
而 `<img src>` 不带 token。收款资料页一开始就是先 fetch 成 blob 再显示,
但发现健康证页一直是直接塞 URL —— 也就是说商家传完健康证就再也看不到自己传了什么。
一并改了。
