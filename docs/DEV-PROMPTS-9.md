### 114. 骑手新单推送(抢单模式的动力来源)

```
给超级赞补上骑手新单推送。先读 docs/DEV-PROMPTS-9.md 顶部约束与 docs/DEV-PROMPTS.md 通用约定。

现状(2026-07-29 审计发现):server/app/services/push.py 只有四个推送场景——notify_order_status(推用户)、notify_new_order(推商家老板)、notify_review_reply(推用户)、notify_favorites(推收藏用户)。**没有任何"有新单可抢"的推送给骑手**;骑手唯一的新单信号是骑手端每 5 秒一次的 availableOrders 轮询(rider_app/lib/main.dart 的 _refresh,发现 fresh 单才响铃 + 振动)。后果:App 一退后台骑手就是盲区。auto_flow.py 的 _notify_no_rider 确实会推在线骑手,但那是"已经超时没人接"的兜底告警,不是正常新单;等它触发时单子已经凉了。
因为这个缺口,前端只能把后台轮询降频到 20 秒而不能停(见 rider_app 的 _startPolling 注释),电量还在白烧。
业务规则(已拍板):
- 触发点:订单进入待接单池时推一次。即支付成功(services/payment_core.py 的 mark_order_paid,那里已经在推商家了)且该单确实需要骑手——**到店自取(pickup)与商家自配送(self_delivery)的单不推**;
- 收件人:is_online 为真的骑手,且订单商家在该骑手的接单半径内(users.grab_radius_km,null=不限;骑手最后上报位置取现有的位置上报数据)。半径外的不推——推了也抢不到,只会训练骑手忽略推送;
- **合并与限频**:同一骑手 60 秒内最多收一条。窗口内又来新单就合并成「附近有 N 个新单」,不要一单一条;用 Redis 记窗口(参照 auto_flow 里 maybe_run_daily_audit 的防重手法);
- 文案:单条给「商家名 → 收货区域,配送费 ¥X」(配送费是骑手最关心的);合并条给「附近有 N 个新单,最高 ¥X」。**不写"快抢""手慢无"这类话术**;
- 点击进抢单大厅并刷新;单子已被别人抢走时提示「这单已被接走,看看其他的」,不弹错误;
- 骑手下线(is_online=false)后不再收到;这是骑手自己的开关,不做"引诱上线"的推送。
技术要点:推送失败绝不阻塞下单主流程(照现有 push 的写法只记日志);push_logs 表记一条便于排查"没收到提醒";合并逻辑放 services/push.py 内部,调用方只管"这单进池了";注意 mark_order_paid 是在事务里调的,推送要放到 commit 之后发(参照 _notify_no_rider 的写法)。
前端配套(rider_app):
- 推送到位后把后台轮询彻底停掉(现在是降频 20 秒的妥协),前台保持 5 秒兜底;
- PushService 的通知点击路由到抢单大厅。
验收:e2e_rider_push.py——造一单支付成功,断言在线且半径内的骑手收到一条(用 push_logs 断言,不真发);半径外的骑手不收;60 秒内第二单合并不新增条数;自取单与自配送单不推;下线骑手不推。回归 e2e_orders + e2e_reversal_audit。
```

## 竞品分析结论(2026-07-29)

功能清单已经比多数同类完整(拼单/预约/自取/追加/超时赔付/发票/售后/申诉/
实名/团购核销)。空间不在"再加功能",在三处:

1. **有实现与公开立场相冲突**——邀请有礼、生日券、复购提醒的券都是平台承担
   (`referrals.py` 头注释写着 subsidy 口径,`marketing.py` 三个任务同理),
   而用户端「我们承诺不做的事」印着"不靠补贴换增长"。金额不大,方向是错的。
2. **零补贴下唯一能规模化的增长引擎是"让商家带客"**,而商家端一件推广物料
   都没有(无店铺码、无海报、无分享、无专属链接)。商家在这里每单多赚十几个点,
   他们有动力,平台没给工具。
3. **真实风险不是功能缺,是供给密度**。低单量 → 骑手赚不到 → 送得慢 →
   用户流失 → 单量更低。解药(顺路聚合/自配送/自取)三样都已经做出来了,
   但都不是主线。

### 115. 营销发券的资金方归位:平台不再出钱

```
把邀请有礼/生日券/复购提醒三处的发券资金方从平台改成商家。先读 docs/DEV-PROMPTS-9.md 顶部约束。

现状:server/app/routers/referrals.py 头注释明写「券为平台承担(subsidy 口径)」,reward_referral_if_first_order 直接 db.add(Coupon(...)) 且不带 funder(默认 platform);services/marketing.py 的 run_birthday / run_winback / run_favorites 走 admin 建的 trigger=birthday/winback 批次,同样是平台预算。而用户端「钱去哪了」页的「我们承诺不做的事」里印着「不靠补贴换增长,也就不会有断补后的涨价」——产品行为和公开承诺不一致,被扒出来是硬伤。
基建已经齐了:Coupon 有 funder(platform/merchant)与 merchant_id 字段,CouponBatch 支持 merchant_id + total 预算封顶 + per_user_limit,商家自建券接口 POST /merchants/me/coupon-batches 已存在(trigger="shop",成本商家承担、平台按券后实收计佣)。
业务规则(已拍板):
- CouponBatch.trigger 增加 "referral"(商家自建的新客推荐券)。商家在店铺设置里可开可关、自定面额与预算总量,与现有店铺券同一套 UI 和同一套预算封顶;
- reward_referral_if_first_order 改为:看被邀请人首单落在哪家商家 → 该商家有启用中的 referral 批次就从批次发两张(邀请人 + 被邀请人各一张,限该店可用、funder=merchant);**没有批次就不发券**,只把邀请关系记成 rewarded,并推「你的好友已经在超级赞下单了」——不再由平台兜底出钱;
- run_birthday / run_winback / run_favorites 同理:只从 merchant_id 非空的批次发;平台批次(merchant_id 为空)一律不再新建,已存在的存量批次跑完即止,admin 建批次接口移除 birthday/winback 的平台选项;
- **不改任何已发出的券**,存量券照常可用——改的是以后不再发平台券;
- 用户端邀请页文案同步:从"你俩各得券"改成"你的好友首单那家店会送你俩券(参与店铺)";没有参与店铺时不许暗示有券。
技术要点:funder=merchant 的券下单时走 discount 口径(与满减同通道),不进 subsidy——审计恒等式与公开账本因此都不用改,但改完必须跑 e2e_reversal_audit + e2e_p4_witness 确认;coupons.source 唯一约束继续防重发;referral 批次的每人限领沿用 per_user_limit。
验收:e2e_referral_funding.py——商家没建 referral 批次时完成首单只记 rewarded 不发券;建了批次则双发且 funder=merchant、merchant_id 正确、只在该店可用;批次 total 发完自动停;存量平台券不受影响。回归 e2e_orders + e2e_reversal_audit + e2e_p4_witness。
```

### 116. 商家专属码与一键海报(零补贴增长引擎)

```
给商家端补推广物料:店铺专属码 + 一键生成海报。先读 docs/DEV-PROMPTS-9.md 顶部约束。

业务规则(已拍板):

- 海报文案**只讲事实不讲话术**:不许出现"最低价""立减""限时"这类词;费率数字取该店真实 commission_rate,不写死 5%(阶梯佣金下可能是 4.5%);
- 商家如果建了店铺券或 referral 批次(#115),海报上多印一行「扫码领本店 X 元券」;没建就不印,不做空头承诺。
技术要点:短链不要暴露内部 id 规律,用 merchants 表加一个 short_code(6 位,建店时懒生成、唯一);海报尺寸按微信分享习惯出 3:4;字体用已打包的 SzSerif/SzSans,不额外加资源;分享走 share_plus(商家端已有依赖)。
验收:e2e_shop_shortcode.py——短码唯一、可解析回店铺、无效码 404;商家端实机生成海报并成功唤起系统分享;海报在深色模式下仍是浅底(离屏渲染固定浅色,照 share_card 的处理)。
```

### 121. 低密度城市把自取与自配送做成主推(策略级,需先拍板)

```
说明:这条是运营策略在产品上的体现,不是新功能——三样解药(顺路聚合 sameShop/sameWay、商家自配送 self_delivery、到店自取 pickup)都已经做出来了,只是都不在主线上。

问题:零补贴 + 低抽成,商家愿意来(省钱),但骑手为什么来?配送费 100% 归骑手听着好,一天只有 5 单的话收入还是低。冷启动会走成:骑手少 → 送得慢 → 用户流失 → 单量更少 → 骑手更少。
思路:在单量密度不够的城市/时段,首页默认主推「附近可自取,省 3 元配送费」,而不是把外卖配送当唯一形态。用户省钱、商家不用等骑手、平台不用先凑出骑手密度。等单量起来再切回配送优先。
开工前先看数据:现有订单里 pickup 占比多少。如果很低(大概率),说明不是用户不要,是入口太深——自取现在藏在结算页的一个开关里。
```
