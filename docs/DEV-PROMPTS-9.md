### 114. 骑手新单推送(抢单模式的动力来源)

```
给超级赞补上骑手新单推送。先读 docs/DEV-PROMPTS-9.md 顶部约束与 docs/DEV-PROMPTS.md 通用约定。

现状(2026-07-29 审计发现):server/app/services/push.py 只有四个推送场景——notify_order_status(推用户)、notify_new_order(推商家老板)、notify_review_reply(推用户)、notify_favorites(推收藏用户)。**没有任何"有新单可抢"的推送给骑手**;骑手唯一的新单信号是骑手端每 5 秒一次的 availableOrders 轮询(rider_app/lib/main.dart 的 _refresh,发现 fresh 单才响铃 + 振动)。后果:App 一退后台骑手就是盲区。auto_flow.py 的 _notify_no_rider 确实会推在线骑手,但那是"已经超时没人接"的兜底告警,不是正常新单;等它触发时单子已经凉了。
因为这个缺口,前端只能把后台轮询降频到 20 秒而不能停(见 rider_app 的 _startPolling 注释),电量还在白烧。
业务规则(已拍板):
- 触发点:订单进入待接单池时推一次。即支付成功(services/payment_core.py 的 mark_order_paid,那里已经在推商家了)且该单确实需要骑手——**到店自取(pickup)与商家自配送(self_delivery)的单不推**;
- 收件人:is_online 为真的骑手,且订单商家在该骑手的接单半径内(users.grab_radius_km,null=不限;骑手最后上报位置取现有的位置上报数据)。半径外的不推——推了也抢不到,只会训练骑手忽略推送;
- **合并与限频**:同一骑手 60 秒内最多收一条。窗口内又来新单就合并成「附近有 N 个新单」,不要一单一条;用 Redis 记窗口(参照 auto_flow 里 maybe_run_daily_audit 的防重手法);
- 文案:单条给「商家名 → 收货区域,配送费 ¥X」(配送费是骑手最关心的);合并条给「附近有 N 个新单,最高 ¥X」。**不写"快抢""手慢无"这类话术**;
- 点击进抢单大厅并刷新;单子已被别人抢走时提示「这单已被接走,看看其他的」,不弹错误;
- 骑手下线(is_online=false)后不再收到;这是骑手自己的开关,不做"引诱上线"的推送。
技术要点:推送失败绝不阻塞下单主流程(照现有 push 的写法只记日志);push_logs 表记一条便于排查"没收到提醒";合并逻辑放 services/push.py 内部,调用方只管"这单进池了";注意 mark_order_paid 是在事务里调的,推送要放到 commit 之后发(参照 _notify_no_rider 的写法)。
前端配套(rider_app):
- 推送到位后把后台轮询彻底停掉(现在是降频 20 秒的妥协),前台保持 5 秒兜底;
- PushService 的通知点击路由到抢单大厅。
验收:e2e_rider_push.py——造一单支付成功,断言在线且半径内的骑手收到一条(用 push_logs 断言,不真发);半径外的骑手不收;60 秒内第二单合并不新增条数;自取单与自配送单不推;下线骑手不推。回归 e2e_orders + e2e_reversal_audit。
```
