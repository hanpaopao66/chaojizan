# 开发提示词 #207–#211:用户端鸿蒙原生版(ArkTS 重写)

鸿蒙在中国手机系统占 19%,连续 7 个季度超过 iOS,而鸿蒙 NEXT 之后**彻底移除
了 AOSP 兼容层,APK 装不上去** —— 现在的三个安卓包在鸿蒙 5/6 上是死的,
不是体验差一点。

拍板:**用户端用 ArkTS/ArkUI 原生重写**,不走 Flutter-on-OHOS 那条 fork。
骑手端和商家端暂不做鸿蒙(商家端的蓝牙热敏打印 + 前台常驻听单 + 扫码核销
在鸿蒙侧几乎要从零写,而那两端加起来只有几百人,可以要求用安卓机)。

## 这条路的代价,先写在前面

**没有任何代码可以复用。** 用户端 Flutter 侧 13000 行 + 共享库里 2600 行的
`api_client.dart`,一行都搬不过来。ArkTS 是另一套语言、另一套 UI 范式
(声明式但不是 Widget 树)、另一套状态管理(`@State`/`@Link`/`AppStorage`)。

**能复用的只有两样,但这两样恰恰最值钱:**

1. **服务端一行不用改。** 接口、鉴权、业务规则全部照旧,鸿蒙端只是又一个
   HTTP 客户端。这也意味着 `api_client.dart` 的方法表就是鸿蒙端要实现的清单;
2. **产品决策不用重想。** 什么该显示、什么不该猜、哪句话怎么说,
   Flutter 版里那些注释写清楚了为什么 —— 重写时照着搬**结论**,
   别重新踩一遍坑。

**工具链在开发机上。** DevEco Studio 6 + HarmonyOS SDK(API 20),
本仓库的 CI 跑不了 `.hap` 构建,`flutter analyze` 那套也管不到这个目录。
这一版的代码是**按官方文档写的、未经编译验证**,第一次打开 DevEco 时
必然要修一批类型和 API 签名 —— 这是选择盲写的必然代价,不是质量问题。

---

## 目标与边界

**这一批只做能点得动的最小闭环**,不追求和 Flutter 版功能对齐:

隐私同意 → 短信登录 → 首页(定位 + 附近商家)→ 店铺菜单 → 购物车 →
结算 → 微信支付 → 订单列表 / 详情。

**明确不做**(留到后面几批):团购券、住宿、跑腿、透明中心、拼单、
邀请、地图轨迹、明厨亮灶直播、售后与评价。

理由是这些在 Flutter 版里也是逐批长出来的,一次全铺开会让第一版永远发不出去,
而**华为激励要求 9 月 30 日前上架**——先有一个能下单的版本,比有一个全的空壳强。

### #207 工程骨架与规范定死

Stage 模型,`AppScope` + `entry` 单模块。目标 API 20(HarmonyOS 6),
兼容下探到 API 12 —— 极光推送的鸿蒙 SDK 要求 API 12+,
再往下就没有厂商推送通道了。

要定死的三件事,后面所有页面都按这个来:

1. **网络层只有一个出口**。对应 Flutter 侧的 `ApiClient`:统一 baseUrl、
   统一带 token、统一把异常翻译成中文人话、401 统一清会话。
   **不许任何页面自己 `http.createHttp()`** —— Flutter 版能做到用户端零处裸调,
   鸿蒙版不该开这个头;
2. **会话存 `preferences`**(`@kit.ArkData`),不是 `AppStorage`。
   AppStorage 是内存态,杀进程就没,而"冷启动免登录"是既有行为;
3. **页面路由用 `Navigation` + `NavPathStack`**,不用旧的 `router`。
   新工程没有历史包袱,直接上新的。

### #208 数据模型与接口清单

照着 `packages/shared/lib/src/models.dart` 和 `api_client.dart` 搬**用户端
用到的那个子集**。注意几条 Flutter 版踩过的坑,鸿蒙版别再踩一遍:

- **金额一律用「分」的整数**,不要在客户端做浮点运算。
  服务端全程是 `*_cents`,客户端一转 double 就会出现 0.1+0.2 的经典问题,
  而这是账目透明的平台,显示的数字对不上是原则问题;
- **不要在客户端另写一份中文映射**。订单状态、配送费构成的中文名
  服务端都下发(`status_label`、`fee_part_labels`、`dine_in_label`),
  客户端自己维护一份迟早分叉,而分叉的后果是三端说法不一致;
- **堂食标识、明厨亮灶标识照实显示三态**,未填报就写「未填报」,
  不要兜底成「有堂食」—— 这是总局令第 123 号的法定公示项,猜一个填上去
  就是拿平台信用给未经核实的信息背书。

### #209 隐私门与短信登录

**隐私门必须在最外层,同意之前一个网络请求都不许发。** Flutter 版就是因为
开屏页套在隐私门外面、启动即请求 `/splash`,才在 #191 返工过一次 ——
这是工信部通报和商店驳回的头号事由,鸿蒙版从第一行就摆对。

登录走短信验证码(`/auth/sms/send` + `/auth/sms/login`),
服务端已有 60 秒冷却、同号日 8 条、同 IP 日 20 条、第 3 条起滑块的防刷。
**游客可浏览**:未登录直接进首页看商家,下单时再引导登录 ——
这是 Flutter 版为苹果审核加的,鸿蒙同理,而且它本身就是对的。

### #210 首页:定位与附近商家

定位用 `@kit.LocationKit` 的 `geoLocationManager`。
权限在 `module.json5` 里声明 `ohos.permission.APPROXIMATELY_LOCATION`,
**用到时才申请、并说明用途** —— 不要在启动时一次性要一堆权限。

拿不到定位要有兜底:Flutter 版是降级到演示城市并**明说**「正在展示演示区域
的商家」,不要静默换坐标让用户以为看到的是身边的店。

商家列表接 `GET /merchants`,注意服务端 2026-08 已经把浏览半径收敛到配送上限
(`_browse_radius_m`)—— **列表里出现的每一家店都必须下得了配送单**,
客户端不要自己再传一个更大的 `radius_m`。分页用 `limit`/`offset`。

### #211 点餐主链路与微信支付

菜单、规格加料、购物车、结算(地址/时间/备注/餐具/优惠券)、下单、支付。

两条硬约束:

- **选券必须按门槛过滤并与满减比价**。服务端 `/coupons` 的 `usable`
  只判「未用未过期」不含门槛,客户端照着面额挑最大的那张会被 409 打回 ——
  Flutter 版的 #188 就是修这个,鸿蒙版直接按正确的写;
- **微信支付走鸿蒙 OpenSDK**(≥1.0.5,`@wechat/wxopensdk` 或官方 HAR)。
  拿到 prepay 参数后调起,**结果以服务端回调为准**,客户端结果只做展示。
  商户号未配置时服务端返回 503,这时明确告诉用户「支付暂不可用」并保留
  待支付订单,**不要假装成功**。
