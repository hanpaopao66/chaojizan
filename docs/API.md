# 超级赞开放接口

给两类人看：

- **商家的收银/ERP** —— 拉单、对账、接事件通知；
- **AI 助手（MCP）** —— 帮用户找店、比价、下单、查进度。

## 现在**不开**第三方用户端

开源之后自然会有人想做替代客户端。第一版明确不开这条，理由写在这里而不是
藏着：第三方用户端需要一整套 OAuth + 用户授权 + 数据最小化，而它的收益
（别人做个更好看的 App）**远小于风险** —— 一个钓鱼客户端拿走的是用户的
收货地址和手机号。等授权体系立住了再说。

---

## 一、两种凭证，两套能力

| | 商家 API Key | AI 助手令牌 |
|---|---|---|
| 长什么样 | `sz_` 开头的随机串 | JWT |
| 谁签发 | 商家在网页控制台 | 用户在 App「我的 → 设置 → AI 助手」 |
| 代表谁 | 一家店 | 一个用户 |
| 能做什么 | **只读**自己店的订单与资料 | 查询 + **创建待支付订单** |
| 能付钱吗 | 不能 | **不能** |
| 怎么吊销 | 控制台里吊销 | App 里吊销，下一次调用即失效 |

两者都用 `Authorization: Bearer <凭证>`。

### 助手令牌为什么付不了钱

「点单」意味着一个自动化程序能花用户的钱。这条线划死在服务端：
能力范围是 `server/app/security.py` 里的 `AGENT_ALLOWED`，**白名单、全匹配、
默认拒绝**。支付路径根本不在里面。

所以助手能把单创建到「待支付」为止，**付款那一下永远在用户自己的 App 里
由人按**。即使令牌泄露，对方能替你创建一张 15 分钟后自动关闭的待付单，
但花不掉你一分钱。

白名单里的写操作**只有一条** `POST /orders`。有一条测试专门钉住这个数字
（`server/tests/unit/test_agent_scope.py::Test默认拒绝::test_写操作只有一条`）——
每多一条，上面那句话就松一分。

## 二、错误怎么读

### 状态码的口径

平台对状态码的用法是固定的，接入方可以按它分支：

| 码 | 含义 | 该怎么办 |
|---|---|---|
| `400` | 请求本身不合法或有敌意（验签失败、路径穿越、回调金额对不上） | 别重试，先查自己 |
| `401` | 没登录、凭证过期、**凭证已吊销** | 重新拿凭证 |
| `403` | 身份对，但**这件事你不能做** | 别重试 —— 这是能力边界，不是临时故障 |
| `404` | 东西不存在，或不属于你 | 两者不区分说法，这是有意的 |
| `409` | 请求合法，但**当前状态不允许**（重复提交、订单已取消） | 看 `detail`，多半是竞态 |
| `413` | 上传太大 | 压缩后重试 |
| `422` | 请求合法，但**业务不接受**（参数越界、余额不够、超出配送范围） | 看 `detail` 改参数 |
| `429` | 撞限流 | 退避后重试 |
| `502` | 上游（地图、短信、支付渠道）出问题 | 可重试 |
| `503` | 该能力**没配置**（如未接入支付） | 别重试，这是部署问题 |

`403` 和 `422` 的区别值得单说：**403 是「你不能做」，422 是「这么做不行」**。
助手令牌调支付接口是 403（换个参数也没用），下单时坐标越界是 422。

### 错误体

```json
{"detail": "这家店超出配送范围(4km),换家近点的店吧"}
```

`detail` 是**给人看的中文**，不是错误码 —— 它会被原样展示给用户。
不要拿它做字符串匹配来分支，**用状态码分支**。

> 现状说明：目前只有 `detail`，没有机器可读的 `code` 字段。给整套接口
> 补机器码是一次涉及 769 处异常的改动，风险大于收益，所以没做。
> 如果你的集成需要精确分支，用「状态码 + 接口」这个组合，它是稳定的。

### 校验失败（422）的形状

FastAPI 的标准形状，`detail` 是数组：

```json
{"detail": [{"type": "less_than_equal", "loc": ["body", "lat"],
             "msg": "Input should be less than or equal to 90", "input": 999.0}]}
```

非有限浮点（`Infinity` / `NaN`）会被换成字符串再返回 —— 它们不是合法 JSON，
不换的话这条 422 自己就序列化不出去，你收到的会是一个 500。

## 三、限流

规则是公开的，和平台公开派单算法一个道理 —— 你该能预先算出自己会不会被拦。

| 场景 | 限额 |
|---|---|
| 下单 | 每用户每分钟 **20** 次 |
| 短信验证码 | 每号每分钟 **5** 条；同 IP 每日 **20** 条；同号第 3 条起要滑块 |
| 注册 | 每 IP 每分钟 **5** 次 |
| 公开页（大屏 / 透明中心） | 每 IP 每分钟 **120** 次 |
| 取号（到店排队） | 每人每分钟 **10** 次 |

> 这几个数由 `server/tests/unit/test_api_doc.py` 钉着 —— 改了配置而忘了
> 改这份文档，那条测试会红。**公开的数字对不上，比不公开更坏。**

撞到限流返回 `429`。**退避重试，不要立刻重发** —— 重发只会让窗口一直满。

## 四、商家接口 `/open/v1`

第一版**故意做窄**：只读。窄比全更容易保证不出事 —— 写操作出错的代价由
商家和顾客承担，等真实对接跑顺了再逐个开。

| 接口 | 说明 |
|---|---|
| `GET /open/v1/shop` | 我的店铺资料 |
| `GET /open/v1/orders` | 拉单（可按状态、时间筛） |

顾客隐私按**商家视角**脱敏，和商家 App 同一套口径 ——
不因为「是机器在读」就多给一位手机号。

### 用量与调用日志

控制台里能看到最近的调用量、错误率、被限流次数，以及最近若干条调用记录
（方法、路径、状态码、耗时）。

**日志里没有请求体和响应体。** 里面是顾客的收货地址、手机号、备注里的忌口
—— 为了让你好排查而把这些多存一份，是拿用户的隐私补贴开发体验。
方法 + 路径 + 状态码足够回答「我的集成为什么失败」；答不了的那部分，
复现一次比长期存着划算。

**「日志里一条都没有」是有含义的**：说明你的 Key 根本没被认出来
（打错了、或者不是这个环境的）。认得出是谁的失败会记 —— 比如
Key 被吊销、店铺被停用，这些在日志里看得见状态码 401。
完全不认识的 Key 不记，否则任何人拿垃圾请求就能把这张表撑爆。

## 五、MCP 接入

见 [`mcp-server/README.md`](../mcp-server/README.md)。七个工具：

`search_merchants` / `get_menu` / `quote_order` / `create_pending_order` /
`get_order_status` / `list_my_orders` / `get_transparency`

**没有支付工具**，两边都有守卫：服务端白名单里没有支付路径，
MCP 侧有测试扫源码钉住「不出现 /pay、/self-refund、/withdraw 这些路径」。

`quote_order`（算价不下单）单独拆出来是有意的：比价用它，
别靠反复下单再取消 —— 那会造出一串垃圾订单，商家端每一张都会响一声。

### 没有沙箱

**现在没有独立沙箱环境。** 在生产环境试 `create_pending_order` 会产生
真实的待支付订单 —— 不付款 15 分钟后自动关闭、不扣钱，但商家端会看到它闪一下。

不做沙箱是权衡的结果：独立沙箱库要维护一套数据，生产库打标一旦漏判就是真钱。
而因为没有支付工具，试用的风险已经被压到很低。

接进客户端之前先干跑：

```bash
SUPERZ_API=https://你的域名 SUPERZ_AGENT_TOKEN=xxx python3 mcp-server/server.py --selftest
```

自检**不创建订单** —— 自检不该产生真实的单。

## 六、业务口径去哪里查

**这份文档不复述业务口径。** 判责怎么分、配送费怎么算、派单怎么排、
排队怎么算，全部在透明中心，那里是唯一事实来源：

| 口径 | 地址 |
|---|---|
| 判责与分摊 | `GET /transparency/liability` |
| 派单算法（含每个权重的理由） | `GET /transparency/dispatch` |
| 排队规则 | `GET /transparency/queue` |
| 分账与佣金 | `GET /transparency/fairness` |
| 资金流向 | `GET /transparency/funds` |

**为什么不在这里抄一份**：抄的那份迟早和真实口径对不上，而那时候公开的是
假的，比不公开更坏。这条规矩在 `services/dispatch.py` 的注释里已经写过一遍
——「公开的前提是只有一份」。

这些接口**不需要登录**，MCP 的 `get_transparency` 工具也读同一份。

## 七、Webhook

商家可在控制台订阅事件。投递失败会重试，控制台里能看到最近的投递记录
和响应码，也能手动重投。

签名验证：请求头带签名，用你的 Webhook 密钥按 HMAC-SHA256 校验请求体。
**用 `compare_digest` 比较，不要用 `==`** —— 后者的耗时随匹配前缀增长，
理论上可被用来逐字节猜出签名。

> 本节的示例代码还没有对应的自动化测试覆盖，属于**未验证**内容。
> 接入时请以 `server/app/services/` 下 webhook 相关模块的实现为准。
