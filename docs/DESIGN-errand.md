# 设计:跑腿(帮送 / 帮买)怎么塞进现有订单模型

这份文档只定结构,不写代码 —— 照 `DESIGN-chain-stores.md` 的先例。
结构定错了后面全是返工,而这一次的结构问题比连锁那次更硬:
**跑腿单没有商家。**

---

## 一、问题:`Order.merchant_id` 是 NOT NULL,而且有 106 处代码依赖它

```
grep -rn "order\.merchant_id\|Order\.merchant_id" app/ | wc -l   # 106
```
分布在 20 个文件里:佣金、评价、售后、发票、税务、风控、回调、
出餐时长、清扫、开放接口……

三条路,先说为什么否掉两条。

### ❌ 方案 A:把 `merchant_id` 改成可空

最"诚实"的建模 —— 跑腿单确实没有商家。但代价是 106 处逐个审:
每个 `db.get(Merchant, order.merchant_id)` 都要判空,而**漏判一处
不会立刻报错**,它会在某条冷路径上悄悄算错一笔钱(比如佣金按 None
走了默认分支)。这类错误正是这个项目反复踩到的那种:
不崩,只是数不对。

### ❌ 方案 B:另起一张 `errand_orders` 表

隔离最干净,存量代码一行不动。但抢单池、派单打分、在途单、结算、
申诉、保障、SOS、转单**全部查 `Order`** —— 复制一套等于把骑手侧
最核心的那条链路劈成两半,以后每加一个骑手功能都要写两遍。
上一批刚因为"两份实现会分叉"把消息中心抽成了共用 service,
这里没有理由反着来。

### ✅ 方案 C:每城一个 `biz_type='errand'` 的服务主体 + 订单自带取件点

发现的关键事实:**`biz_type` 在代码里是白名单用法,不是黑名单。**

```python
# routers/merchants.py 里到处是这一句,而不是 "!= hotel"
Merchant.biz_type == "food"
```

也就是说,一个 `biz_type='errand'` 的主体**天然不会**出现在外卖列表、
搜索、首页推荐里 —— 排除机制已经存在,而且已经被现有用例覆盖过。
这比我们自己新写一堆 `if not errand` 可靠得多:
新写的每一处排除,都是一个将来会被忘记的地方。

于是:

- `merchant_id` 指向本城的「跑腿服务」主体,**非空约束不动,
  106 处代码一行不改**;
- 但**取件点不在商家身上** —— 跑腿的取件地址是用户当场填的,
  每单都不同。所以取件点作为订单自己的字段。

## 二、结构

### 订单新增字段

| 字段 | 说明 |
|---|---|
| `order_kind` | `food`(默认) / `errand_send` 帮送 / `errand_buy` 帮买 |
| `pickup_address` / `pickup_lat` / `pickup_lng` | 真实取件点(帮买时是"去哪买") |
| `pickup_contact_name` / `pickup_contact_phone` | 取件联系人(帮送:寄件人) |
| `errand_note` | 物品描述 / 要买什么 |
| `goods_budget_cents` | 帮买:用户预付的预估商品款 |
| `goods_actual_cents` | 帮买:小票上的实付金额 |
| `goods_receipt_url` | 帮买:小票照片(**唯一对账依据**) |
| `pickup_photo_url` | 帮送:取件时拍的物品照(唯一交接凭证) |

### 一个访问器,而不是散落的 if

```python
def pickup_point(order, merchant) -> PickupPoint:
    """骑手要去哪取。外卖 = 商家位置,跑腿 = 订单自带的取件点。"""
```

抢单池、地图、导航、顺路计算**全部走它** —— 现在这些地方读的是
`merchant.lat/lng`,改成读访问器。这是这个方案唯一需要改的一类调用点,
而且改错了会立刻表现成"地图指错地方",不会悄悄算错钱。

### 状态机

跑腿单**没有商家环节**:支付成功直接进抢单池,不经过
"待接单 → 已接单 → 出餐完成"。

```
外卖:  待支付 → 待接单 → 已接单 → 出餐完成 → 已取餐 → 已送达 → 已完成
跑腿:  待支付 →              待抢单 → 已取件 → 已送达 → 已完成
```

实现上复用同一套 `OrderStatus`,支付成功后直接置 `READY`
(语义是"可以取件了"),抢单池的过滤条件本来就收 `READY`。

⚠️ 要小心的是那些**假设 READY 意味着商家出餐完成**的地方:
出餐超时提醒(`_sweep_ready_timeout`)、出餐时长统计(`prep_time`)、
商家侧待办。这些都要按 `order_kind` 排除跑腿单 ——
否则商家后台会出现一堆"你有单没出餐"的幽灵待办。

## 三、钱

### 帮送

```
用户付 = 跑腿费(距离 + 时段 + 天气 + 上门难度,复用现有 pricing)
骑手拿 = 跑腿费 × 98%
平台收 = 跑腿费 × 2%(与团购券同口径,账单上明写)
```

⚠️ 这里和外卖有一处**必须说清楚的差别**:外卖的配送费是
**100% 归骑手、平台一分不抽**,而跑腿要抽 2%。两个口径同时存在,
界面上不讲清楚就会变成"你不是说配送费不抽吗"。

说法应当是:外卖里平台的收入来自商家佣金,配送费不碰;
跑腿没有商家,2% 是平台在这条业务上唯一的收入。
**在跑腿的账单上单独列出来,不藏在总价里。**

### 帮买

```
用户付 = 预估商品款 + 跑腿费
骑手拿 = 实付商品款(全额,平台不抽) + 跑腿费 × 98%
平台收 = 跑腿费 × 2%
差额   = 预估 − 实付,原路退用户
```

**商品款平台一分不抽** —— 那是骑手替用户垫付的钱(虽然钱从平台走),
对它抽成没有任何道理。

三条规则(见 DEV-PROMPTS-22.md #185):
1. 实付 < 预估 → 差额原路退;
2. 实付 > 预估 → 20% 且 ≤20 元以内,平台先结给骑手再向用户补收;
   超出上限,骑手**必须先发起确认**,用户同意才买;
3. 买不到 → 商品款全额退,跑腿费**用户只付到店那段的距离费**,
   且这条要**写在下单页**而不是藏在协议里 —— 提前说了就不叫坑。

### 结算与对账

跑腿单不进商家结算(那个主体没有 owner 收款账户)。
`settle_order` 里按 `order_kind` 分叉:跑腿只产生骑手入账行 +
平台服务费行,**不产生商家入账行**。

⚠️ 审计恒等式要同步扩展:现在是
`商家净额 + 平台佣金 + 骑手收入 = 用户实付`,
跑腿这条是 `骑手收入 + 平台服务费 + 商品款 = 用户实付`。
两条都要在 `services/audit.py` 里各自平账,
不能让跑腿单在旧恒等式下被判成"对不上"。

## 四、合规硬约束

- **帮买只做包装商品与商超日用,不做即食餐饮。**
  代购即食食品需要食品经营许可 —— 让骑手去一个没证的摊子买一份
  小笼包,就是给无证经营导流,而我们外卖那边卡证卡得很严,
  两套标准会自己打架。想吃现做的,走我们自己的外卖;
- **不做**:药品(含非处方)、烟草、酒类。烟草专卖与处方药
  各有专门法规,不是加个勾选能解决的;
- **帮送禁运清单硬编码拦截**:危险化学品、易燃易爆、活体动物、
  现金与贵重金属、管制刀具、处方药。命中直接拒单并说明原因 ——
  只写在用户协议里等于没写;
- **不做保价**。保价意味着平台承担赔付,而平台没有补贴预算。
  界面上如实写"贵重物品请勿使用本服务"。

## 五、落地顺序

1. **访问器 + `order_kind` 字段**(不含任何跑腿功能):
   把现有读 `merchant.lat/lng` 的地方改成读访问器,跑一遍回归。
   这一步是纯重构,风险最低,但它把后面所有事情的地基铺平;
2. **帮送**:下单 → 抢单 → 取件拍照 → 送达。定价复用现有;
3. **帮买**:在帮送之上加预付、小票、差额结算、买不到;
4. **商家侧幽灵待办排查**:跑一遍商家后台,确认跑腿单
   没有渗进"待出餐""今日营业额""出餐时长"里。

⚠️ 第 4 步不是收尾,是**必须单独排**的一步。跑腿单复用了 `Order` 表,
凡是"统计所有订单"的地方都会把它算进去 —— 商家看到自己的营业额
凭空多出一截,是这个方案最容易出的错。

## 执行记录(实现完成后回填)

结构按上面的方案落地了,`Order.merchant_id` 一行没改。实现中定死或变化的几点:

### 帮买的加价上限:20% 且 ≤20 元

设计时只写了"设一个浮动上限",实现时定为 `RAISE_RATIO=0.20` +
`RAISE_MAX_CENTS=2000`。两个数一起用是因为单独用任何一个都不对:
只用比例,买一台两千块的东西超支 400 元也算"在上限内";
只用绝对值,买十块钱的东西超 20 元等于翻三倍。

这两个数存在的意义是**让骑手在店里只需要看一眼**:超了就点确认,
不超就直接买。没有明确上限的话,他每次都要自己判断"这点差价要不要打扰顾客",
而那个判断题本来就不该由他来做。

### ⚠️ 补收目前只落账,不真的收钱

实付超过预估时,`food_cents` / `total_cents` 会上调,账面上看得见,
**但没有真的向用户收到这笔钱** —— 微信支付商户号还没下来,
没有可用的补收通道。

这一条**上线前必须接上**,否则每一单超支都是平台在垫。
代码里(routers/errands.py 的 submit_receipt)写了同样的警告。

发现它的过程值得记:审计的跑腿恒等式当场把它抓出来了 ——
「骑手入账 5294 + 服务费 6 ≠ 用户实付 3300」。
`settle_goods` 早就把差额算出来了,但**没有任何调用方执行它**,
和等餐补偿那次是同一类错:写完函数没接线,和没写是一回事。

### 买不到只收 base

`unavailable_fee_cents` 只取拆分里的 `base`(到店那段的距离费),
夜间/天气/上门难度都不收 —— 上门那一段根本没发生。

### 第 4 步的验证做进了 e2e 而不是单独一轮排查

`e2e_errand_send` 里直接断言:跑腿单不进真实商家的订单列表、
状态流里没有「商家已接单」。比事后人工翻一遍可靠,而且以后不会退化。

### ⚠️ 第 4 步真抓到一个:无骑手兜底把跑腿单当成「商家已出餐」赔了钱

上面那句「验证做进了 e2e」当时说早了。真正的漏网之鱼不在商家界面里,
而在一个**不按商家过滤、直接扫全表**的后台清扫里:

```python
# _sweep_no_rider
if from_status == OrderStatus.READY:      # 商家已出餐 → 平台赔餐损
```

这句对外卖是对的。但跑腿单**支付后直接进 READY**(语义是"可以取件了"),
然后一直躺在池子里等骑手 —— 没人抢就掉进这个分支。
`merchant_id` 指向的是虚拟服务主体:没有经营者、没有厨房、没做任何东西。
帮买单更糟,那笔 `food_cents` 装的是**用户预付的商品款**,
赔出去等于同一笔钱付两遍(用户已全额退款)。复现出来是
`('earning', 3000, '无骑手接单取消,平台赔付餐损')`。

`services/errand.py` 的 docstring 里明写着"结算里对跑腿单不生成 MerchantEarning",
那句话在 `settlement.py` 里是真的 —— 但这条清扫路径绕过结算自己写入账行。
**同一条规则写在两个地方,总有一个不知道例外。** 这个项目已经栽过几次
(等餐补偿、新手阈值),这次是第三次。

顺带修了推送:虚拟主体的 owner 挂平台管理员,不修的话管理员会收到
一堆「你有单没出餐」——正是第 4 步预警的那种幽灵待办,只是它出现在推送里
而不是待办列表里。

### ⚠️ 服务端全通,但骑手在 App 里根本做不完一单

第 4 步收尾时按方法名扫了一遍「谁调用了谁」,结果是:

| 接口 | 服务端 | e2e | 有界面调 |
|---|---|---|---|
| `uploadPickupPhoto` 取件拍照 | ✓ | ✓ | **没有** |
| `requestRaise` 骑手发起加价 | ✓ | ✓ | **没有** |
| `decideRaise` 用户回应加价 | ✓ | ✓ | **没有** |

后果不是"少个功能",是**流程断在半路**:骑手在超市里发现要多花钱,
提交小票被服务端 409 挡回来、提示写着"先问顾客",而他手上并没有"问"
这个按钮 —— 小票交不了,加价发不出,这一单卡死在收银台前。
就算他发得出去,用户端也没有同意/拒绝的入口,单子会一直挂着。

**e2e 全绿掩盖了这件事**,因为 e2e 测的是服务端,它按顺序调三个接口
当然能跑通。写完接口没接线,和没写是一回事 —— 这是同一个毛病的第四次。

接的时候有一条要守住:**加价上限不在客户端算**。让服务端拒绝,
客户端只把那个 409 变成一个可点的入口。同一条规则在两边各实现一遍,
迟早分叉,而分叉那天没人会发现。

### 剔除一类订单,就必须补一条「它确实没有」的检查

这个 bug 之所以躲过账务自检,是因为菜品侧恒等式里有一句
`not is_errand(o)` —— 跑腿单没有商家入账,留在那条恒等式里必然不平,
所以剔除本身是对的。但剔除的**副作用**是:跑腿单上出现的任何商家入账行,
金额多离谱都在视野之外。

补了 `errand_merchant_earning` 检查,直接扫「跑腿单上净额非零的商家入账」。
以后不管哪条路径再写进去,自检当场报出来,不用等谁想起来去看。

### 「虚拟主体」这个方案的代价,集中在用户界面上

结构上它省掉了 106 处判空,这笔账是划算的。但它有一类固定的代价:
**凡是"对着 merchant 做点什么"的界面,跑腿单都会带出一个空壳入口。**
这一轮扫出四处:

- 用户端「再来一单」把跑腿单也收进去,点开是虚拟主体的空菜单
  (而且"再来一单"对跑腿本来就不成立 —— 上次寄的和这次要寄的没关系);
- 订单详情的「联系商家」按钮,点进去是跟一个没有人的账号聊天;
- 评价卡让人给「本城跑腿服务」打星,星级还真累加进了它的评分;
- 差评(≤3 星)触达会把「你收到一条差评」推给平台管理员 ——
  因为虚拟主体的 owner 挂的是他。

前两处在客户端挡掉,后两处**在服务端挡**:客户端挡了只管新版本,
老版本的 App 和任何 API 调用方还是会把星级写进去。

这类问题不会自己冒出来,只能按「哪些界面读 merchant」逐个过。
以后再往这个结构上加东西,这一步要单独排一次。

同一类的第五处在骑手端:「取餐核验」弹窗要骑手输**小票上单号的后 4 位**,
而跑腿没有商家也没有小票。服务端对不传码是放行的,所以骑手留空也能过 ——
但界面明晃晃写着"输小票上单号的后 4 位",他多半会去点
「核验不了?强制取餐(会记录)」,于是每一单跑腿取件都在事件流里留一条
「强制取餐(未通过尾号核验)」。那条记录是给「拿错别人的餐」追溯用的,
被跑腿单填满就废了。跑腿改成直接取件,e2e 里断言事件流不含这条痕迹。

**这五处的共同点**:界面本身没报错、没崩、analyze 和 e2e 全绿,
只是对着一个不存在的对象做了一件没有意义的事。
虚拟主体方案的账要这么算:省下 106 处判空,换来一份「凡是碰 merchant
的界面都要过一遍」的清单 —— 这笔账仍然划算,但那份清单是必须还的。

### 一个被审计救回来的开发库清理

补收实现之前跑出来的 26 张帮买单账面不平(骑手按小票拿钱、
用户还按预估付钱)。这些单让 `e2e_support_audit` 的
「补账后自检零问题」变红 —— **没有去放宽那条断言**,
而是按修好的规则把数据补正。生产上跑腿还没上线,不存在这类单。
