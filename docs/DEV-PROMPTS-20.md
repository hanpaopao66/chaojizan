# 开发提示词 #160–#164:菜品一键导入与兼职骑手

调研完这两件事,结论都和"一键接入"这个说法不太一样 ——
**一个是接不了(法律上),一个是压根不用接(本来就通)。**

---

## 结论一:菜品导入没有"接入"这条路,只有"商家自己导出"

| 路子 | 能不能走 | 为什么 |
|---|---|---|
| 抓取美团/饿了么页面 | ❌ | 不正当竞争,有判例 |
| 对接对方开放平台 API | ❌ | 需要对方授权,竞品不会给 |
| 代商家登录去抓 | ❌❌ | 要商家交账号密码,风险还转嫁给商家 |
| **商家自己导出 → 我们解析** | ✅ | 唯一干净的路,而且已核实可行 |

### 抓取这条路为什么堵死

**大众点评诉百度案**:百度地图、百度知道大量复制大众点评的用户评价,
法院判赔经济损失 300 万 + 合理开支 23 万。

裁判要点有两条,都对我们不利:

1. **「最小必要」**:使用他人数据应采取对数据持有者损害最小的方式;
2. **「实质性替代」**:抓取后的展示如果构成对原服务的实质性替代,即为不正当。

我们要抓的是**商家的完整菜单(名称/价格/图片/分类)** ——
这正是外卖平台最核心的商品数据,抓来直接建店,「实质性替代」几乎是板上钉钉。

### 代商家登录更糟,而且是原则问题

有一种做法是让商家填美团账号密码,我们代他登录抓菜单。**不做。**

- 违反对方服务协议,商家的账号可能被封 —— **风险落在商家头上,不是我们头上**;
- 我们会拿到商家在别家平台的账号密码。这个项目连用户手机号都上了隐私中间号,
  不可能反过来去收集商家在竞品的凭据;
- 全局安全约定里,收集他人平台的账号口令是明确禁止的。

### 但商家导出自己的数据,是他的权利

**已核实**:美团商家版后台有「下载管理 → 下载商品」,商家可以导出自己的商品清单。

法律上也站得住:「二选一」已被认定为滥用市场支配地位
(阿里 2021 年被罚 182.28 亿、美团 2021 年被罚 34.42 亿)。
商家多平台经营是受保护的,导出自己的经营数据是这件事的应有之义。

**关键区别**:我们不碰对方系统,数据是商家自己交给我们的。

## 结论二:骑手不需要"接入" —— 众包骑手本来就能两边跑

**已核实**:众包骑手**没有排他限制**,多平台跑单是常态
(专送骑手才有排他,他们由加盟商/代理商招募、不能拒单)。

所以「让美团骑手能接我们的单」在技术上不是个问题 ——
**他下载我们的 App 注册就行了,今天就可以。**

### 真问题是另外两个

1. **他为什么要装第三个 App;**
2. **他打开一看 0 单,还会不会有第二次。**

这是冷启动和密度问题,不是接入问题。用技术手段解决不了,
但**产品设计可以解决一部分** —— 见 #162。

### 有一种"接入"必须明确不做

做一个聚合工具,帮骑手同时看美团/饿了么/我们的单。这需要抓取或自动化操作
竞品 App —— 法律风险同上,但更要命的是:

**被封号的是骑手的账号,不是我们的。**

他在美团跑了两年、有稳定收入,因为装了我们的工具被封,损失是他的。
这个项目把「不用算法困住人」写进了公开承诺,**不能反手让骑手替我们承担风险**。

### 160. 菜品导入:三条通道,按数据质量排序

```
## 不要只做"从美团导" —— 那是在服务已经在美团的商家

三条通道,优先级从高到低:

**① 收银系统导出(数据最干净,优先做)**

商家如果在用客如云/哗啦啦/二维火这类收银,商品数据本来就在他自己手里,
格式规范、分类清楚、规格完整。比从平台后台导出的表格干净得多。

**② 平台后台导出的表格(覆盖面最广)**

- 美团:商家版后台「下载管理 → 下载商品」(**已核实存在**);
- 饿了么、京东到家:**需要实测一遍再写文档**,不要照抄美团的路径去教商家 ——
  教错了他找不到,这一步就断了。

**③ 拍菜单 OCR(这条才是增量)**

前两条服务的是**已经在美团开店**的商家。而夫妻店、新店、只做堂食想试试外卖的,
根本没有可导出的东西 —— 他有的是一张纸质菜单或者一块价目板。

OCR 这条通道对我们的意义更大:它不依赖任何竞品,而且服务的是别人不服务的人。

技术上用 PaddleOCR 自部署(开源,无调用费),或国内通用 OCR 的免费额度。
**平台无补贴预算,不要选按次计费的方案。**

## 核心设计:列映射,不要写死表头

各家的导出表头完全不同,而且**会变** —— 写死一套字段名,对方改版就全挂。

做法:
1. 读表头 → 猜测映射(名称/价格/分类/描述/图片),给出默认;
2. **让商家看一眼映射结果再确认** —— 「我们把「商品名称」认成了菜名,对吗」;
3. 预览前 5 条解析结果,确认无误才写库。

猜错不可怕,不给他改的机会才可怕。

## 图片:必须正面处理,不能默默盗链

导出表里的图片通常是**指向美团 CDN 的 URL**。直接拿来用有两个问题:

1. **防盗链**:多半根本加载不出来,商家的店就成了一片破图;
2. **版权**:美团有「拍店」服务,那些图可能是美团出钱拍的,权利不在商家手里。

所以:
- **不做自动搬图。** 导入时把图片列的 URL 显示出来,告诉商家
  「这些图在对方平台上,我们不会替你搬过来 —— 版权可能不在你手里,
  而且大概率也加载不出来」;
- 提供批量上传入口,让他重传;
- 没图的菜先用品类占位图(已有 category_photo),不留空白。

**宁可让商家多传一次图,也不给他一个可能侵权的默认。**

## 规格与加料(options)先做扁平

各家的规格格式差异极大(美团的「规格/属性」、饿了么的「多规格」、
收银系统的「做法/加料」)。**第一版只导名称、价格、分类、描述。**

带规格的菜导入后标注「这道菜在原平台有规格,需要你补一下」,
给一个直达编辑页的入口。做不好的映射不如不做 —— 价格算错比没导入更糟。

## 明确不做的

- 不抓取、不代登录、不接对方 API;
- 不做"同步"(双向或单向持续同步)。同步意味着我们要持续读对方系统,
  那就绕回抓取了。**只做一次性导入。**
```

### 161. 导入的真正门槛是信任,不是技术

```
## 商家心里的问题是「你拿我菜单干嘛」

一个还在观望的商家,把完整菜单交给一个新平台 —— 他会想:
你会不会拿去分析我的定价?会不会给我的同行看?会不会我不用了你还留着?

**这个顾虑是合理的,而且技术做得再好也绕不过去。**

## 所以要明说,并且写进可验证的地方

导入页面上直接写清楚三条:

1. **导入的数据只用于建你自己的店** —— 不做行业价格分析、不做品类报告;
2. **不给任何第三方看**,包括其他商家;
3. **你随时可以全部删掉**,删了就是删了(复用已有的账号删除那套口径)。

然后把这三条放进 `/transparency`,和佣金、派单算法一样可查。

## 这一条不是文案工作

写了做不到就是假承诺。所以配套要有:

- 导入的原始文件**不长期留存**(解析完就删,或者最多留 7 天供商家复查);
- 导入记录里不存"这家店卖什么价"这种可聚合的横向数据表;
- 谁访问过导入数据要有审计(已有 audit 那套)。
```

### 162. 兼职骑手:不争夺他的时间,只争夺他的顺路

```
## 我们和美团抢骑手是抢不过的,也不该抢

美团单量密度是我们的几百倍。一个骑手要"专职跑超级赞"是不现实的,
让他这么做也是不负责任 —— 他会没饭吃。

**所以目标不是让他来跑我们,是让他在跑美团的路上顺手带我们一单。**

这恰恰是我们已有设计的强项:

- `dispatch.py` 已经有顺路撮合(same_way / detour_m,#140);
- 我们**不要求在线时长、不要求接单率、没有服务分**(#144/#147 已公开承诺);
- 配送费与小费 100% 归骑手。

美团众包要他保持在线、看接单率;我们什么都不要求。
**对一个"顺路多挣一单"的人来说,我们的规则本来就是最合适的那个。**

## 要解决的头号问题:打开看到 0 单

这是冷启动阶段最致命的一件事。他打开一次是 0 单、两次是 0 单,
第三次就不会再打开了 —— 而且他会告诉别的骑手"那个平台没单"。

**做法:不让他打开看,有顺路单才通知他。**

1. 骑手设一条常跑路线或常驻区域(**不是上传实时位置** ——
   他没在跑我们的单时,我们不需要知道他在哪);
2. 有单落在他设的区域里,推送一条:「XX 路有一单,取餐 800 米,
   送 2.1 公里,¥7.5」——**一条推送要包含够他决策的全部信息**,
   点开再看是浪费他的时间;
3. 他不接,不记录、不影响任何事(我们本来就没有接单率)。

## 第二个:区域没单就说没单

他真打开了而当前没单,**直接说「你这片现在没有单,别在这儿等」**。

这很反直觉 —— 常规做法是想办法留住他。但留住一个白等的骑手,
就是在偷他的时间,而他迟早会发现。

顺带给一句有用的:「这片过去一周的下单高峰是 11:30–12:30」
(数据来自 #149 那套聚合,给信息不给指令)。

## 第三个:第一单的信任

新骑手最怕的是"跑完了钱拿不到"。所以第一单要:

- 抢单前就把「这单你能拿多少」算清楚显示(已有 trip_economics);
- 送达后**立刻**入账可见(已有);
- 首单完成后主动推一条:「¥7.5 已入账,可随时提现」——
  **不是营销推送,是兑现承诺的证据**。

## 明确不做的

- **不做兼职骑手等级/任务/冲单奖**。那是评分体系和烧钱玩法,两条都违背既定立场;
- **不做"多平台聚合抢单"工具** —— 封号风险落在骑手头上;
- **不问他在哪个平台跑**。这是他的事,问了也没用,还显得我们要管他。
```

### 163. 顺手拆掉一道我们自己加的门槛:健康证

```
## 这一条有法规依据,而且是实打实的降门槛

现在骑手入驻要传健康证(RiderProfile.health_cert_photo_url)。
调研发现:**国家层面并不要求送餐员持健康证。**

依据是《网络餐饮服务食品安全监督管理办法》的口径:要求餐食封装、
**避免送餐人员直接接触食品** —— 因此送餐员不属于"直接接触入口食品的人员",
不在预防性健康检查的范围内。

**四川省已明确取消对外卖员健康证的要求**(我们在成都)。
但平台的规则没跟着变,骑手照旧要花钱、跑一趟、等出证。

## 这不是放松标准,是不再要求一个法律没要求的东西

对我们的意义很直接:一个想顺手跑一单的兼职骑手,
现在要为此专门去办一张证 —— 大部分人到这一步就走了。

## 但不能一刀切

杭州等地有地方性的网络餐饮配送监管办法,可能有额外要求。
所以:**按城市判断**,复用已有的 city 字段与开城清单:

- 默认不要求(依据国家口径);
- 城市清单里可以标注"本市要求健康证",该市骑手仍需上传;
- 界面上写清楚为什么 ——「你所在的城市不要求送餐员健康证,
  我们也就不要求。这是法规口径,不是我们放松了标准」。

## 培训考试保留,但要能三分钟做完

上岗培训(80 分通过)是安全相关的,保留。
但对兼职骑手要能**三分钟内做完**:食安封签、交通安全、异常处置,
考完立刻能接单。

现在的门槛结构要重新过一遍:哪些是安全底线(留),
哪些是我们跟着行业惯性加的(去掉)。
```

### 164. 导入不该只服务"从别处搬过来"的商家

```
## 一个容易走偏的地方

「一键导入」听起来是在抢美团的商家。但真正能被我们抢过来的,
是那些**已经在美团亏钱、想找条活路**的商家 —— 他们本来就在观望。

而导入功能对他们的价值不在于省了两小时录入,
在于**降低"试一下"的心理成本**:菜单十分钟就搬完了,不行再撤,损失不大。

所以导入完成后那一屏很关键,不要写"导入成功,共 42 道菜",要写:

- 你的店已经能接单了(直接给预览链接);
- 还差什么(图片 3 道菜没有、2 道菜有规格要补);
- **随时可以撤**(这句要写出来 —— 降低试错成本才是这个功能的真价值)。

## 顺带:也给纸质菜单一条路

OCR 那条通道(#160 的③)服务的是**从来没开过外卖**的店。
这类店的老板往往连"商品分类"是什么都要想一下 ——
导入完成后要有个简单的整理步骤,而不是把 40 道菜平铺给他。
```

---

## 明确不做的(整批)

- **抓取竞品平台数据**:大众点评诉百度已有判例,「实质性替代」这一条我们必踩;
- **代商家登录竞品后台**:要商家交账号密码,风险还转嫁给商家;
- **持续同步**:同步意味着持续读对方系统,绕回抓取。只做一次性导入;
- **自动搬运竞品 CDN 上的图片**:防盗链会挂,版权多半也不在商家手里;
- **多平台聚合抢单工具**:封号风险落在骑手头上;
- **兼职骑手等级 / 冲单奖 / 任务体系**:评分体系 + 烧钱,两条都违背既定立场。

---

## 建议顺序

1. **#163 拆健康证门槛** —— 最小的改动、最直接的效果,而且有法规依据。
   先做这个,因为它不依赖任何别的东西;
2. **#160 + #161 菜品导入** —— 一起做。#161 不是文案,是 #160 能不能被信任的前提;
3. **#162 兼职骑手顺路推送** —— 依赖 #140 已有的顺路逻辑,改动不大,
   但要先想清楚"常驻区域"怎么设才不变成位置追踪;
4. **#164** —— 跟着 #160 一起收尾。

⚠️ 两处要先落实再动手:

- **饿了么/京东到家的导出路径没实测过。** 不要照抄美团的说明去教商家,
  教错了这一步就断了;
- **健康证的地方性要求要逐城市确认。** 成都可以去掉,别的城市要单独查。

## 执行记录:#165–#167(骑手入驻门槛)

### 调研结论:不需要人脸,但**培训是法定的**

问题是「商业性外卖只要姓名+身份证号就能接单吧」。核完法规,答案是**不是** ——
少了一条,而且是有罚则的那条。

| 项 | 要不要 | 依据 |
|---|---|---|
| 姓名 + 身份证号(二要素核验) | ✅ | 可追溯;法规鼓励用人口库而非人脸 |
| **食品安全培训 + 记录存 2 年** | ✅ | **123 号令第 28/29 条,罚则第四十四条** |
| 健康证 | ❌ | 送餐员不属于"直接接触入口食品的人员";四川已取消 |
| 人脸认证 | ❌ | 有其他方式时**不得**作为唯一验证方式 |
| 年满 18 周岁 | ✅ | 劳动法 |

**人脸这条的依据值得单独记**:《人脸识别技术应用安全管理办法》
(网信办+公安部,2025-06-01 施行)原文 ——

> 若实现相同目的或达到同等业务要求,存在其他非人脸识别技术方式的,
> **不得将人脸识别技术作为唯一验证方式**。
> 鼓励优先使用国家人口基础信息库……**以减少人脸信息的收集与存储**。

所以把人脸做成注册门槛不只是没必要,是**违反**这条办法。

**培训这条的依据**(总局令第 123 号,已核对中国政府网公报原文):

> 第二十九条 网络餐饮服务经营者委托开展配送业务的……
> **受托方应当对配送人员进行食品安全培训、管理,培训记录保存期限不得少于二年。**

商家把配送委托给平台,平台就是"受托方"。

### 改之前发现的三个现存问题

**① 骑手实名根本没在核验。** `services/idcheck.py` 早就写好了完整的二要素核验,
但 riders.py 提交认证时**压根没调它** —— 只是存下姓名、证号、身份证照片,
置 pending,等管理员看照片审批。人工看照片判断不了真伪,而二要素查的是公安库。
**这套既慢又不准。**

**② 用户侧早就做对了,骑手侧没跟上。** `/auth/verify-identity`(买酒用)是
本地校验位 → 二要素核验 → **证号 Fernet 加密落库,明文不入库不出接口,不存照片**。
而 `RiderProfile.id_card_no` 是**明文 18 位落库**,还存身份证照片,
并且 `RiderProfileOut` 把证号和照片 URL **直接出接口**。同一个项目两套标准。

**③ 真正的门槛是"等审批"。** 二要素几秒钟出结果,走通了当场就能接单。

### 做了什么

- 实名改为**当场核验当场生效**:本地校验位 → 18 岁 → 二要素 → approved。
  核验服务挂了**返回 503 而不是放行** —— 放行等于没有实名;
- 证号 **Fernet 加密落库**,迁移里把存量 44 条就地加密后**删掉明文列**

  一个列表接口不该批量吐出几百个身份证号;
- 培训从「考试」改成「培训」:新增 `rider_training.json`(4 节 / 3 分钟,

  证明不了培训了什么;
- 上线卡点从「默认关」改为**默认必需**,但用 `rider_training_grace_until`
  给存量骑手一个宽限窗口:窗口内放行 + 提醒,**不挡他上线** ——
  挡了就是让他今天没饭吃。宽限日期**写错也不放行**(配置错误不该让
  合规卡点形同虚设)。

认证页专门放了一块「我们不要的东西」:不要身份证照片、不要人脸、不要健康证,

或者以为后面还有一步。

培训页同理:第一屏就写"这是监管对平台的要求,不是平台给你加的规矩"。

### 顺带发现并修掉一个把责任判反的 bug(民宿线)

回归第二次红在 `e2e_stays_aftersale`,和骑手这批无关,但**是个真 bug**:

`_sweep_stays` 里「判未入住」跑在「售后自动成立」**之前**。后果是:

1. 客人提「到店无房」售后 —— 他没入住恰恰是因为**商家没房**;
2. 清扫先把这单判成 `noshow`,而 noshow 分支会**扣他首晚房费归商家** ——
   **商家的过失让客人买单,方向完全反了**;
3. 紧接着售后自动成立要把订单改成 `cancelled`,撞上状态机
   (未入住 → 已取消不是合法转换)抛异常,**整轮清扫就地中断** ——
   后面所有订单的退款、离店结算全都不执行。

第 3 条最要命:**一笔卡不住的售后能让当轮所有人拿不到钱**,而且悄无声息。

修了两处:

- 判 noshow 时**排除有挂起售后的订单** —— 先把投诉处理掉再谈未入住;
- 单条售后失败 `continue` 而不是让整轮挂掉,但**记 `logger.exception`**,
  不静默吞掉。

三条单测钉住(含"未入住→已取消不是合法转换"这个前提本身)。

这个 bug 是被我自己踩出来的:前面验明厨亮灶时有几次重启服务**忘了带
`AUTO_FLOW_ENABLED=false`**,后台清扫跑了一遍,把陈旧的住宿单判成了 noshow,
才暴露出这条路径。Makefile 的注释里本来就写了这个前置条件,是我没照做。

### 三个测试跟着改了语义,不是"改到绿"

改完跑回归又红了两次,两次都**不是产品 bug,是测试在验旧语义**:

- `e2e_rider_onboarding` 整套建立在 `rider_exam_required` 开关 +「10 题 80 分」
  之上。开关已经没有了(培训是法定必需,不存在"要不要强制"),
  所以按新语义重写:宽限窗口放行+提醒 / 过期硬卡 / 答错有讲解可重来。

顺带把 `rider_exam_required` 从平台开关白名单里删了,换成
`rider_training_grace_until` —— 留一个"要不要合规"的开关本身就是错的。

### 还修了一个会随回归增长而恶化的测试脆弱点

`e2e_referral` 在整轮回归里挂(单独跑绿):`rewarded` 该是 1,实际 0。

原因不是奖励逻辑坏了 —— 是 `referrals.py` 里那句
`if order.risk_flags.get("hits"): return`(风控命中的单不触发奖励,设计如此)。
而 `unique_spot()` 从 900 格里随机选,整轮回归会在同一片网格里落几百单,
两小时内 306 单命中 `addr_freq`(同格 24h ≥4 单且 ≥2 账号)。

**这个用例的成败被押在"别的用例用了哪几格"上。** 而且回归用例越多越容易挂。

修法:给 `unique_spot` 加 `band` 参数,让必须"不被风控标记"的用例走一条
与默认网格不相交的独占带。`e2e_risk` 同一个毛病(它要验"第几单才触发标记",
必须从干净格子开始数),给了 band=2。

**这里的几何比看起来紧**:两个约束方向相反 ——
① 要和默认网格不相交;② 每一格都得留在 4km 配送半径内。
踩过两次:先往北挪 5.5km(出半径,订单被"超出配送范围"拒 ——
那不是避开风控,是把用例改挂了),再往南挪两格也出半径。
最后是南移一格 + 逐条向西挪经度。实测三条带互不相交、最远角 3.7km 内。

### 追一个"测试又挂了"追出来的会计 bug

`e2e_finance` 反复挂在「明细合计 ≠ 日汇总」。前一次我以为是读顺序的时序问题
(先读明细后读汇总,中间落一条入账就对不上),改成"汇总→明细→汇总、
两次汇总一致才断言"。**这个改动本身是对的,但它把真正的 bug 露出来了** ——
两次汇总一致,明细却还是多 ¥30。

查库对了一遍真值:

| | 行数 | 净额合计 |
|---|---|---|
| 库里真实 | 1030 | 1,649,352 |
| 日汇总接口 | — | 1,649,352 ✓ |
| **翻页明细** | **1029** | **1,652,352 ✗** |

`/merchants/me/finance/orders` 按 `(created_at DESC, id DESC)` **两列**排序,
游标却只带 `created_at` 并用严格 `<`。**页边界落在同一秒的多行中间时,
这一秒剩下的行会被整组跳过。** 演示库一天 1030 行里同秒最多 9 行,
翻页只取到 1029 行 —— 漏掉的恰好是一条 **-¥30 的冲账**。

于是:**商家看到的对账明细比他实际到手的钱多 ¥30。**
而「每一单的账都可查」是这个平台写在承诺里的东西。

修成标准 keyset 分页(游标带全排序键):

```
WHERE created_at < :cursor
   OR (created_at = :cursor AND id < :before_id)
```

`FinanceOrderOut` 加 `id`,客户端 `financeOrders(before:, beforeId:)` 一起传。
老调用方只传时间时退化为原行为(不会更糟)。实测:1030 行、合计与汇总分毫不差。

测试里顺带钉了一条**行数唯一性** —— 只验金额的话,
"漏一条正的又漏一条负的"能互相抵消,照样绿。

## 执行记录:#168 订单信息法定留存

### 查出来的:送达时间根本没有落点

123 号令**第十五条**:平台应当如实记录并保存订单信息(含食品名称、下单时间、
**送餐人员、送达时间**、收货地址),**保存时间自交易完成之日起不少于三年**。

注意这比旧规(36 号令的六个月)长得多 —— 旧口径下写的任何"清理历史订单"
的想法,现在都是违规的。

逐项核过:

| 法定项 | 落点 | 结论 |
|---|---|---|
| 食品名称 | `orders.items` | ✓ |
| 下单时间 | `orders.created_at` | ✓ |
| 送餐人员 | `orders.rider_id` | ✓ |
| **送达时间** | **没有** | **✗** |
| 收货地址 | `orders.address` | ✓ |

`orders` 有 `accepted_at` 却没有 `delivered_at`。送达时间只能从
`order_events` 的状态流转事件推,而那不够:

1. 事件表是流水,查一单的送达时间要 join + 过滤;
2. **直接落库的订单没有对应事件** —— 实测 35042 单已送达/完成,
   `delivered` 事件只有 **2055** 条。

**法定要记录的字段就该有自己的列。**

### 做了什么

- `orders` 加 `delivered_at` / `completed_at`,`/transition` 与清扫任务
  两条路径都落时间(只改一条的话,自动完成的单照样没有);
- 迁移回填:先按 `order_events` 精确回填,剩下的用 `updated_at` 兜底。
  兜底是估算,但**监管调取时"这单什么时候送到的"答不上来比答近似值更糟**;
  真实产生的新单走 `/transition`,是精确的;
- 回填后 35042/35042 单都有送达时间。

### 留存本身:什么都不用改,但要钉住

全仓扫过,**没有任何地方删订单**;注销账号是把用户匿名化
(个保法第四十七条把"法律、行政法规规定的保存期限未届满"列为删除义务的例外)。

所以这一条现状就是合规的 —— 但加了四条单测钉住它,
**给未来想加"清理历史订单"的人看**:三年内删一条都是违规。

## 执行记录:存量骑手过渡

### 做的是"通知 + 设窗口",不是"给他们补一条记录"

培训记录是**法定记录**(第二十九条,保存不少于二年,监管可以调取)。
给没培训过的人补一条"已通过",是在伪造一份随时可能被查的合规记录 ——
**一旦查出来,面对的不是「没培训」的处罚,而是「造假」。**

(开发库里那 484 条 `content_version='seed'` 的记录是测试基础设施,
那些骑手都是 e2e 造出来的,不是真人。生产上不能这么干。)

### 新增 `POST /admin/riders/training-rollout`

- `dry_run: true` —— 先看影响面有多大,不推送;
- `grace_until: "2026-08-15"` —— 设窗口 + 通知全体未完成的骑手,
  窗口内照常上线但每次带提醒;
- `grace_until: ""` —— **立即生效**,没做培训的下次上线就被拦。

推送话术是「这是监管对平台的要求,不是给你加的规矩 —— 三分钟」。
立即生效在合规上最干净,但会让一批骑手当天跑不了单,窗口给多久由调用方定。

日期写错返回 422;而运行时 `_parse_grace` 解析失败一律硬卡 ——
**配置错误不该让合规卡点形同虚设。**

### 还没做

- **异常触发的人脸核身**:二要素只证明"姓名+证号真实且匹配",
  不证明"拿手机的人就是他",账号出租防不住。留到有真实骑手规模后,
  按设备突变/跨城跳跃触发,且**必须提供人工审核作为替代**
  (办法明文禁止"唯一验证方式");
- **健康证的地方性要求**:成都可以去掉,杭州等地有地方规章需逐城市确认。
  当前是全局选填,城市级判断还没做;
- 订单信息保存期限:第十五条要求**不少于三年**(旧规是 6 个月),
  我们现在存多久需要单独核一遍。

## 执行记录:#169–#171 收货地址对齐

### #169 智能识别(粘贴一段文字自动拆栏)

用户的地址往往已经存在于别处 —— 微信里同事发的、上一个平台复制的、
快递单上抄的。**让他对着现成的文字重新手打一遍是在制造错误**:
打错一个数字,骑手就打不通电话。

新增 `POST /addresses/parse`,纯本地正则。**不外发**:这段文本里有姓名和
手机号,送去第三方解析等于把用户的个人信息交出去;顺带也不花按次计费的钱。

写的时候踩了两个坑,都留在测试里:

1. `_ADDR_HINT` 第一版把「大厦」「广场」「小区」「花园」塞进**字符类**,
   于是「大」「小」「广」「花」「园」都成了单字地址特征词 ——
   **「大雄」「小明」「花花」这类常见人名全被判成地址**。
   (主流平台的官方示例正好是「大雄」,一测就露馅);
2. 试过从开头切人名(`王小明北京市…`),结果「上海」「成都」被当成人名。
   **开头的汉字压倒性地更可能是省市名,那个方向天然赢不了** ——
   改为只从末尾兜底(中文地址的书写习惯是地址在前、人名在后)。

### #170 地图选点页的周边地点列表

光给一个图钉 + 反查出来的一行地址,用户很难确认"这就是我家" ——
反查给的往往是路名,而他要的是「XX 小区 10 号楼」。

新增 `GET /geo/around`。**复用逆地理编码的 `get_poi=1`**,
腾讯会一并返回周边 POI 与距离,不用再打一次周边搜索 ——
少一次调用就少一份配额和延迟。

客户端:`MapPickerPage` 加一个可选的 `onAround` 注入点。
不注入时退化为原来的「一行反查地址 + 确认」,页面照常可用 ——
**shared 不该假定每个宿主都要这个列表**。

选中列表里的地点时用**它的坐标**(那是这栋楼的准确位置);
没选就用图钉 —— 用户拖到自家单元门口,不该被吸附到几十米外的大门。

### #171 「距离最近」+ 按距离排序

两件事**故意分开**:

- **排序**:默认地址永远排最前 —— 用户特意设过「默认」,
  那是他的明确意愿,不该被算出来的距离盖过去;
- **「距离最近」标签**:标在**真的最近**的那个上,而不是排序后的第一个。

合成一件事的话,要么默认地址被挤走(违背用户意愿),
要么标签指着一个并不最近的地址(是在骗人)。有 dart 测试钉住这一点。

位置来源:调用方没给就自己取一次 `getLastKnownPosition` ——
**不弹权限、不等 GPS**。「哪个地址离我近」这件事,几分钟前的位置足够用了,
为它卡住整个地址簿的加载不划算;拿不到就退回原顺序,功能不受影响。

**没有做「自动选中最近的」**:截图里那句"已为你自动选中"是在一个
**单选列表**里预选,用户仍能改;而我们这个列表点一下就返回了 ——
在这里"自动选中"等于替他做决定,他连别的地址都没看见。
所以只标出来 + 说一句,选还是他选。

### 顺带修掉一个会随单量炸掉的核账 bug

回归挂在 `the number of query arguments cannot exceed 32767`。

`services/audit.py`(每日自动核账)用 `order_id.in_([...])` 传的是
**Python 列表**,SQLAlchemy 会给每个 id 绑一个占位符,而 PostgreSQL
单条语句的参数上限是 32767 —— **一个月完成单超过这个数,核账就直接挂**。

后果不是"少一条告警",是**整个核账不再运行** ——
而这套东西的全部意义就是"差一分钱系统报警"。改成子查询。

第一次只改了三处,漏了售后判责那一处,`NameError` 才暴露出来;
测试因此断言的是**四处**都走子查询 —— 漏一处,核账照样会在那个量级挂掉。

### 还没做

- **「100%附近用户选择」**(截图 2 里那个比例):要聚合其他用户的选址行为。
  我们现在单量太小,算出来的比例会误导人 —— 等有真实密度再说;
### #172 城市切换器 —— 它修的是一个真 bug,不是加个控件

截图顶部那个「西安市 ⌄」看着是个小控件,做的时候发现它对应一个真问题:

`geoTips` 的 city 参数**写死成「成都」**,而地址页从来没传过。
服务端用腾讯的 `region_fix=1` 把 POI 搜索**限死在指定城市** ——
限死本身是对的(不加的话搜「一号店」会返回全国同名地点,用户容易选中
外地那个,下单后才发现超出配送范围),但**城市选错就搜不到自己家**。

实测:西安的「紫薇臻品」在 `city=成都` 时返回 **0 条**,`city=西安` 返回 10 条。
**成都以外的用户根本搜不出自己的地址,界面上还看不出为什么。**

做了三件事:

- `GET /geo/cities`:清单来自**实际有商家的城市**(配了 open_cities
  就以清单为准)—— 列一个没有商家的城市,用户切过去只会看到空列表。
  面板里把商家数露出来(「成都市 · 1011 家店」),清单里没商家的标「暂无商家」;
- `geoTips` 的 city 从"有默认值"改成 **required** —— 这个参数没有安全的默认值;
- 客户端 `SzCityChip`:城市优先级是**用户记住的选择 > 定位解析 > 留空**。
  留空时显示「选择城市」而**不猜一个填进去** ——
  猜错了用户会以为已经选对,然后搜不出东西也不知道为什么。

实机验过:模拟器拿不到定位时如实显示「选择城市」,点开面板列出
「成都市 · 1011 家店」,选中后顶部变成「成都市」。
