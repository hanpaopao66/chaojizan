# 开发提示词 #269–#276:开源可信度 —— 从「我们说」到「你可验」

来源是一次讨论:仓库已经公开(github.com/hanpaopao66/chaojizan),README、
决策记录、130 套 e2e、见证节点这些底子都在,比绝大多数开源项目好。
所以这批**不是**补「像样的开源项目该有的门面」,而是一件事:

**把已有的硬货,变成外人不看我们脸色就能验证的东西。**

资深程序员的认可从来不是被 README 的口号打动,而是他动手验证了一件
我们声称的事,发现是真的。README 写着「不要相信我们,验证我们」——
这批就是把这句话从账本扩展到整个仓库:测试是不是真的绿、APK 是不是
真的从这个 tag 编的、别的城市是不是真的部得起来。

## #276 先做这条,不排队:全历史密钥扫描

放在最后一个编号、但**最先做**,因为仓库已经公开了,这条不是预防是排雷。

`scripts/security_scan.sh` 管的是当前工作区的增量;git 历史里进过又删掉的
东西它管不着,而公开仓库的历史人人可翻。用 gitleaks 扫全部历史:

```bash
gitleaks git . --report-path /tmp/gitleaks-report.json
```

**要做**:

- 扫出真密钥 → **换钥优先于改历史**。仓库已公开,历史早被克隆过,
  rewrite history 已经保护不了任何东西,只会弄断所有人的 fork。
  该轮换的轮换(JWT_SECRET、短信/地图 Key、frpc token),轮换完历史里
  那份就只是废纸;
- 扫出的误报整理成 `.gitleaksignore`,然后把 gitleaks 加进 CI ——
  security_scan.sh 继续管本地提交前,gitleaks 管推上去之后的兜底;
- 扫完没事就把「扫过、哪天扫的、结论」记在本文档末尾,一句话即可。

## #269 README 挂 CI 徽章:质量信号已经存在,缺的只是被看见

`.github/workflows/ci.yml` 已经有三个 job:服务端 e2e(真 PostGIS +
Redis + MinIO,跑在真实 HTTP 接口上)、单元测试、三端静态检查。
这在开源项目里是很硬的信号,但现在只有点进 Actions 页的人知道。

**要做**:

- README 标题下挂徽章:CI 状态、许可证、最新 release;
- 「改完代码跑什么」那节加一句:CI 对每个 PR 跑同样三件事,
  并链到 ci.yml —— 那个文件里的注释(为什么 CI 用 minio、为什么
  演示口令每次随机)本身就值得被读到;
- **不做** codecov 之类的覆盖率徽章。130 套 e2e 的价值在「跑在真实
  接口上」,行覆盖率数字反而把它拉低成普通指标。

小半天的活,先干掉。

## #270 关键设计决策配代码坐标 + 决策记录索引

README「关键设计决策」一节写得对,但资深读者看完第一反应是「代码呢」。
另外 DEV-PROMPTS 已经 30 篇,外人不知道从哪读起 —— 这些文档是仓库里
最独特的资产(README 自己说了「比 commit 信息更完整」),没有导览等于没有。

**要做**:

- 「关键设计决策」每条后面补文件坐标:状态机唯一入口(`state_machine.py`)、
  条件 UPDATE 防双花在哪个函数、每日核账恒等式在哪、快照存在哪张表。
  格式照 DEV-PROMPTS-29 引代码的写法,`文件:行号`;
- 新建 `docs/INDEX.md`:按主题(账本与透明 / 并发与钱 / 骑手 / 商家 /
  部署运维)把 30 篇 DEV-PROMPTS 和 DESIGN-*.md 归类,每篇一行
  「讲了什么 + 最值得看的一个决定」;README 的 docs/ 说明指过去;
- **不做**内容重写。索引只指路,不复述 —— 复述会和原文漂移。

## #271 账本链协议规格:让「第三方实现」从口号变成可能

见证节点现在有 Python(`witness/superz_witness.py`)、Go(`witness/go/`)
和网页版 —— 但都是**我们写的**。「社区见证」的说服力上限,取决于
一个陌生人能不能不读我们的代码、只读一份规格,就写出自己的验证器。
现在算法散在三份实现的注释里,做不到。

**要做**:

- `docs/LEDGER-SPEC.md`:锚点数据格式、`chain_hash = sha256(昨日链哈希
  + 今日账本哈希)` 的精确定义(编码、字段序、边界情况:首日、空账日、
  费率变更日)、三原则校验的逐条算法(佣金 ≤ 内嵌上限、净额恒等式、
  配送费只进不冲、团购费率),以及公开接口的 URL 与响应契约;
- **测试向量**:附几组真实历史锚点(输入 → 期望哈希),含至少一组
  费率口径变更跨界的。第三方实现对着向量自测,不用问我们;
- 规格里写明版本号与变更规则:改格式必须发新版本号并保留旧版校验
  逻辑 —— 历史锚点按当天口径复算,这条已经在做,写进规格里锁死;
- witness/README 加一段:欢迎任何语言的独立实现,对得上测试向量的
  列进 nodes 页。**第一方实现从此降级为「参考实现」。**

这是全仓库最独特的东西,也是最可能被行家转发的一份文档。

## #272 SECURITY.md + 威胁模型:碰钱的系统要敢摊开写

这是个碰钱的系统,却没有 SECURITY.md —— 想报漏洞的人现在只能发 issue,
等于让他公开挂出来。

**要做**:

- `SECURITY.md`:怎么私下报告(邮箱)、多久必回(和骑手意见反馈
  「平台必须回复」同一口径)、赏金没有就直说没有,别学大厂含糊;
- 威胁模型一节(就写在 SECURITY.md 里,不单开文档):我们想过哪些
  攻击面,哪些有对抗(刷单 → 反作弊闭环;双花 → 行锁与条件 UPDATE;
  篡账 → 哈希链与见证节点;支付重放 → 幂等入账),哪些明确还没有
  (见证节点被喂假数据的女巫问题、DDoS)。**没防的写出来比藏着强** ——
  「样本不足就说不足」在安全上的同义句是「没防的就说没防」;
- CONTRIBUTING 和 README「参与」一节链过去。

## #273 开城手册:AGPL「拿去用」的真正对象是另一个城市的人

`deploy/README.md` 写得不错,但它是**这套部署**的运维手册:预设了
deploy_server.sh 从开发机 rsync、frps 中转、.env.prod 已经存在。
README 终局那段承诺「任何人可以拿它在任何城市部署」,兑现物应该是:
一个会 Docker 的陌生人,不问我们任何问题,照文档一个周末起一套。

**要做**:

- `docs/OPEN-A-CITY.md`,按时间顺序写:
  1. 要花多少钱:VPS 什么配置、域名、备案要多久 —— 真实数字,
     这本身是「5% 能活」的证据;
  2. 要办什么证:微信支付商户号、地图 Key、短信签名各去哪申请、
     卡多久、个体户行不行;
  3. `server/.env.example` 逐段过一遍:哪些必填、哪些空着会发生什么
     (minio 不起则上传 503 这类要写明,别让人自己撞);
  4. 起 compose → 跑迁移 → seed → 用演示账号走一遍完整下单流程
     作为验收;
  5. 哪些东西**不要**照抄我们的:frp 内网穿透是我们省钱的选择,
     人家有公网 IP 的云主机直接跑更简单;
- 手册里的每条命令自己在干净机器(或干净 VM)上跑过一遍再写,
  没跑过的命令不进文档 —— 这份文档的失败模式就是「作者环境里都对」;
- **不做**多租户/一套部署管多城。开城 = 各城一套独立部署、独立账本,
  这是架构现状,也符合「利润留在本地」的立意,写清楚即可。

## #274 构建公证:线上跑的确实是这个 tag 编出来的

README 说「线上运行版本 = 本仓 tag」、APK 装前校验 SHA-256 ——
但这两条现在都是**我们自己说的**:APK 由 `scripts/release_apks.sh`
在开发机上打包,SHA-256 也是我们算的。校验和只能证明「下载没坏」,
证明不了「确实从这个 tag 编的」。

**要做(分两档,先做第一档)**:

- 第一档 · 公开构建:发版走 GitHub Actions,由 tag 触发,在公开
  runner 上打 APK 并发 GitHub Release,摘要写进 Release 页。
  信任根从「作者的开发机」换成「公开可查的 CI 日志」。
  release_apks.sh 里官网直链包/商店包两种产物不能混(#192)的约束
  原样带过去;地图 Key 走 Actions secret,**打进包里的是 Key 本身,
  这不算泄密但要在文档里说清楚**(客户端 Key 本来就是公开的,
  腾讯侧按包名+签名限制);
- 第二档 · 逐字节可复现:Flutter 产物要逐字节一致得钉死构建时间戳、
  签名过程外置等一堆东西,**先立目标不立军令状** —— 在 Release 页
  写明「当前做到公开构建,逐字节可复现在路上」。诚实的中间态
  好过吹了再圆;
- 服务端同理但更简单:镜像在 CI 构建、推带 digest 的 registry,
  透明中心版本公示从「tag 名」升级为「tag 名 + 镜像 digest」。

## #275 贡献门槛:issue 模板 + 十个真实的 good first issue

`.github/ISSUE_TEMPLATE/` 现在不存在。想报 bug 的用户和想上手的
开发者面对同一个空白框。

**要做**:

- issue 模板三份:bug(哪个端、什么版本、复现步骤)、功能建议
  (提醒先翻 DEV-PROMPTS 的「明确不做」——很多提议我们不是没想到,
  是想到了并写了为什么不做)、部署求助(引到开城手册);
- 从积压里挑约十个标 `good first issue`,标准:一个下午能完成、
  不碰状态机和钱、e2e 能兜住。宁缺毋滥,标错一个劝退一个;
- PR 模板一句话:改了什么、`make unit / analyze / test` 哪些跑了。
  CONTRIBUTING 已有的规矩不重复。

## 验收时要一起看的

这批全是对外承诺,所以每一条都要过同一个问题:

**一个不认识我们、也不想信我们的人,能独立验证这条吗?**

- 徽章 → 他能点进去看到每个 PR 的真实运行记录吗?
- 规格 → 他能不读我们的代码写出对得上测试向量的验证器吗?
- 开城手册 → 他能不进我们的群、一个周末起一套吗?
- 构建 → 他能从 Release 页追到那次公开构建的日志吗?

答案是「能,但得先问我们一句」的,就还没做完。
