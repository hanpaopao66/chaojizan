# 超级赞(chaojizan)

[![CI](https://github.com/hanpaopao66/chaojizan/actions/workflows/ci.yml/badge.svg)](https://github.com/hanpaopao66/chaojizan/actions/workflows/ci.yml)
[![Release](https://img.shields.io/github/v/release/hanpaopao66/chaojizan)](https://github.com/hanpaopao66/chaojizan/releases)
[![License: AGPL-3.0](https://img.shields.io/badge/license-AGPL--3.0-blue)](LICENSE)

超级赞是一个开源的生活服务平台,出发点是「群众帮群众」:把日常要用的东西装进一个 App —— 聊天、视频、小程序、外卖、到店团购、酒店、跑腿。账号和实名、消息、支付和账本、地图和配送、小程序托管、审核和申诉,这些底座修一次,上面每接一个业务都能直接用。

平台的收入只有几笔固定费用:外卖佣金 5% 封顶,团购核销收 2%,酒店离店收 5%,跑腿收 2%,消息、视频和小程序不收费。配送费一分不抽,账目每月公开,有结余也不分红,用在骑手保障、商家扶持和降费率上。代码 AGPL 开源,一个城市一个月一百多块钱就能跑起来。

## 怎么收费

| 业务 | 平台收多少 |
|---|---|
| 外卖 | 商家佣金 5% 封顶,单量大的商家阶梯降到 4%;配送费一分不抽 |
| 到店团购 | 核销才收 2%,未使用随时全额退 |
| 酒店 | 离店才收 5%;取消、未入住不收 |
| 跑腿 | 跑腿费收 2%,账单上单列;帮买的商品款一分不抽 |
| 消息、视频、小程序 | 不收费 |

几句话写在明处:

- 外卖佣金 5% 是上限,不是目标。哪天 3% 能活,就降到 3%。
- 配送费和小费 100% 归骑手,提现不收手续费。
- 每一单的钱去哪了(商家实收 / 骑手所得 / 平台留存),顾客在订单页看得到。
- 平台不以盈利为目的:收入先覆盖服务器、短信、地图和客服的开销,每月收支公开,结余不分红。
- 不做会员等级,不发平台补贴,不卖数据,不竞价排名,不收推广费。

平台收入只有上面这几笔。出了事按谁的问题算谁的:商家有责任,顾客拿回全款(配送费和小费也退),钱由商家出;骑手有责任,先从公开可查的骑手保障金池出,不够的由骑手承担,不封顶,能申诉。平台只在一种情况下出钱:平台判错了,平台自己认。首单立减、超时安抚券这类平台出钱的开关连同代码已经删了,拨不回来;停发之前发出去的券照旧能用。

## 自己部署一个

### 1. 后端(5 分钟)

```bash
docker compose up -d db redis          # PostgreSQL(PostGIS) + Redis

cd server
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload          # http://localhost:8000/docs 看接口文档

# 另开终端灌演示数据
cd server && source .venv/bin/activate && python -m scripts.seed
```

或者全容器化:`docker compose up -d --build`。

### 5. 改完代码跑什么

```bash
make unit          # 纯函数单测,秒级
make analyze       # Dart 静态检查 + 三端 Dart 单测 + 各 web tsc + 小程序测试
make test          # 近 200 套 e2e,跑在真实 HTTP 接口上(需要服务已启动)
```

`make test` 的前置条件写在 Makefile 注释里(服务端要用 `AUTO_FLOW_ENABLED=false` 启动等),少一个都跑不完。e2e 清单在 `server/tests/e2e_suites.txt`,新写的要加进去,单测会拦漏加的。CI 把这份清单按实测耗时分成 4 组并行跑,每组一个干净库,套件之间不能互相依赖数据。

CI 对每个 PR 跑同样的三件事:服务端 e2e(起真 PostGIS/Redis/MinIO,和生产同一条代码路径)、三端静态检查与 Dart 单测、工作区与全历史的密钥扫描。配置在 [.github/workflows/ci.yml](.github/workflows/ci.yml),里面的注释解释了每个不显然的选择。

├── developer-web/        # 开发者后台:小程序 / 小游戏 / 机器人的发布与管理

`docs/DEV-PROMPTS-*.md` 是这个项目的决策记录:每批功能动手前先写清楚调研结论、要守的边界、不做什么以及为什么。比 commit 信息完整,想看「为什么是这个设计」可以从 [docs/INDEX.md](docs/INDEX.md) 进。

订单状态流:待支付 → 待接单 → 制作中 → 待取餐 → 配送中 → 已送达 → 已完成。骑手在「制作中/待取餐」阶段抢单,每次流转写入 `order_events` 审计表。

## 一些设计决定

每条都给了代码坐标,不用信描述,可以直接去读实现(行号会漂移,对不上时按函数名搜):

- **金额一律用「分」存整数**,杜绝浮点误差 —— `server/app/models.py` 的 `Dish.price_cents`,订单侧 `Order.*_cents` 同理
- **状态机集中管控**:非法流转直接 409,每次变更写审计表 —— 唯一入口 `server/app/state_machine.py` 的 `assert_transition()`,审计表 `order_events`
- **账本只追加不修改**:冲账 = 追加负数行;每日核账恒等式,篡改 1 分钱会被抓出来 —— 铁律写在 `models.py` 的 `RiderEarning` 文档里,冲账在 `services/settlement.py` 的 `reverse_merchant_earning()`
- **防超卖、防双花、抢单防冲突**:一律用数据库条件 UPDATE,并发安全在存储层保证 —— 抢单 `routers/riders.py` 的 `grab_order()`,库存扣减 `routers/orders.py`,提现行锁 `request_withdrawal()`
- **支付幂等**:模拟支付与微信回调走同一个入账函数,联调只换通道不换逻辑 —— `services/payment_core.py` 的 `mark_order_paid()`
- **快照优于重算**:凡是要当证据或当钱的(配送费拆分、申诉证据),一律在下单/送达当时存快照 —— 设计理由写在 `models.py` 的 `Order.fee_parts` 字段上
- **样本不足就说不足**:分位数、热力图这类统计,低于门槛不给数字只给样本数 —— `services/drop_time.py` 的 `MIN_SAMPLE = 20`,热力图每格带 `enough` 标记

## 几个常被问到的

**没有补贴,冷启动怎么办?**

死亡螺旋怕的是每单倒贴钱:补贴一停人就走,不停钱就烧完。我们不补贴,也不打算跟大平台抢全国的量。一个城市一个月的固定开销一百多块,单少只是长得慢,不会被拖死。起步也不需要三边凑齐:消息、视频、小程序不靠商家和骑手的密度,用户有别的理由先用起来;外卖先找自带熟客的小店,一份 21 块的菜别的平台扣 4 块多,这里扣 1.05;骑手不够的地方先用到店自取和商家自配送。

**这不也是抽成吗,只是多少的区别?**

是抽成。区别不只在多少:5% 封顶写在这里,能降就降;收入只有上面那几笔,不卖数据、不收推广费、不抽配送费;平台自己的收支按月公开,结余不分红;代码开源,账算得对不对谁都能核。

**公平、公正、公开具体指什么?**

公开:每一单的钱怎么分,顾客在订单页看得到;平台账目串成哈希链,谁都能跑见证节点复算;线上跑的版本就是本仓库的 tag。公平:店铺排序不卖钱,小程序目录的排序是一段公开的纯函数;信用分只算平台判定成立、能申诉的事,接单之后才给这一单的交易对方看,不用来派单和定价。公正:判了责任、处罚了人都能申诉;判责规则、处置统计、管理员查看私聊的次数,都在透明中心公示。
