# 超级赞(chaojizan)

[![CI](https://github.com/hanpaopao66/chaojizan/actions/workflows/ci.yml/badge.svg)](https://github.com/hanpaopao66/chaojizan/actions/workflows/ci.yml)

一个群众帮助群众的平台,旨在提高国内群众挣到的钱。

**超级赞是一个超级 App,我们把它当大基建来做。** 聊天、刷视频、用小程序,点外卖、买团购、订酒店、
叫跑腿,都在一个 App 里。账号和实名、消息、支付和账本、地图和配送、小程序托管、审核和申诉,
这些底座平台修一次,上面的每个业务、每个第三方开发者都能用。外卖只是跑在上面的第一个业务。

平台本身不以盈利为目的:收的钱用来养活这套底座(服务器、短信、地图、客服),
每个月的收支在透明中心公开;有结余不分红,用在骑手保障、商家扶持和降费率上。
代码 AGPL 开源,一个城市一个月一百多块钱就能跑起来。

## 平台原则(产品决策以此为纲)

1. **商家只抽 5%** —— 菜价里没有平台税,点单页明示。**5% 是上限,不是目标:
   哪天 3% 能活,就降到 3%(这行写在这里当立字据)**
2. **配送费 100% 归骑手** —— 按距离计价,平台分文不取,小费也全归骑手,提现零手续费
3. **账目三方透明** —— 每一单"钱去哪了"(商家实收/骑手所得/平台留存)对用户公开可查
4. **平台不以盈利为目的** —— 收支按月公开,结余不分红,用在骑手保障、商家扶持和降费率上。
   平台也**不出钱赔付、不发补贴**:谁的责任谁承担;骑手出了责任,先从公开可查的骑手保障金池出,不够的由骑手承担,能申诉

其他几块的收费一样写在明处:团购核销才收 2%,酒店离店才收 5%,跑腿费收 2% 并在账单上单列一行;
消息、视频、小程序不收钱。平台的收入只有这几笔 —— 不卖数据、不竞价排名、不收推广费、不抽配送费。

## 常见问题

**没钱补贴,冷启动不就是死亡螺旋?**

死亡螺旋怕的是每单倒贴钱:补贴一停人就走,不停钱就烧完。我们不补贴,也不打算跟大平台抢全国的量;
一个城市一个月的固定开销一百多块,单少只是长得慢,不会被拖死。起步也不需要三边一起凑齐:

- 消息、视频、小程序不靠商家和骑手的密度,用户有别的理由先用起来;
- 外卖先找自带熟客的小店。每家店有自己的二维码和海报,熟客挪过来商家直接省钱 ——
  一份 21 块的菜,别的平台要扣 4 块多,这里扣 1.05;
- 骑手不够的地方先用到店自取和商家自配送,单量起来了再交给众包骑手。

**你这不也是抽成吗,只是多少的区别?**

是抽成。区别不只在多少:5% 封顶写在这里,能降就降;收入只有上面那几笔,不卖数据、不收推广费、
不抽配送费;平台自己的收支按月公开,结余不分红;代码开源,账算得对不对谁都能核。

**公平、公正、公开具体指什么?**

- 公开:每一单的钱怎么分,顾客在订单页上看得到;平台的账目串成一条哈希链,谁都能跑见证节点复算,
  改历史上任何一分钱都会被发现;线上跑的版本就是本仓库的 tag。
- 公平:店铺排序不卖钱,小程序目录的排序是一段公开的纯函数;信用分只算平台判定成立、能申诉的事,
  接单之后才给这一单的交易对方看,不用来派单和定价。
- 公正:判了责任、处罚了人都能申诉;判责规则、处置统计、管理员查看私聊的次数,都在透明中心公示。

      结构设计与踩坑记录见 [docs/DESIGN-errand.md](docs/DESIGN-errand.md)
- [ ] 场景难度进 ETA 补时(等送达段数据攒够,**只补时不加价**)

**明确不做**(理由写在 [docs/DEV-PROMPTS-22.md](docs/DEV-PROMPTS-22.md))

爆单预警与单量预测(我们的量级上只是噪音)、热力图上的"推荐去哪跑"(那是软性派单)、
派单分、服务分、骑手等级和段位这类影响接单的分数,拿来处罚的违规积分(处置按违规计次,和信用分无关)、
付费排名与竞价、平台补贴烧钱玩法。

信用分(顾客、商家、骑手都有,2026-09 起):0–100,90 起步,最近 180 天完成一单 +1(最多 +10);
只扣平台判定成立、当事人能申诉的事 —— 顾客是被判为顾客原因的配送异常,商家是被平台复核判为商家责任的售后,
骑手是被判为骑手责任的配送异常和售后,三种角色都算判定成立的违规(按严重程度 −20 / −10)。
接单前取消、拒单、同意退款、转单、差评、慢都不扣分。只在接单之后、只给这一单的交易对方看分数和等级,
不进派单、曝光、排名、定价、处置。公式见透明中心「信用分怎么算」([services/credit.py](server/app/services/credit.py))。

### 生活服务 · 到店团购与排队(运营中)

低价引流到店,核销才收 2%;未使用随时全额无理由退,不靠「过期不退」摸钱。
排队取号、叫号,不卖插队。

### 生活服务 · 酒店住宿(运营中)

对标 OTA 12%–20% 佣金加"全网独家"排他条款:我们佣金 5%,**离店才收**——
订单取消、客人未入住,平台分文不取;无排他、无竞价排名、无年费。
房态房价商家自管,取消政策下单前明示,到店无房商家赔首晚 30% 违约金给客人。

### 生活服务 · 跑腿代购(运营中)

帮送(A 取 B 送)与帮买(骑手替你去买)。跑腿费**平台只收 2%,在账单上单列一行**——
和外卖那边"配送费一分不抽"是两个口径,不明说就成了自打嘴巴:外卖平台的收入来自
商家佣金,跑腿没有商家,这 2% 是这条业务上唯一的收入。

帮买的**商品款你先付给平台,骑手不垫自己的钱**——让收入最低的那个人先掏钱,
是把平台的资金风险转嫁给他。商品款平台一分不抽,按小票实付结给骑手,**小票你看得到**;
超支 20%(且 ≤20 元)以内骑手直接买,超出必须先问你;买不到全额退商品款,
跑腿费只收到店那一段的距离费,这条写在下单页不藏在协议里。

**不做**:即食餐饮代购(需食品经营许可,我们不给无证经营导流)、烟、酒、药;
不做保价——赔不了你真实损失,与其事后争执不如提前写明贵重物品请勿使用。

### 出行 · 打车(筹备中)

司机每单被抽走两三成,高峰还有乘客看不见的差价。我们的版本:司机不被抽走三成车费,
计价规则公开,账目同一套透明框架。

### 以后接进来的行当

凡是抽成高、账目不透明的行当,都可以接到这套底座上,用「低抽成 + 账目公开 + 代码开源」重做一遍:

| 行当 | 行业现状 | 我们要做的样子 |
|---|---|---|
| 家政 | 中介两头收费,阿姨月薪被抽两到四成 | 阿姨的钱不过中介的手 |
| 维修 | 上门费+虚报故障,"小病大修"成行规 | 明码标价,不搞小病大修 |
| 货运 | 司机先交会员费,算法一路压运价 | 不收会员费,不用算法压价 |
| 零工 | 劳务中介层层转包,日结被截一两成 | 日结工资一分不被中介截 |

### 终局

这套代码 AGPL 开源,任何人可以拿它在任何城市部署一个不吸血的平台。
它能跑通,就会有人跟着做——改变不了行业,就写一个样本出来。

### 5. 改完代码跑什么

```bash
make unit          # 纯函数单测,秒级
make analyze       # Dart 静态检查 + merchant-web tsc
make test          # 近 200 套 e2e,跑在真实 HTTP 接口上(需要服务已启动);清单在 server/tests/e2e_suites.txt
```

`make analyze` 必须带上 `packages/shared`——在 app 目录里跑 `flutter analyze`
**不会**检查它(shared 是 path 依赖,被当外部包跳过),而客户端大部分代码就在那儿。
曾因此漏掉一个重复定义的方法:analyze 全绿、e2e 全绿,直到打 release 包才编译失败。

`make test` 的三个前置条件写在 Makefile 注释里(服务端要用
`AUTO_FLOW_ENABLED=false` 启动等),少一个都跑不完。它跑完全部再汇总,
不在第一个失败处停;新写的 e2e 要加进 `server/tests/e2e_suites.txt`(漏加了单测会拦)。
CI 把这份清单按实测耗时分成 4 组并行跑(`python -m tests.run_e2e --shard k/4`),
每组各自一个干净库,所以套件之间不能靠前一个套件留下的数据。

CI 对每个 PR 跑同样的三件事(服务端 e2e 起真 PostGIS/Redis/MinIO,
和生产同一条代码路径),外加工作区与全历史两层密钥扫描 ——
配置在 [.github/workflows/ci.yml](.github/workflows/ci.yml),
里面的注释解释了每个不显然的选择(为什么 CI 也用 MinIO、
为什么演示口令每次随机),值得一读。

## 关键设计决策

每条都给了代码坐标 —— 不用信我们的描述,直接去读实现。
(行号会随改动漂移,对不上时按函数名搜)

- **金额一律用「分」存整数**,杜绝浮点误差
  —— [models.py#L468](server/app/models.py#L468) `Dish.price_cents` 行尾就是这句口径注释,
  订单侧 `Order.*_cents` 全套同理
- **状态机集中管控**:非法流转直接 409,每次变更写审计表
  —— 唯一入口 [state_machine.py#L58](server/app/state_machine.py#L58) `assert_transition()`,
  409 落点 [orders.py#L757](server/app/routers/orders.py#L757),
  审计表 `order_events` 在 [models.py#L1314](server/app/models.py#L1314)
- **账本只追加不修改**:冲账=追加负数行;每日核账恒等式(e2e 篡改 1 分钱必被抓出)
  —— 铁律写在 [models.py#L826](server/app/models.py#L826) `RiderEarning` 的 docstring,
  冲账实现 [settlement.py#L125](server/app/services/settlement.py#L125)
  `reverse_merchant_earning()`(三个金额字段整体取负新插一行),
  七条恒等式在 [audit.py](server/app/services/audit.py) 文件头、主函数 `run_audit()`
- **防超卖/防双花/抢单防冲突**:一律数据库条件 UPDATE,并发安全在存储层保证
  —— 抢单 [riders.py#L1518](server/app/routers/riders.py#L1518) `grab_order()`
  (手慢的收到 409),库存扣减 [orders.py#L260](server/app/routers/orders.py#L260)
  (`stock >= quantity` 条件),提现行锁 [riders.py#L1879](server/app/routers/riders.py#L1879)
  `request_withdrawal()`
- **支付幂等**:模拟支付与微信回调走同一入账函数,联调只换通道不换逻辑
  —— 共同入口 [payment_core.py#L22](server/app/services/payment_core.py#L22)
  `mark_order_paid()`,两个调用方:[orders.py#L716](server/app/routers/orders.py#L716)(模拟)/
  [payments.py#L170](server/app/routers/payments.py#L170)(微信回调)
- **公开数据无个案**:大屏/透明中心全部平台级聚合,手机号打码、坐标只到城市级
  —— [screen.py#L293](server/app/routers/screen.py#L293) `screen_latest_orders()`
  (打码+坐标两位小数+订单号只露尾 6 位),
  聚合口径 [transparency.py#L213](server/app/routers/transparency.py#L213) `fairness_public()`
- **快照优于重算**:凡是要拿出去当证据或当钱的(配送费拆分、申诉证据),
  一律下单/送达当时存快照。事后按当前费率重算,和当时真正收的对不上
  —— 设计理由就写在字段上:[models.py#L552](server/app/models.py#L552) `Order.fee_parts`,
  写入处 [orders.py#L627](server/app/routers/orders.py#L627),
  骑手端明确「读快照不重算」[riders.py#L489](server/app/routers/riders.py#L489)
- **样本不足就说不足**:分位数、热力图这类统计,低于门槛不给数字只给样本数——
  "这里确实快"和"我们还不知道"是两件事,混在一起就是在编
  —— [drop_time.py#L39](server/app/services/drop_time.py#L39) `MIN_SAMPLE = 20`,
  热力图每格带 `enough` 标记 [riders.py#L586](server/app/routers/riders.py#L586) `order_heatmap()`
- **e2e 全链路回归**:`make test` 近 200 套端到端测试,跑在真实 HTTP 接口上
