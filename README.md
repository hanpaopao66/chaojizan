[![CI](https://github.com/hanpaopao66/chaojizan/actions/workflows/ci.yml/badge.svg)](https://github.com/hanpaopao66/chaojizan/actions/workflows/ci.yml)

一个群众帮助群众的平台,旨在提高国内群众挣到的钱,向外卖平台等第三方黑心平台宣战。

> **超级赞是「群众帮群众」计划的第一战。** 目标不只是外卖:凡是高抽成、不透明的行业,
> 这套「低抽成 + 账目公开 + 代码开源」的模式都成立。外卖打穿之后,再打下一个。
>
> ⭐ 如果你认同「外卖可以不是这样」,给个 star 就是最简单的支持。
> 也欢迎提 issue / PR / 把它部署到你的城市——或者来帮我们打下一个战场。

**低抽成外卖平台**:商家总负担 5% 封顶(行业平台 20%+),用户端 / 商家端 / 骑手端三端 + 一个后端,
到店团购、透明中心、运营大屏、公开账本一应俱全。

## 平台三原则(产品决策以此为纲)

1. **商家只抽 5%** —— 菜价里没有平台税,点单页明示。**5% 是上限,不是目标:
   哪天 3% 能活,就降到 3%(这行写在这里当立字据)**
2. **配送费 100% 归骑手** —— 按距离计价,平台分文不取,小费也全归骑手,提现零手续费
3. **账目三方透明** —— 每一单"钱去哪了"(商家实收/骑手所得/平台留存)对用户公开可查

透明本身就是与吸血平台竞争的武器。5% 是唯一收入(不卖数据、不竞价排名、不收推广费、
不抽配送费),平台自身收支公开,盈余不分红——优先骑手保障、商家扶持和降费率。

### 同场加映 · 到店团购(运营中)

低价引流到店,核销才收 2%;未使用随时全额无理由退,不靠「过期不退」摸钱。

### 同场加映 · 酒店住宿(运营中)

对标 OTA 12%–20% 佣金加"全网独家"排他条款:我们佣金 5%,**离店才收**——
订单取消、客人未入住,平台分文不取;无排他、无竞价排名、无年费。
房态房价商家自管,取消政策下单前明示,到店无房商家赔首晚 30% 违约金给客人。

### 同场加映 · 跑腿代购(运营中)

帮送(A 取 B 送)与帮买(骑手替你去买)。跑腿费**平台只收 2%,在账单上单列一行**——
和外卖那边"配送费一分不抽"是两个口径,不明说就成了自打嘴巴:外卖平台的收入来自
商家佣金,跑腿没有商家,这 2% 是这条业务上唯一的收入。

帮买的**商品款你先付给平台,骑手不垫自己的钱**——让收入最低的那个人先掏钱,
是把平台的资金风险转嫁给他。商品款平台一分不抽,按小票实付结给骑手,**小票你看得到**;
超支 20%(且 ≤20 元)以内骑手直接买,超出必须先问你;买不到全额退商品款,
跑腿费只收到店那一段的距离费,这条写在下单页不藏在协议里。

**不做**:即食餐饮代购(需食品经营许可,我们不给无证经营导流)、烟、酒、药;
不做保价——赔不了你真实损失,与其事后争执不如提前写明贵重物品请勿使用。

### 第二战 · 打车(筹备中)

司机每单被抽走两三成,高峰还有乘客看不见的差价。我们的版本:司机不被抽走三成车费,
计价规则公开,账目同一套透明框架。

### 以后的仗,一场一场打

凡是抽成不透明、靠信息差吸血的行当,都值得用「低抽成 + 账目公开 + 代码开源」重做一遍:

| 行当 | 行业现状 | 我们要做的样子 |
|---|---|---|
| 家政 | 中介两头收费,阿姨月薪被抽两到四成 | 阿姨的钱不过中介的手 |
| 维修 | 上门费+虚报故障,"小病大修"成行规 | 明码标价,不搞小病大修 |
| 货运 | 司机先交会员费,算法一路压运价 | 不收会员费,不用算法压价 |
| 零工 | 劳务中介层层转包,日结被截一两成 | 日结工资一分不被中介截 |

### 终局

这套代码 AGPL 开源,任何人可以拿它在任何城市部署一个不吸血的平台。
它能跑通,就会有人跟着做——改变不了行业,就写一个样本出来。

## 架构

```
chaojizan/
├── apps/
│   ├── user_app/        # 用户端(Flutter):品类逛店、下单、追踪、售后、团购
│   ├── merchant_app/    # 商家端(Flutter):接单出餐、菜品、对账、营销、打印
│   └── rider_app/       # 骑手端(Flutter):抢单、导航、钱包、实名认证
├── packages/shared/     # 三端共享:模型、API 客户端、登录/开屏/推送/地图
├── server/              # 后端(FastAPI + PostgreSQL/PostGIS + Redis)
│   └── app/
│       ├── state_machine.py   # 订单状态机(所有状态变更的唯一入口)
│       ├── services/          # 结算/审计/账本锚点/风控/营销/定价……
│       └── routers/           # 业务路由 + 公开数据(screen/transparency)
├── web/                 # 官网 + 运营大屏 + 透明中心(React + Three.js + ECharts)
├── merchant-web/        # 商家网页工作台(React+TS+AntD):外卖接单/菜品批量、
│                        #   酒店房态中控台/前台办理,构建产物由后端托管 /merchant
├── witness/             # 社区见证节点脚本(任何人可跑,复算公开账本)
├── docs/                # 开发提示词(每个功能"为什么这么做"与"明确不做什么")
│                        #   + 结构设计文档 + 运维手册
└── deploy/              # 生产部署(compose 全栈:api/nginx/frpc,内网穿透自持)
```

`docs/DEV-PROMPTS-*.md` 是这个项目的决策记录:每批功能动手前先写清楚
调研结论、要守的边界、**明确不做什么以及为什么**。比 commit 信息更完整,
适合想理解"为什么是这个设计"的人。

**订单状态流**:待支付 → 待接单 → 制作中 → 待取餐 → 配送中 → 已送达 → 已完成
(骑手在「制作中/待取餐」阶段抢单;每次流转写入 order_events 审计表)

### 5. 改完代码跑什么


`make analyze` 必须带上 `packages/shared`——在 app 目录里跑 `flutter analyze`

`make test` 的三个前置条件写在 Makefile 注释里(服务端要用
`AUTO_FLOW_ENABLED=false` 启动等),少一个都跑不完。

CI 对每个 PR 跑同样的三件事(服务端 e2e 起真 PostGIS/Redis/MinIO,
和生产同一条代码路径),外加工作区与全历史两层密钥扫描 ——
配置在 [.github/workflows/ci.yml](.github/workflows/ci.yml),
里面的注释解释了每个不显然的选择(为什么 CI 也用 MinIO、
为什么演示口令每次随机),值得一读。

## 关键设计决策

- **金额一律用「分」存整数**,杜绝浮点误差
- **状态机集中管控**:非法流转直接 409,每次变更写审计表
- **账本只追加不修改**:冲账=追加负数行;每日核账恒等式(e2e 篡改 1 分钱必被抓出)
- **防超卖/防双花/抢单防冲突**:一律数据库条件 UPDATE,并发安全在存储层保证
- **支付幂等**:模拟支付与微信回调走同一入账函数,联调只换通道不换逻辑
- **公开数据无个案**:大屏/透明中心全部平台级聚合,手机号打码、坐标只到城市级
- **快照优于重算**:凡是要拿出去当证据或当钱的(配送费拆分、申诉证据),
  一律下单/送达当时存快照。事后按当前费率重算,和当时真正收的对不上
- **样本不足就说不足**:分位数、热力图这类统计,低于门槛不给数字只给样本数——
  "这里确实快"和"我们还不知道"是两件事,混在一起就是在编
- **e2e 全链路回归**:`make test` 130 套端到端测试,跑在真实 HTTP 接口上
